Several of the most important controls therefore can't be checked from this code, and I've marked them as needing verification. I didn't change any code.

**Result: Fail.** The delete button destroys data on one click and fails silently. I've marked it must-fix because both problems show directly in the code. The biggest security unknown is whether the server itself checks who is allowed to delete; that's server-side, so it can't be seen here.

## Findings

**[Must-fix · Confirmed] Irreversible delete runs on one click, with no confirmation and no error handling**
- **Evidence:** `src/ProjectRow.tsx:11` calls `api.del(...)` straight from `onClick`. `src/api.ts:3` returns the raw `fetch` result, and nothing checks `res.ok`. `fetch` only rejects on network failure, so a 401, 403 or 500 looks the same to the UI as a success.
- **Impact:**
  - A mis-click deletes a project.
  - If the server refuses the delete, the admin gets no message. The row also stays on screen after a delete that worked, so the admin can't tell what happened.
  - Nothing stops double-clicks, so repeated DELETE requests can be sent.
  - This is what the security reference calls mishandling an error or unusual condition in a high-risk action.
- **Fix:**
  - Ask for confirmation, naming the project and saying the delete can't be undone (or offer undo / soft-delete if the product supports it).
  - Disable the button while the request is pending.
  - Make `api.del` throw when `!res.ok`, and show the error to the admin.
  - Remove or refetch the row only after the server confirms success.
- **Verify:** Mock the delete endpoint to return 403, 500 and a network error. Each case should show an error and keep the row. A success should remove the row once, and a double-click should send one request.

**[Needs verification · high impact] The admin-only check is only in the browser**
- **Evidence:** `ProjectRow.tsx:10` hides the button when `user.role !== "admin"`. That is only a display choice. Anyone can send `DELETE /api/projects/<id>` with their own cookie, without using this UI.
- **Impact:** If the server doesn't check the caller's role for that project, any logged-in user can delete any project by ID. That would be a broken-access-control / IDOR flaw (OWASP A01).
- **Verify:** Log in as a non-admin and send the DELETE directly with curl or devtools, for a project you own and one you don't. Both should return 403, and the project should still exist afterwards.

**[Should-fix · Likely] The project ID is put into the URL without encoding**
- **Evidence:** `ProjectRow.tsx:11` builds the path as `` `/api/projects/${project.id}` ``.
- **Impact:**
  - URL parsing resolves `../` segments. An ID like `../users/42` should make the admin's cookie-authenticated DELETE go to `/api/users/42`, and `?` or `#` in an ID would change the query or fragment.
  - This only matters if IDs can ever contain these characters, for example if they come from the client or an import. Server-generated UUIDs would make it harmless.
  - I tried to confirm the resolution with a quick `node` check, but you declined the command, so it's untested.
- **Fix:** Use `encodeURIComponent(project.id)`. Better, have `api.ts` take `(resource, id)` and encode inside it, so no caller can skip it.
- **Verify:** Delete a row whose ID is `../x`. The request URL in the Network tab should be `/api/projects/..%2Fx`.

**[Needs verification] Cross-site request forgery (CSRF) on a cookie-authenticated DELETE**
- **Evidence:** `api.ts:3` sends `credentials: "include"` and there's no CSRF token or custom header.
- **Why it's only "needs verification":** DELETE forces a CORS preflight, so the actual protection comes from server settings: the CORS allowlist (no reflected origin together with `Access-Control-Allow-Credentials: true`) and `SameSite` on the session cookie.
- **Fix:** Confirm those server settings. Also send a CSRF token or a custom header the server requires on every state-changing request.
- **Verify:** From another origin, try the DELETE with credentials. Also check the response headers and the cookie attributes.

**[Needs verification] Access could be granted wrongly when user data is missing**
- **Evidence:** `auth.ts:3` returns `useContext(UserContext)` without checking it, and `UserContext` isn't in the repo.
- **Impact:** If there's no provider, the page crashes on `user.role`. If the context's default value (or a stale value after logout or switching accounts) has `role: "admin"`, the admin button shows for the wrong person. The server check above would still block the delete, but the UI shouldn't grant access by mistake.
- **Fix:** Make the default `null`, handle a missing user explicitly, and clear the context on logout.

**[Should-fix · Confirmed] Missing API base URL is not caught**
- **Evidence:** `api.ts:1` joins strings with `base + path`.
- **Impact:** If `VITE_API_URL` isn't set, requests go to the relative path `undefined/api/...`. Also, `credentials: "include"` sends cookies to whatever host that variable names, so the build config becomes a trust boundary.
- **Fix:** Throw at startup if the variable is missing, build URLs with `new URL(path, base)`, and require `https` in production.

## What already passes
- `{project.name}` is rendered as JSX text, so React escapes it. The component has no `dangerouslySetInnerHTML`, `href` or other risky place to inject content.
- No secrets or tokens are in client code or in browser storage.
- The delete uses the DELETE method, not a GET link.

## Outside security, briefly
- Every row's button has the same label, "Delete project", so a screen-reader user can't tell the rows apart. Use something like `aria-label={`Delete ${project.name}`}` or visible text that names the project.
