# Work-orders screen review

**Scope:** `src/WorkOrders.tsx` (35 lines) and `src/workorders.css` (10 lines). I only read the code. There's no app shell, no parent that supplies the data, and nothing I could run, so I didn't render anything or test it with a keyboard or screen reader.

**Verdict: Pass with issues.** Nothing I can confirm is a must-fix. Two items could become must-fix depending on how the parent component behaves (#1, #2).

## Highest-impact findings

**1. [Should-fix / needs verification] "Close work order" runs immediately, with no confirmation, pending state or undo**
Evidence: `WorkOrders.tsx:27`. It calls `onClose(wo.id)` directly and sits next to Assign with the same visual weight (`.actions button`, css:7).
Impact: One mis-tap on a phone closes a work order. It then presumably drops out of the "Open" list with no feedback. A double-click can also call `onClose` twice.
Fix: Add an undo toast (better for a frequent action) or a confirm step. Disable the button or show "Closing…" while the request is in flight. Style it differently from Assign.
Verify: Check whether the parent already asks for confirmation. If it doesn't, this becomes a must-fix.

**2. [Should-fix / likely] Focus is lost when a card is closed**
Evidence: No focus handling anywhere in the component. Because the list is "Open" work orders, a closed item is presumably removed from `items`.
Impact: Keyboard and screen-reader users are sent back to `<body>` and lose their place. Nothing announces that the close succeeded.
Fix: After removal, move focus to the next card's heading (or the previous one, or the `h1` if the list is now empty). Announce "Work order closed" in a live region that is always present on the page.
Verify: Tab to Close, press Enter, and check where focus ends up and what VoiceOver or NVDA says.

**3. [Should-fix / likely] Due date can show one day early**
Evidence: `WorkOrders.tsx:23`, `new Date(wo.due).toLocaleDateString()`. Under the ECMAScript spec, a date-only string like `"2026-09-24"` is read as midnight UTC. Anywhere in the Americas that displays as Sep 23. I couldn't run this; it comes from the spec.
Impact: A technician sees the wrong deadline. Also, with no format options, `09/10/2026` could mean September or October depending on who reads it. If the page is server-rendered, the server's timezone and locale can differ from the browser's, which causes a hydration mismatch.
Fix: Check what the API actually sends in `due`. If it's a plain date, format it with `timeZone: "UTC"` and an unambiguous style (`{ dateStyle: "medium", timeZone: "UTC" }`) or parse it as a local date.
Verify: Render with `TZ=America/Chicago`.

**4. [Should-fix] Overdue items aren't flagged, and the list isn't sorted**
Evidence: The due date is plain text (line 23). Items render in whatever order they arrive (line 15). Only P1 has any visual marker (css:8), and P2/P3 have no styles at all.
Impact: The main thing a work-order queue answers is "what do I do next?", and this screen makes people work it out by reading every card. Overdue P1s look the same as P3s due next month.
Fix: Sort by priority, then due date (or confirm the API already does). Add an "Overdue" label in text, not just colour. Consider making "Unassigned" stand out, since that's the triage signal.

**5. [Should-fix] Button labels are inconsistent and partly wrong**
Evidence: Line 26 says `Assign {wo.asset}`; line 27 is a generic `Close work order`.
Impact:
- "Assign Pump 3" reads as assigning the *asset* to someone, not the work order.
- It still says "Assign" when someone is already assigned; it should say "Reassign".
- Two work orders on the same asset get identical button names.
- In a screen reader's list of buttons, every Close button is announced the same way.
Fix: Label both buttons by work order, e.g. `aria-label={`Close work order ${wo.id}`}` or visible text that includes the ID. Show "Reassign" when `wo.assignee` is set.

**6. [Should-fix] Loading, error and empty states drop the page structure**
Evidence: Lines 8–10 return a bare `<p>` or `<div>` with no `<main>` and no `<h1>`.
Impact: The page loses its heading and main landmark exactly when users most need to know where they are. Also, `role="status"` is added to the page already filled in, and screen readers often don't announce live regions that appear that way.
Fix: Always render `<main><h1>Open work orders</h1>…`, and switch only the body. Keep the status region on the page permanently and change its text.

**7. [Should-fix / likely] The raw error string is shown to users**
Evidence: Line 9 displays `{error}` as-is.
Impact: Users may see things like "TypeError: Failed to fetch" or server internals, which are useless to a technician and may leak implementation details.
Fix: Show plain-language copy, and put the technical detail in logs or a collapsible "Details" section.

**8. [Should-fix] Component CSS changes the whole app**
Evidence: css:1 defines `:root` tokens, css:5 styles every `dl` on the page, and css:10 sets the focus style for every `button`.
Impact: Importing this screen restyles `dl` and focus rings elsewhere and can override design-system tokens.
Fix: Scope the rules to `.wo-card dl` and `.wo-card button`, and take tokens from the app's design system.

## Smaller items
- `dt` and `dd` are both muted grey (css:5), so the actual values (assignee, due date) look like secondary text. Make `dd` use `--text`.
- The P1 `▲` in `::before` can be read aloud as "black up-pointing triangle". Use `content: "▲ " / ""` to hide it from screen readers, or add a visible "High" text label.
- Long asset names or issue text with no spaces (serials, part numbers) can overflow the card on a phone. Add `overflow-wrap: anywhere`.
- There's no dark-mode handling: the card has a fixed dark text colour and no background. Check this against the app theme.
- `<main>` inside a component can produce two main landmarks if the app shell already has one. Check this.
- There's no filtering or searching by assignee, priority or asset. Whether that matters depends on queue size (judgment call).

## What already works
- Loading, error (with retry) and empty states all exist, and the empty-state text is specific ("New requests from technicians will appear here").
- The markup is semantic: `ul`/`li`, an `article` labelled by its `h2`, a `dl` for the fields, `<time dateTime>`.
- Buttons are native `<button>` elements, at least 44px tall, with a visible `:focus-visible` outline (#0b57d0 has enough contrast on white).
- Priority is shown as text ("P1"), not just colour.
- The grid is responsive: `minmax(min(100%, 300px), 1fr)` stops cards overflowing on narrow screens, and the action buttons wrap.
- The muted grey (#57606a) has about 6:1 contrast on white, which passes AA.
- It doesn't look generic: no gradients, glass effects or filler copy. It's plain and utilitarian, which suits a maintenance tool.
