## Review: `PriorityQueue.tsx` + `queue.css`

**Verdict: Fail.** One must-fix: screen reader users get no correct feedback after moving an item. The rest is should-fix work around names, layout edge cases, and the animation. I only read the code. There's no `package.json`, so I couldn't render the component or test it with a keyboard or screen reader.

### Must-fix

**1. The screen reader announcement describes the wrong item, and usually says nothing.** *Confirmed in code.*
Evidence: `PriorityQueue.tsx:27`. The message is always built from `items[0]`, whichever item the user moved.
Impact: move item #5 up to #4 and `items[0]` stays the same, so the text doesn't change and nothing is announced. When the top item does change, users hear about "first", not about what they moved. The only feedback for this action is the visual reorder, which is WCAG 4.1.3 (Status Messages).
Fix: keep track of the item that was just moved and announce its new position, e.g. `"Patch CVE-123 moved to position 4 of 12"`. Set it in the click handler, or compare old and new indexes by id.
Verify: with VoiceOver or NVDA, move a middle item and check that you hear the new position.

### Should-fix

**2. Every row's button has the same name, "Move up".** `:34`. When screen reader users jump between buttons they hear "Move up, button" over and over, with no item name. Add the title to the name: `aria-label={`Move ${it.title} up`}`, or add visually hidden text inside the button.

**3. The top item's "Move up" button still works.** `:34` at `i === 0`. It looks active but does nothing (or whatever `onBump` does at the top). Use native `disabled` there, or remove the button from that row.

**4. The animation breaks after the page scrolls.** `:15–18`. Positions are saved in viewport coordinates (`getBoundingClientRect().top`). If you scroll between two updates, every row's saved `prev` is off by the scroll distance, so the whole list slides on the next bump. Anything that shifts the layout above the list does the same. Measure relative to the list instead (`el.offsetTop`, or subtract `listRef.current.getBoundingClientRect().top`). Two smaller problems:
- `positions` never deletes ids that leave the list. An item that comes back animates from an old position.
- If you click again before an animation finishes, the measurement includes the transform that's still running, which causes a jump. Cancel running animations with `el.getAnimations().forEach(a => a.cancel())` before measuring.

**5. The IDs are hardcoded (`pq-h`, `pq-status`, `:25–27`).** If the component is rendered twice, the IDs are duplicated and the second section's `aria-labelledby` points to the first heading. Use `useId()`.

**6. The grid breaks with real-world data.** `queue.css:2`
- The rank column is `2ch`, so ranks from 100 up overflow into the title.
- The title column is `1fr`, whose minimum size is `auto`. A long title with no spaces (a URL or stack trace) widens the grid and causes horizontal scrolling. Use `minmax(0, 1fr)` with `overflow-wrap: anywhere`.
- At 320px, four columns leave very little room for the title. Consider wrapping the score under the title on narrow screens.

**7. Missing states.** An empty `items` array renders a heading and an empty `<ol>`. `onBump` returns `void`, so if it calls a server there's no pending state, nothing stops a double click, and there's no error or rollback path. Whether this matters depends on the `onBump` contract. Please confirm whether it's async.

**8. `<button>` has no `type="button"`** (`:34`). Inside a `<form>`, each button would submit it.

**9. Safari may drop list semantics.** `list-style: none` on `.pq` (`css:1`): I remember WebKit/VoiceOver treating such lists as not being lists, but I haven't checked this against current Safari. If it still does, add `role="list"` to the `<ol>`.

### Judgment calls
- **"Move up" versus score.** The list shows a score but also has manual reordering. If the order comes from the score, users can't tell whether "Move up" changes the score or overrides it. The label or a short hint should say which.
- **Reduced motion.** With reduced motion on, the row jumps instantly and nothing shows where it went. A brief highlight on the moved row, with no movement, would help.
- **Colors and heading level.** `#ddd` and `#0b57d0` are hardcoded, so there are no dark-mode tokens. The `h2` level assumes where the component is placed. Both are fine unless there's a design system to follow.

### What already passes
- Real `<button>`s, so keyboard activation works.
- A visible `:focus-visible` outline, with an offset.
- 40px targets, above the WCAG 2.5.8 minimum of 24px.
- `<ol>` gives the right ordered-list semantics.
- The JS animation checks `prefers-reduced-motion`.
- The section is labeled by its heading.
- Keyed rows mean React most likely keeps the moved row's button in the DOM, so focus follows the item. That's worth a quick keyboard test, since focus behavior depends on how React reorders the rows.
