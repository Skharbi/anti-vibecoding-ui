# AI assistant panel review: `src/AssistantPanel.tsx`

**Verdict: Fail.** The panel has three confirmed trust-boundary flaws. Each one lets text the model writes turn into code running in the page or into real account actions, with nothing checked in between. That matters here because the README says the assistant reads tickets and customer records. Customers write those, so anyone who submits a ticket can steer what the model says: a ticket reading "ignore previous instructions and…" is enough.

This review is from reading the code only. There's no `package.json` or app to run, so nothing was executed, and backend controls are marked "needs verification".

## Must-fix

**1. Model output is inserted into the page as raw HTML (XSS)**
- **Evidence:** `src/AssistantPanel.tsx:22`, `dangerouslySetInnerHTML={{ __html: reply.html }}`
- **Impact:** A ticket containing a prompt injection can get the model to output something like `<img src=x onerror=…>`. That script then runs in a support agent's logged-in session, where it can read customer records and call any API the agent can.
- **Fix:** Have the server return Markdown or structured text, and render it with a sanitizing renderer that has a strict allowlist of tags and attributes (no raw HTML, `http(s)` links only). If you must keep HTML, run it through DOMPurify before rendering. Add CSP and Trusted Types on top as extra protection.
- **Verify:** Put `<img src=x onerror=alert(1)>` and `<a href="javascript:alert(1)">` in a ticket, ask about that ticket, and confirm neither runs.

**2. The model can make any API call, with the user's cookies, without asking**
- **Evidence:** `:14` fetches `r.action.url` with the model-chosen `method` and `body`, plus `credentials: "include"`.
- **Impact:** Any URL, any method, any payload goes out under the agent's authority. The README names refunds and account changes as possible actions. One injected ticket could therefore issue a refund or change an account with no human seeing it. The result of the call is also thrown away, so the agent never learns that anything happened, or that it failed.
- **Fix:**
  - Treat actions as suggestions only. Show a confirmation card with the action type, the customer, the amount or field being changed, and Confirm/Cancel buttons.
  - Replace the model-supplied URL with a small allowlisted set of action types, each mapped to a fixed endpoint in the client.
  - On the server, recheck authorization for the human user, independently of what the model said.
  - Show whether the action succeeded or failed.
- **Verify:** A reply containing `call_api` makes no network request until the user confirms. A reply with a URL outside the allowlist is rejected.

**3. The model can send the browser to any URL**
- **Evidence:** `:13`, `window.location.href = r.action.url`
- **Impact:**
  - A `javascript:` URL runs script, the same risk as finding 1.
  - An outside URL works as an open redirect to a phishing page, from inside a trusted internal tool.
  - Even a harmless URL navigates away from the panel, so the reply is lost.
- **Fix:** Show the link instead of navigating. Allow only `https:` URLs on allowlisted origins, show the destination domain, open in a new tab with `rel="noopener noreferrer"`, and only when the user clicks.
- **Verify:** `javascript:alert(1)` and `https://evil.example` are refused or shown as plain text.

**4. No loading, error, or double-submit handling**
- **Evidence:** `:9–15` never checks `res.ok`, so a 4xx/5xx or non-JSON response makes `res.json()` throw, and the rejection is unhandled. There's no pending state, so the button can be clicked again while a request is running.
- **Impact:**
  - After clicking Ask, nothing on screen changes. On failure the panel stays silent.
  - Repeated clicks each send a request, which together with finding 2 can **run the same action twice** (for example, a double refund).
- **Fix:**
  - Add explicit states: idle, pending, success, and error with a Retry option.
  - Disable Ask while a request is running.
  - Add an `AbortController` to drop stale responses when the user asks again.
  - Block empty questions.
- **Verify:** Fake a 500 error, a timeout, and a slow response followed by a new question. Each case shows the right state, and the older answer never overwrites the newer one.

## Should-fix

- **The answer isn't announced to screen readers.** Nothing tells assistive tech when a reply arrives (`:22`). Put an `aria-live="polite"` status region around the pending and done messages, not around the whole reply. Move focus to or announce errors.
- **Missing `Content-Type` header.** The request at `:10` sends a JSON string with no `Content-Type`, so the browser sends it as `text/plain`. The server may not parse it. It also counts as a "simple" cross-origin request, which skips the browser's preflight check, and it relies on cookies. **Needs verification:** set `Content-Type: application/json` and confirm the server has CSRF protection and rejects other content types.
- **The panel doesn't say what the assistant can access or do.** "Ask the assistant" is generic. The panel should say that answers draw on this customer's tickets and records, and that actions need the agent's confirmation. Label model output as a suggestion, not a verified fact.
- **Hard-coded `id="q"`.** At `:19–20`, two copies of the panel on one page would share the same id and the label would point to the wrong box. Use React's `useId()`.
- **The panel region has no name.** Give the `<aside>` an `aria-label` or a heading so screen-reader users can find it among the page's landmarks.

## Judgment calls

- **One reply at a time.** Each new answer replaces the last, with no conversation history. That may be deliberate, but support work often needs follow-up questions.
- **No keyboard shortcut to submit.** Ctrl/Cmd+Enter is a common expectation in a textarea.
- **No styling.** There's no styling to review yet, so nothing visually generic to flag. When it's styled, it should look like part of the support tool, not a floating chat bubble.

## What already passes

- The label is correctly tied to the textarea (`htmlFor`/`id`).
- The controls are native `<textarea>` and `<button>`, so they're keyboard-reachable and have accessible names without extra ARIA.
- The `<aside>` landmark is a reasonable semantic choice.
