## Must-fix

**1. Checkout sends the user's role, identity and price, all taken from values the browser can change**
Evidence: `src/checkout.ts:12` sends `total`, `isAdmin` and `userId` in the order body. `isAdmin` and `userId` come from `getUser()`, and `src/user.ts:1` reads them from `sessionStorage`. `total` is calculated in the browser at `checkout.ts:7`.
Impact: anyone can run `sessionStorage.setItem("user", '{"id":"victim","isAdmin":true}')` or edit the request in dev tools. If `/api/orders` accepts any of these fields, a user could order on someone else's account, gain admin rights, or set their own price. The client-side flaw is confirmed. Whether it can actually be exploited depends on the server, which needs checking.
Fix: send only `{ items: [{ sku, qty }], coupon }`. The server should work out the user from the session cookie (`credentials: "include"` already sends it), look up prices itself, calculate the total, and ignore or reject any extra fields.
Verify: send a POST with `isAdmin: true`, another user's `userId`, and `total: 0`. The server should reject or ignore all three.

**2. Failed orders are reported as successful**
Evidence: `checkout.ts:14` returns `res.json()` without checking `res.ok`.
Impact: an error response with a JSON body (for example a 400 for an invalid coupon, a 409 for out of stock, or a 401 for an expired session) comes back to the caller as if it were an order. If the proxy returns an HTML 502 page, `res.json()` throws a `SyntaxError` that hides the real cause. The user can end up seeing a confirmation for an order that doesn't exist.
Fix: check `res.ok`. On failure, throw a typed error that carries the status and the server's error body, and give the caller a clear success/failure result.
Verify: mock 400, 401 and 502 responses and confirm each one shows an error, never a confirmation.

**3. Placing an order can create duplicates**
Evidence: `placeOrder` sends no idempotency key and has no timeout or `AbortController`. Nothing in the repo disables the submit button while a request is in progress.
Impact: a double-click, or retrying after a slow request, can charge the customer twice.
Fix: generate an idempotency key once per checkout attempt and send it as a header, and have the server deduplicate on it. Add a timeout. Disable the submit button while the request is pending.
Verify: send the same request twice with the same key and confirm only one order is created.

**4. The Refund button fires on one click, with no confirmation and no pending state**
Evidence: `src/OrderView.tsx:9` is `<button onClick={onRefund}>`. `onRefund` is typed `() => void`, so the component can't know when the refund finishes or whether it failed.
Impact: a refund is destructive and involves money. One accidental click triggers it, a double-click triggers it twice, and there is no success or error message. If the (missing) caller adds a confirmation step, this becomes should-fix, but nothing in the repo shows one.
Fix: make it `onRefund: () => Promise<void>`. Add a confirmation step that states the amount. Disable the button and show "Refunding…" while the request is in progress. Announce the result with a `role="status"` region, and show errors with `role="alert"`. The refund request should also send an idempotency key.
Verify: double-click Refund and confirm only one request is sent. Make the request fail and confirm the error is shown and announced.

## Should-fix

- **`getUser()` is fragile** (`user.ts:1`). If the stored data is corrupt, `JSON.parse` throws and checkout crashes. If nothing is stored, it returns `{}`, so `user.id` is `undefined` and the order is still sent. It also keeps role data somewhere any script injected into the page (XSS) can read it. Take user and role data from a server endpoint, not from storage.
- **Money is calculated with floating-point numbers** (`checkout.ts:7`). `qty * unitPrice` gives results like `0.1 + 0.2 = 0.30000000000000004`. Once fix 1 is done the client total is display-only, but it should still use integer cents.
- **The total is shown as a raw number** (`OrderView.tsx:7`). It renders `Total: 1234.5` with no currency and no locale formatting. Use `Intl.NumberFormat(locale, { style: "currency", currency })`, and add a currency field to `Order`.
- **Order status is never shown.** `status` is in the `Order` type but not rendered, so a user can't tell whether an order is pending, shipped or already refunded. The page also offers Refund without showing any refund state.
- **There are no loading, error or empty states.** `OrderView` assumes a full `order` object is always passed in. Whoever renders it has to handle loading, not-found and forbidden cases.

## Needs verification (backend)

- **Hiding a button is not access control.** `permissions.canEdit` and `canRefund` (`OrderView.tsx:8-9`) only control what the page shows. The `/orders/:id/edit` route and the refund endpoint must check on the server that the user owns the order or has the right role. `ownerId` is not used in the client, which is fine.
- **CSRF protection.** `/api/orders` is a cookie-authenticated POST. Check whether the session cookie is `SameSite` and whether the endpoint uses a CSRF token.
- **Coupon checks.** The server must validate coupons, including how many times one can be used.

## What already passes

- The page uses real HTML elements correctly: an `<a>` to go to the edit page and a `<button>` for the refund action, with no misused ARIA.
- The heading `Order {id}` is a sensible `h1` for this page.
- `credentials: "include"` is the right basis for authenticating by session cookie on the server, once the body stops claiming who the user is.
