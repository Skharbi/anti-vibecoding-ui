## Must-fix

**1. The permission check lets people through when it fails**
Evidence: `src/ProjectSettings.tsx:11`: `.catch(() => setCanEdit(true))`. At line 9, `r.json()` runs without first checking `r.ok`.
Impact: If the permissions request fails for any reason (network drop, timeout, a 500 or gateway error that returns HTML), the page shows the Delete button. That includes users who aren't allowed to edit.
Fix: Treat any failure as "no permission." Check `r.ok` before parsing, use `.catch(() => setCanEdit(false))`, and show a "Couldn't load permissions — Retry" state instead of hiding the problem.
Verify: Make `/permissions` return a 500 or fail the network request. The Delete button must not appear.
Needs checking: `DELETE /api/projects/:id` must reject users without permission on the server. Hiding the button doesn't stop anyone from calling the endpoint directly.

**2. "Project deleted." shows before the delete succeeds, and stays if it fails**
Evidence: line 15 sets `deleted = true` before any request is sent. Lines 16–21 swallow every error (`catch {}`), and after 3 failed attempts the function just ends. Line 24 then shows "Project deleted." no matter what happened.
Impact: If the delete returns 403, 500 or never reaches the server, the user is still told it worked. The project remains, and they have no way to retry.
Fix: Track `idle → deleting → deleted | error` states. Show "Deleted" only after an `ok` response. On failure, show the error and a retry option.
Related: the retry loop also retries 4xx responses, which will never succeed, and it has no backoff between attempts. A retry after a network error can also get a 404 if the first attempt actually went through. Count 404 as deleted and only retry network errors and 5xx responses.
Verify: Make DELETE return a 500. The user should see an error, not "Project deleted."

**3. One click permanently deletes the project**
Evidence: line 28: `onClick={deleteProject}` runs immediately, with no confirmation.
Impact: A single misclick deletes the project.
Fix: Add a confirmation dialog that names the project and says what will be lost. For a high-impact delete, have the user type the project name. Offer undo or soft delete instead if the backend supports it.
Verify: Clicking Delete opens the dialog. Cancelling, pressing Esc or clicking the backdrop leaves the project untouched. Focus moves into the dialog and returns to the button when it closes.

## Should-fix

**4. `projectId` goes into URLs without encoding** (lines 8, 18)
If `projectId` comes from the route or other user-controlled input, a value like `x/../../users/me` could send a request with the user's cookies (`credentials: "include"`) to a different endpoint. I haven't confirmed this because I can't see where `projectId` comes from. The fix is cheap either way: wrap it in `encodeURIComponent(projectId)`.

**5. No loading, error or "no permission" state** (lines 4, 28)
`canEdit` starts as `false`, so while permissions load, and for users who can't edit, the page is just a heading. Nothing says why the controls are missing. Add a loading state, an error state with retry, and a short note such as "Only project admins can delete this project."

**6. Out-of-order permission responses** (lines 7–12)
If `projectId` changes quickly, a slow response for the previous project can set `canEdit` for the current one. Use an `AbortController`, or ignore the response in the effect's cleanup.

**7. Screen readers and focus after deleting** (line 24)
The Delete button disappears while it has focus, so focus drops to `<body>`. The "Project deleted." text isn't announced to screen readers. Wrap it in `role="status"`, or better, send the user to the project list with a confirmation message there. Right now they're left on the settings page of a project that no longer exists.

**8. The page never names the project** (line 27)
"Project settings" doesn't say which project, which matters most right before a permanent delete. Show the project name in the heading and in the confirmation dialog.

**9. Hardcoded spacing values** (lines 24, 26, 27)
Values like `13px 21px`, `17px 23px`, `22` and `7` are inline styles that don't follow any scale, and the two states use different padding. If the app has design tokens or shared components, use them. That includes a danger-style button variant, since the delete action currently looks like any other button.
