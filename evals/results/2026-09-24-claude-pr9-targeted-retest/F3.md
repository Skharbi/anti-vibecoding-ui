## What I fixed

**Saving twice with the same result gave no announcement the second time** (`src/NotificationSettings.tsx:13-14`, `:37`)
The status message sits in a `role="status"` region, and screen readers only announce it when its text changes. If a user saves once and gets "Notification settings saved.", then saves again and gets the same message, the text doesn't change. React leaves the page untouched and nothing is announced. The same happens when an error repeats on retry, which is when the user most needs to hear it.

**Fix:** `submit` now clears the status before saving starts, so each result is new text and gets read out. It also stops an old "saved" or error message from staying on screen while a new save is running.

## Not changed, worth checking

- **Save button during saving:** it's disabled while a save runs. When a button that has focus is disabled, recent browsers drop focus from it, and the "Saving…" label on a disabled button isn't reliably read out. The save is short and the result is announced by the status region, so I didn't treat this as a failure. If testing with NVDA or VoiceOver shows focus jumping around, keep the button enabled with `aria-disabled` while saving and ignore extra clicks in `submit`.
- **Error urgency:** errors use the same polite status region as success messages, so a screen reader waits until it's idle to read them. That's acceptable. Moving errors to `role="alert"` would mean a second region that exists from page load, not switching the role on the fly. Whether errors should interrupt is your call.
- **Heading level:** `<h2>` is right only if the page around the panel has an `<h1>`. I can't see that page from here.
- **Fieldset border:** `#c4c7cc` is low contrast, about 1.7:1 on white. It only groups content visually, and the `<legend>` identifies the group, so it doesn't fail WCAG.
