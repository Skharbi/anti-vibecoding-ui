## Needs verification first: browser support

**[Likely must-fix] The whole stepper depends on the Navigation API and has no fallback**
Evidence: `src/checkoutStepper.js:3` and `:19` call the global `navigation` directly, with no check that it exists.
Impact: in any browser without `window.navigation`, line 3 throws when the module loads. The click handler on line 16 is never attached, so **Continue does nothing** and checkout is blocked. That part is certain from the code. The unverified part is which of your browsers lack the API. From memory: Chrome and Edge have had it since 102. Firefox and Safari only added it recently, and I don't believe iOS Safari 17 or 18 has it. Since you support iOS Safari 17+, this is very likely a hard failure there.
Fix: base the stepper on `history.pushState` plus `popstate`, which works in every browser you support. Or check `if ("navigation" in window)` and fall back to that path.
Verify: check MDN's compatibility data for `Window.navigation` and `NavigateEvent.intercept()`, then test on a real iOS 17 device or simulator.

## Must-fix (confirmed in code)

1. **The page opens with an empty step.** A first page load doesn't fire a `navigate` event, and nothing renders the step on startup (`:3–14`). Users see "Checkout", a blank area and a Continue button. Fix: render the step named in `location` when the module loads.

2. **Continue on the last step breaks.** On `review`, `steps.indexOf("review") + 1` is 4, so `next` is `undefined` and the page goes to `?step=undefined` (`:18–19`). That fails the check on line 6, so it's a full page reload into an empty checkout. Nothing places the order, and the button still says "Continue" on the step where it should say "Place order". Fix: handle the last step explicitly (submit the order, with its own label and pending state).

3. **Going back to the start leaves the wrong step on screen.** If checkout starts at a URL with no `?step`, going from `?step=shipping` back to that first entry hits line 6 (`step` is `null`) and returns without re-rendering. The URL now means "cart" but the shipping step is still displayed. Fix: treat a missing `step` as `"cart"` everywhere, as line 17 already does.

4. **Steps can be skipped without validation.** Continue always moves forward (`:16–20`), and step modules have no way to block it. Visiting `?step=review` directly also works. A user can reach review with no shipping or payment details. Fix: have each step module export something like `validate()` or `canLeave()` and check it before navigating. The server must enforce this regardless.

5. **Keyboard focus is lost on every step change.** `intercept()` defaults to `focusReset: "after-transition"`, which moves focus back to the top of the page after each step. A keyboard or screen-reader user presses Continue and loses their place, and nothing announces the new step. Fix: after rendering, move focus to the new step's heading (with `tabindex="-1"`), and update `document.title` to something like "Shipping – Checkout (2 of 4)".

6. **Fast clicks can show the wrong step or two steps at once.** The handler empties the container, waits for the import, then renders (`:9–11`). It never checks `event.signal`. If you double-click Continue, the first (cancelled) navigation can still render when its import finishes, possibly after the second one. Fix: check `event.signal.aborted` after `await`, and use `container.replaceChildren()` before rendering.

## Should-fix

- **No loading or error state.** The container is emptied before the import (`:9`), so every step change flashes blank. If `import()` fails (flaky mobile connection, stale deploy), the page stays blank with no message and no retry. Show a pending state, catch the error, and offer "Retry".
- **The intercept guard is too loose.** Line 6 checks only the query string. It should also require `event.canIntercept` (otherwise `intercept()` throws for cross-origin URLs), and skip `event.formData` and `event.downloadRequest`. Without the `formData` check, a step form that POSTs to a `?step=` URL would be intercepted and its submitted data silently dropped.
- **No progress indicator.** Users can't see which step they're on or how many remain. Add an ordered list of steps with `aria-current="step"` on the current one, and let users go back to completed steps.
- **No viewport meta tag** in `checkout.html:1`. iOS Safari lays the page out at about 980px wide and zooms out, so the page is tiny on a phone. Add `<meta name="viewport" content="width=device-width, initial-scale=1">`.
- **One generic Continue button for every step.** It sits outside any `<form>`, so pressing Enter in a shipping field won't submit. Each step would do better with its own form and a specific submit label ("Continue to payment").

## What already works

- `step` is checked against a fixed list before the dynamic `import()` (`:6`), so the URL can't make the page load arbitrary code.
- Clearing the container with `innerHTML = ""` is safe; there's no injection risk.
- The page uses `<main>`, `<h1>`, `lang` and a real `<button type="button">`.
