## Must-fix (confirmed in the code)

**1. Logout clears nothing, so the next person on the device sees the previous patient's records**
Evidence: `src/session.ts:12-14` only redirects to `/login`. The `accessToken`, `user` and `records` values all stay in `localStorage`.
Impact: On a shared computer (a clinic kiosk, a family laptop), `loadRecords()` in `src/records.ts:4-5` returns the cached records **before it checks auth at all**. The next person who opens the portal sees the previous patient's diagnoses, medications and lab results, and doesn't even need to log in.
Fix: Logout should remove every user-specific key (or everything the app stores). It should also call a server logout/revoke endpoint, then redirect with `location.replace` so Back doesn't return to the old page.
Verify: Log in, load records, log out, then check that DevTools → Application → Local Storage is empty and that `loadRecords()` makes a network request.

**2. Patient health data is stored in `localStorage` indefinitely, and the cache isn't tied to a user**
Evidence: `src/records.ts:8` writes the full records response (MRN, name, date of birth, diagnoses, medications, labs, per `src/types.ts:1`) to `localStorage` with no expiry. `login()` never clears it.
Impact: The data survives closing the browser, and any script running on the site can read it. If a different patient logs in on the same browser, they get the **first patient's** records, because the cache is read before any request is made. Treat this as a serious privacy risk. I'm not calling it a HIPAA violation, because that depends on scope I can't check from here.
Fix: Don't store health data in browser storage. Keep it in memory, for example in the component's state or a query cache. If you really need offline access, that needs its own threat model and a design with encryption and clearing on logout.
Verify: After loading records, no health data should appear in any browser storage.

**3. Error responses get cached as if they were records, permanently**
Evidence: `src/records.ts:6-8` never checks `res.ok`. A 401, 403 or 500 response with a JSON body is saved as `"records"` and returned to the page. Every later call serves that cached error, because nothing ever refetches.
Impact: One expired token or server hiccup leaves the patient with a broken records view until they clear their storage. It also means expired sessions are never noticed.
Fix: Check `res.ok`. On 401, clear the session and send the user to login. On other errors, throw a typed error so the page can show an error state with a retry option. Never cache a failed response.
Verify: Mock a 401 and a 500 and confirm neither one gets stored and the right state appears.

**4. `login()` "succeeds" when the login actually failed**
Evidence: `src/session.ts:2-5` also never checks `res.ok`. A failed login leaves `accessToken` undefined, and `setItem` stores the literal string `"undefined"`. The promise still resolves, so the caller carries on as if the user were logged in.
Impact: The user gets no clear feedback that login failed, and every later request goes out with `Bearer undefined`. `authHeader()` (`src/session.ts:9`) also sends `Bearer null` when no token exists.
Fix: Throw on responses that aren't OK or that have no token. Make `authHeader()` fail, or send the user to login, when there's no token.
Verify: Test that a login with wrong credentials rejects and that the UI shows an error.

## Should-fix

**5. The access token is stored in `localStorage`** (`src/session.ts:4`). Any XSS anywhere on the site could steal it. Better options are an HttpOnly, Secure, SameSite session cookie (which then needs a CSRF defense for state-changing requests), or keeping a short-lived token in memory and refreshing it through an HttpOnly cookie. How bad this is depends on the token's lifetime, which I couldn't check from this repo.

**6. No handling for session expiry or inactivity.** The app has no idle timeout, reacts to no 401s, and doesn't share logout across open tabs. For a patient portal on shared devices, logging users out after inactivity and syncing logout across tabs (via the `storage` event or a `BroadcastChannel`) is the usual expectation.

**7. `PatientRecord` is never used.** `loadRecords()` returns `any` (`src/records.ts:3`), so a change in the API's response shape reaches the UI without any warning. Type the return value and ideally validate the response at runtime.
