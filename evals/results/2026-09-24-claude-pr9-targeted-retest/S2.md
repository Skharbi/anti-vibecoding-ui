## final
The main problem is security: anyone who can post a comment can run script in the browser of everyone who reads it. There are also real form bugs, including one that can lose what the user typed. **Verdict: Fail.**

This review covers `src/Comment.tsx` and `src/CommentForm.tsx`. The repo has no commits, no `package.json` and no CSS, so this was a code-only review. I tried to run `marked` in the scratchpad to show the attack happening, but that command needed approval and wasn't run.

## Must-fix

**1. Stored XSS: comment bodies are inserted into the page as raw HTML**
- **Evidence:** `src/Comment.tsx:6` turns the user's `comment.body` into HTML with `marked.parse`, and `src/Comment.tsx:10` inserts it with `dangerouslySetInnerHTML`. Nothing cleans the HTML in between.
- **Impact:** `marked` does not sanitize its output; its own docs say so, though I checked that from memory rather than by running it. So a body like `<img src=x onerror=…>` or `[x](javascript:…)` runs in every reader's session. That could let an attacker take over sessions, post as other users, or do anything the reader is allowed to do. Since comments are stored, one post hits every viewer.
- **Fix:** Sanitize before rendering, e.g. `DOMPurify.sanitize(marked.parse(body))`. Better still, render Markdown to React elements (for example `react-markdown` without `rehype-raw`), which doesn't use raw HTML at all. Block link schemes other than `http`, `https` and `mailto`. Also sanitize or validate on the server if the API returns HTML anywhere else. A Content Security Policy helps as a backup, but it doesn't replace sanitizing.
- **Verify:** Add a unit test that renders the payloads above and checks there are no `on*` attributes, no `<script>` and no `javascript:` links in the output.

**2. The draft is erased before the post succeeds**
- **Evidence:** `src/CommentForm.tsx:5` calls `onPost(body); setBody("")` in one go, and `onPost` is typed `=> void`, so the form can't wait for the result or catch an error.
- **Impact:** If the request fails (network, 4xx/5xx), the user's text is already gone and nothing tells them.
- **Fix:** Type it as `onPost: (body: string) => Promise<void>`, `await` it, and clear the box only after it succeeds. On failure, keep the text and show the error next to the form (linked with `aria-describedby`, announced with `role="alert"`).

## Should-fix

- **Double posts:** No pending state (`src/CommentForm.tsx:8`), so clicking Post twice sends two comments. Disable the button and show "Posting…" while the request is in flight.
- **Empty comments:** Blank or whitespace-only bodies are accepted. Add `required`, trim before posting, and consider a `maxLength` that matches the server's limit.
- **Hard-coded `id="c"`** (`src/CommentForm.tsx:6-7`): Two forms on one page (e.g. reply forms) would share the id, and the second label would point to the first textarea. Use `useId()`.
- **Raw timestamp** (`src/Comment.tsx:9`): Readers see an ISO string like `2026-09-24T13:05:00Z`. Keep it in `dateTime`, but show a formatted date (`Intl.DateTimeFormat` or a relative time) and set the timezone on purpose.
- **Markdown is re-parsed on every render:** Minor, but it adds up in long threads. `useMemo` on `comment.body` fixes it.

## Minor
- The local type `Comment` hides the DOM's built-in `Comment` type. Rename it to something like `CommentData`.
- `as string` hides the fact that `marked.parse` can return a Promise if async extensions are ever turned on.

## What already works
- `<article>`, `<header>` and `<time dateTime>` are used correctly.
- The textarea has a visible, linked `<label>`, and the button is a native `type="submit"`.
- The author name is rendered as text, so it's escaped and safe.
- The label tells users Markdown is supported.
