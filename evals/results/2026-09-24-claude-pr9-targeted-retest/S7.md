## Security review: Team Notes frontend

**Verdict: Pass with issues.** I found no confirmed high-impact security flaw in the frontend. The real protections for this app live on the server, and I couldn't see the server code. I only read the code; I didn't run the app or check live response headers.

**What I reviewed:** `src/App.tsx`, `src/main.tsx`, `index.html`, `vite.config.ts` and `package.json`. The app is a single screen that loads notes from `/api/notes` with the user's cookie (`credentials: "include"`) and shows them.

### What already passes
- **No cross-site scripting (XSS) risk found.** Note titles and bodies are shown as plain text (`App.tsx:18`), and React escapes plain text automatically. Nothing in the code inserts raw HTML, runs code from strings, or builds links from note data.
- **No secrets in the code.** There are no API keys, tokens or environment variables in the source or the Vite config.
- **Nothing stored in the browser.** The app doesn't use localStorage, sessionStorage or IndexedDB, and holds notes only in memory.
- **No third-party scripts.** `index.html` only loads the app's own bundle.
- **Errors don't leak details.** A failed load shows only "Couldn't load notes." It never shows status codes, stack traces or server messages (`App.tsx:12`).
- **No cross-site request forgery (CSRF) risk in this code.** The only request reads data (a GET). Nothing in the frontend changes data.

### Should-fix
**1. No lockfile, and every dependency version is a range.**
Evidence: `package.json:3-4` uses `^` ranges, and there's no `package-lock.json` or pnpm/yarn equivalent. The repo also has no commits yet.
Impact: each install can pull different versions of React, Vite and their dependencies, so builds can't be reproduced and a compromised package release would be picked up automatically.
Fix: commit a lockfile and use `npm ci` in CI. Add a dependency audit step, such as `npm audit` plus Dependabot or Renovate.
Verify: two clean installs produce the same dependency tree.

**2. The app crashes if the API returns something that isn't a list.**
Evidence: `App.tsx:11` passes the response straight to `setNotes`, and `notes.map` at line 18 fails on anything that isn't an array. Examples are `{ "error": ... }` with a 200 status, or an HTML login page from a proxy.
Impact: the screen goes blank with no error message and no way to recover. This is a stability problem rather than an exploit.
Fix: check `Array.isArray(data)` before storing it, and show the existing error message otherwise. Also handle 401/403 separately, for example by prompting the user to sign in instead of showing a generic "Couldn't load notes."
Verify: mock a 200 response with `{}` and a 401 response, and confirm the error message appears.

### Needs server-side or deployment checks (can't be settled from the frontend)
- **Who can read which notes.** `/api/notes` must return only the notes the logged-in user's team is allowed to see. The frontend does no filtering, and it shouldn't be relied on to. Test with two accounts on different teams.
- **Session cookie settings.** Confirm the cookie is `HttpOnly`, `Secure` and `SameSite=Lax` or `Strict`. When write endpoints are added, they'll need CSRF protection, because the app sends cookies with every request.
- **Where note content comes from.** Plain-text rendering is safe today. If notes ever render Markdown or HTML, that content must be sanitized first, for example with DOMPurify.
- **Security headers.** There's no deployment config in the repo. On the live site, check for `Content-Security-Policy` (at least `default-src 'self'; frame-ancestors 'none'`), `X-Content-Type-Options: nosniff`, `Referrer-Policy` and HSTS.
- **Known vulnerabilities (unchecked).** I didn't check current advisories. From memory, some Vite 5.x dev-server releases had bugs that let people read arbitrary files. That only matters if the dev server is reachable from the network (`vite --host`). Confirm the installed Vite version is patched and that the dev server is never exposed.
