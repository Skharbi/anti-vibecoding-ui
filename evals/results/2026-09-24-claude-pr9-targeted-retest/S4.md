## final
I reviewed `src/Login.tsx` by reading it only. The repo has no package.json, tests or styles, so I couldn't run it. **Verdict: Fail.** Two things must be fixed, and several more should be.

## Must fix

**1. The `next` parameter allows open redirects and script injection**
Evidence: `src/Login.tsx:12-13`. The raw `?next=` value goes straight into `window.location.href`.
Impact:
- `/login?next=https://evil.example` sends someone who just signed in to an attacker's site. That makes convincing phishing easy ("your session expired, sign in again").
- `?next=javascript:...` also works, because browsers run a `javascript:` URL assigned to `location.href`. That turns the redirect into script running on your site with a fresh session.
- `//evil.example` and `/\evil.example` get around a simple "starts with `/`" check.

Fix: allow only same-origin destinations.
```ts
function safeNext(raw: string | null): string {
  if (!raw) return "/home";
  try {
    const url = new URL(raw, window.location.origin);
    return url.origin === window.location.origin ? url.pathname + url.search + url.hash : "/home";
  } catch {
    return "/home";
  }
}
```
Verify: `next` set to `https://evil.example`, `//evil.example`, `/\evil.example` and `javascript:alert(1)` should all land on `/home`. `/settings?tab=2` should still work.

**2. Error messages are missing or wrong**
Evidence: `src/Login.tsx:10-11`.
- **Network failure shows nothing.** If `fetch` fails (offline, DNS or CORS error), the error isn't caught. The user clicks "Sign in" and nothing happens.
- **Every non-OK status says the password is wrong.** A 500, a 429 rate limit, a 403 CSRF rejection or a locked account all show "Email or password is incorrect." Users will keep retrying or reset a password that was fine. With a rate limit, retrying makes the lockout worse.

Fix: wrap the call in `try/catch`. Show the credentials message only for 401 (or whatever status the API uses for bad credentials). Give 429 and 5xx their own messages, and add a network-error message.

## Should fix

3. **No pending state; the form can be submitted twice.** The button stays active while the request is in flight, and nothing tells the user it's working. Add a `submitting` state, disable the button while it's set, and change the label to "Signing in…". Keep it disabled after success until the page navigates away.
4. **A repeated error isn't announced to screen readers.** `role="alert"` (`:22`) only announces when its text changes. On a second failed attempt the text is identical, so screen-reader users hear nothing. Clear `error` at the start of `submit`. Also add `aria-invalid` and `aria-describedby` to the inputs so the error is tied to them.
5. **Inputs aren't marked `required`** (`:19`, `:21`). Empty submissions go to the server and come back as "incorrect password". Add `required` so the browser checks first.
6. **Hard-coded ids** (`"email"` and `"pw"`). If the form is rendered twice (say, a modal plus a page), the ids clash and the labels point at the wrong fields. Use `useId()`.
7. **No `method="post"` on the form.** If someone submits before JavaScript loads, the browser sends a GET to the current URL. That's harmless today only because the inputs have no `name`. If someone adds `name` attributes later, the password would end up in the URL, browser history and server logs. Adding `method="post"` removes that risk.

## Needs checking on the backend
- **Login CSRF.** The session is cookie-based (`credentials: "include"`). The JSON content type forces a preflight only if the server rejects form-encoded and `text/plain` bodies. Confirm that, or confirm there's a CSRF token.
- **Server-side controls I can't see from here:** session rotation after login, cookie flags (`HttpOnly`, `Secure`, `SameSite`), rate limiting, and headers that stop the page being framed.
