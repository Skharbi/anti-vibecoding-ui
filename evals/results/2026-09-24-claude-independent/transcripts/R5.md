## final
I reviewed `src/SignupForm.tsx`, the only file in the repo. There's no package.json or app to run, so this is a static read of the code, not tested behaviour. **Verdict: Fail.** Several problems either lose what people typed or leave them with no idea what went wrong, which explains the complaints.

## Must-fix

**1. Any server error clears everything the user typed**
- **Evidence:** `SignupForm.tsx:33`: `setForm(initial)` runs whenever `!res.ok`.
- **Impact:** Suppose the email is already taken, or the server hiccups. The user loses their name, email and 12+ character password, and all they see is "Something went wrong" (`:32`). This is probably the biggest single source of frustration.
- **Fix:** Delete line 33. Show the server's actual reason (email already registered, rate limited, etc.) and attach field-specific errors to the field they belong to.

**2. Errors appear on fields the user hasn't touched yet**
- **Evidence:** `:22` checks all fields on every keystroke in any field.
- **Impact:** Typing the first letter of your name immediately shows "Invalid email" and the full password-rules error under two empty fields. The email field also says "Invalid" while you're still typing it.
- **Fix:** Keep track of which fields have been touched. Validate a field when the user leaves it (on blur) and validate everything on submit. After a field has shown an error, re-checking it as the user types is fine, so the error clears as soon as it's fixed.

**3. The request body probably isn't read as JSON (likely; needs a backend check)**
- **Evidence:** `:30` sends `JSON.stringify(form)` without a `Content-Type` header, so the browser sends it as `text/plain`.
- **Impact:** Many backends (Express `json()`, FastAPI, etc.) won't parse that body and will reject the request. Combined with #1, a correctly filled form would fail and then be wiped.
- **Fix:** Add `headers: { "Content-Type": "application/json" }`.

**4. No feedback while submitting, after success, or on network failure**
- **Evidence:** `:30–34`.
  - There's no pending state, so the button can be clicked repeatedly and create duplicate submissions.
  - When `res.ok` is true, nothing happens at all: no redirect and no message.
  - If `fetch` throws (offline, timeout), the promise rejection isn't caught, so the user gets no message.
- **Fix:**
  - Add a `submitting` state that disables the button and changes its label to "Creating account…".
  - Wrap the request in `try/catch` with a message the user can act on, such as a retry option.
  - Make success lead somewhere: a redirect or a confirmation screen.

**5. Fields have no labels, and errors aren't connected to their fields**
- **Evidence:** `:39, :41, :43` use only a placeholder. The error `<span>`s aren't linked to their inputs.
- **Impact:**
  - The placeholder disappears once the user types, so they can't check which box is which.
  - Screen readers announce the fields without names, and they don't announce the errors.
  - This fails WCAG 1.3.1, 3.3.1, 3.3.2 and 4.1.2.
- **Fix:**
  - Give each field a visible `<label htmlFor>`.
  - Link each error with `aria-invalid` and `aria-describedby`.
  - Put the server error in `role="alert"`.
  - After a failed submit, move focus to the first field with an error.

## Should-fix

**6. Password rules only appear as an error**
- **Evidence:** `:14–15`.
- **Impact:**
  - Users only discover the rules by breaking them.
  - `[^\w]` doesn't count `_` as a symbol, so `Password_2024x` is rejected with no explanation.
  - There's no show-password toggle, and with a 12+ character composed password that means a lot of mistyping.
- **Fix:** Show the requirements under the field from the start, ideally as a checklist that ticks off as each rule is met. Add a show/hide toggle.

**7. Wrong input types and no autocomplete hints**
- **Evidence:** `:41` is a plain text input for email. None of the inputs have `autoComplete`.
- **Impact:**
  - Phones don't show the email keyboard.
  - Browsers don't autofill name and email.
  - Password managers don't offer to generate a strong password, which is the easiest way for users to meet your strict rules.
- **Fix:**
  - Email field: `type="email"`, `autoComplete="email"`.
  - Name field: `autoComplete="name"`.
  - Password field: `autoComplete="new-password"`.
  - Add `noValidate` on the form so the browser's own popups don't clash with your error messages.

**8. Vague error text**
- **Evidence:** "Required" and "Invalid email" (`:12–13`).
- **Fix:** Say what to do, e.g. "Enter your full name" and "Enter an email like name@example.com".

## Judgment call

- **Password composition rules.** Requiring uppercase, a number and a symbol makes signup harder. NIST SP 800-63B now advises against these rules and recommends a length minimum plus a check against known-breached passwords. It's worth deciding whether you really need them. Whatever you choose, remember the client-side check is only for convenience: the server has to enforce the same policy.

## What already works

- It's a real `<form>` with a `type="submit"` button, so pressing Enter submits it.
- The password field is masked.
- Submitting re-runs validation before anything is sent.
- The email check is reasonably lenient; it doesn't reject valid addresses.
