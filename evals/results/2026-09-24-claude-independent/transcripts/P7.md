## Must-fix

**1. Switching accounts shows the previous account's invoices**
Evidence: `src/useInvoices.ts:3`, `:6`, `:8` and `src/AccountSwitcher.tsx:4-5`
- The cache is shared across the whole module and uses the fixed key `"invoices"`. Nothing ties it to the signed-in account.
- `switchTo` changes the session on the server, then moves to `/billing` without reloading the page. The module cache survives that.
- When `/billing` mounts, `useInvoices` finds the old entry, skips the fetch (line 8) and shows the previous account's invoices.

Impact: users see another account's billing data, which matters most when accounts belong to different clients or tenants. Logging out without a full reload has the same problem.
Fix: store entries under the account ID (`invoices:${accountId}`), and clear or invalidate the cache whenever the session changes, in `switchTo` and on logout. If the account ID isn't available on the client, clear the whole cache on switch.
Verify: load `/billing` as account A, switch to B, and check that the network tab shows a new `/api/me/invoices` request and that B's rows appear.

**2. The switcher moves to `/billing` even when the switch failed**
Evidence: `src/AccountSwitcher.tsx:3-5`
- `fetch` only rejects on network failure. A 401, 403 or 500 still resolves, so the code goes to `/billing` anyway.
- If the network does fail, the promise rejection is never caught, so nothing happens and the user sees no message.

Impact: the user thinks they are working in account B while the session is still A. That's misleading feedback during an account-context change.
Fix: check `res.ok`. Only navigate on success, and show an error otherwise.

**3. Error responses get cached as invoice data**
Evidence: `src/useInvoices.ts:9`
- There is no `r.ok` check, so a 401 or 500 JSON body is parsed and stored in the cache as if it were invoices.
- It stays there for the life of the page and can't be retried.
- Non-JSON responses and network errors cause unhandled rejections.

Fix: throw when `!r.ok`, and don't cache failures.

## Should-fix

**4. The request body may not be read as JSON (CSRF needs checking on the backend)**
Evidence: `src/AccountSwitcher.tsx:3`
- The body is JSON, but no `Content-Type` is set, so the browser sends `text/plain`. Many servers won't parse that as JSON.
- If the server does accept `text/plain` JSON, this cookie-authenticated POST can be sent cross-site without a CORS preflight. That makes it a CSRF risk for a session-changing endpoint.

Fix: set `Content-Type: application/json`. Also confirm the backend rejects other content types and has CSRF protection (token or SameSite cookies). I can't confirm that from the frontend code.

**5. The hook has no loading or error state**
Evidence: `src/useInvoices.ts:11`
- It returns only `data`, which is `undefined` both while loading and after a failure.
- The type is `unknown`, so callers have to cast it without any checks.

Fix: return `{ data, error, status }` and type the invoice shape.

**6. Duplicate requests and state updates after unmount**
Evidence: `src/useInvoices.ts:7-10`
- If two components mount before the first response arrives, both send the request, because the cache only holds finished results.
- There's no `AbortController`, so a late response can land after the component has unmounted. Combined with finding 1, a late response from account A can also overwrite the cache after the switch to B.

Fix: cache the in-flight promise under the account-scoped key, and abort or ignore the request on unmount or account change.

**7. The switcher shows no progress or current account**
Evidence: `src/AccountSwitcher.tsx:8`
- Buttons stay enabled while the switch is in progress, so double-clicks or clicking A then B can race.
- Nothing marks the active account. Use `aria-current="true"` plus a visible marker.
- The list has no accessible name. Add a heading or `aria-label="Switch account"`.
- There is no success or failure announcement for screen readers. Use a status region.
