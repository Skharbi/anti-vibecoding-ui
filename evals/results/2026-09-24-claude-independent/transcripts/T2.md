## final
I rewrote `sql/monthly_revenue.sql` and added the two indexes it needs in a new file, `sql/indexes.sql`. I haven't run either one: I couldn't check whether Postgres is installed here, so there's no `EXPLAIN ANALYZE` or timing to back this up yet.

**The rewritten query:**
```sql
SELECT c.id, c.name, SUM(o.total) AS month_total
FROM customers c
LEFT JOIN orders o
       ON o.customer_id = c.id
      AND o.created_at >= date_trunc('month', now())
      AND o.created_at <  date_trunc('month', now()) + interval '1 month'
WHERE reverse(lower(c.email)) LIKE 'moc.emca@%'
GROUP BY c.id
ORDER BY month_total DESC NULLS LAST;
```

**What was slow and what changed:**

1. **No index could be used on `orders`.** `orders.customer_id` had no index at all. Also, `date_trunc('month', o.created_at) = ...` wraps the column in a function, so Postgres can't use an index on it. Every customer's subquery had to scan through orders.
   - **Fix:** the date check is now a range: from the start of this month up to, but not including, the start of next month. Both the old check and the new one use the session time zone, so results are identical, including across daylight-saving changes.
   - **New index:** `orders (customer_id, created_at) INCLUDE (total)`. It answers each customer's lookup straight from the index, and it also covers the foreign key, which speeds up deletes on `customers`.

2. **The email filter always scanned the whole table.** `LIKE '%@acme.com'` starts with a wildcard, so a normal index can't help.
   - **Fix:** the query now matches the reversed email, `reverse(lower(email)) LIKE 'moc.emca@%'`. That turns it into a starts-with match, which a normal index can serve. It matches the same rows as before.
   - **New index:** an expression index on `reverse(lower(email))`. The query only uses it if its expression stays exactly as written.

3. **Correlated subquery replaced with `LEFT JOIN` + `GROUP BY`.** The old version always ran one subquery per customer. With a join, Postgres can pick either a per-customer index lookup (when few customers match) or a single pass over this month's orders (when many do). Output is unchanged:
   - Customers with no orders this month still appear, with `NULL`, and sort last.
   - Grouping by the primary key alone is enough to also select `c.name`.

**Before you deploy:**
- **`CONCURRENTLY`:** the index statements use it so they don't lock the tables while building. It can't run inside a transaction, so run the file outside a transaction block (and outside any migration tool that wraps it in one).
- **Changing domains:** if the domain will change or you need other kinds of partial matches, a `pg_trgm` GIN index on `lower(email)` would let you keep the original `LIKE '%@...'`. It's more flexible but bigger and slower to update.
- **Filtering by domain often:** a stored `email_domain` column with a normal index would be simpler than either option.
- **Checking the plan:** run `EXPLAIN (ANALYZE, BUFFERS)` against real data. You should see index scans on both new indexes and no sequential scans.
