## Arabic order details review: Fail

I only read the code (`src/OrderDetails.tsx`, `locales/ar.json`). Nothing was rendered or clicked. The screen sets `dir="rtl"`, but the layout and formatting underneath are still written for left-to-right English. The result is a mirrored English screen, not a proper Arabic one.

### Must-fix

**1. Left/right classes break the RTL layout**
Evidence: `text-left` (`:8`, `:11`), `mr-2` (`:9`), `ml-4` (`:12–14`), `pl-3 border-l-4` (`:17`).
Impact: The heading and back link line up to the left, which is where Arabic lines end. The icon's gap is on its outer side, so it touches the text. The detail rows are indented from the wrong side. The accent border on each item sits at the end of the row instead of the start.
Fix: Use start/end classes instead: `text-start`, `me-2`, `ms-4`, `ps-3 border-s-4`. These need Tailwind 3.3 or later.

**2. Arrows point the wrong way**
Evidence: `ArrowLeft` for "back" (`:9`), `ChevronRight` on each item (`:20`).
Impact: In RTL, "back" should point right and "go forward" should point left. As written, the back link seems to point forward.
Fix: Add `rtl:-scale-x-100` to both icons, or pick the icon based on direction. Icons that don't mean a direction (like a checkmark) should stay as they are.

**3. The "request return" button cuts off its label and does nothing**
Evidence: `:24` has `w-32 whitespace-nowrap overflow-hidden`, and the label is "طلب إرجاع المنتجات واسترداد المبلغ" (about 34 characters). The button has no `onClick` and no `type`.
Impact: At 128px wide, most of the label is hidden, with no "…" to show it was cut. The button is also the only action on the screen, and clicking it does nothing.
Fix: Remove the fixed width and `overflow-hidden`, and use a shorter label such as "طلب إرجاع". Connect the button to the returns flow. Returns have consequences, so the flow needs a confirmation step and a state for orders that can't be returned.

**4. The item count uses the wrong Arabic plural**
Evidence: `:19` renders `{i.qty} {t("items")}`, and `"items": "قطع"`.
Impact: Arabic has six plural forms. "قطع" is only correct for 3–10. For example, 1 should be "قطعة واحدة", 2 should be "قطعتان", and 11 or more should be "قطعة". Most orders will show a grammatically wrong count.
Fix: Use ICU plural messages or `Intl.PluralRules("ar")`, with keys for `zero/one/two/few/many/other`. Pass `qty` into the message instead of joining strings.

**5. Date and currency are hard-coded in US English format**
Evidence: `toLocaleDateString("en-US")` (`:13`) and `` `$${total.toFixed(2)}` `` (`:14`).
Impact: Dates show as `9/24/2026`, which Arabic readers may read as day/month. The price always shows as US dollars in English format, and the `Order` type has no currency field.
Fix: Use `Intl.DateTimeFormat(locale, { dateStyle: "long" })` and `Intl.NumberFormat(locale, { style: "currency", currency: order.currency })`, and add `currency` to `Order`. Decide which digits to use: Arabic-Indic (٠١٢) or Western (012, via `-u-nu-latn`). That's a product choice.

### Should-fix

**6. Order ID and customer name can display out of order**
Evidence: `#{order.id}` (`:11`) and `{order.customerName}` (`:12`).
Impact: How mixed-direction text displays depends on the ID's format. A numeric ID shows as `#1234`, but an ID like `ORD-12` can have the `#` land on the other side. Latin customer names that end in numbers or punctuation can also display out of order.
Fix: Wrap the ID in `<bdi dir="ltr">` and the name in `<bdi>`.

**7. Labels and values are joined in code**
Evidence: `{t("customer")}: …` on `:12–14`.
Impact: The ASCII colon and word order are fixed in code, so translators can't change them.
Fix: Use one message per line, e.g. `"customer_line": "العميل: {name}"`. A `<dl>` with `<dt>`/`<dd>` pairs would be better markup for this layout anyway.

**8. Item rows look clickable but aren't**
Evidence: `:17–21`. The `<li>` shows a chevron but has no link or handler.
Fix: Either make each row a link to the product or remove the chevron.

**9. Item keys can collide**
Evidence: `key={i.name}` (`:17`).
Impact: Two lines with the same product name (for example, different sizes) produce duplicate keys, which can make React render the wrong rows.
Fix: Add a line-item `id` to the type and use it as the key.

**10. Direction and language are hard-coded in the component**
Evidence: `:7`, `dir="rtl" lang="ar"` on a `div`.
Impact: Popups or dialogs rendered outside this `div` will be LTR. Also, "Arabic version" suggests this may be a separate copy of the component. If so, the Arabic and English screens will drift apart over time.
Fix: Use one component and set `dir`/`lang` on `<html>` from the active locale.

### Judgment calls
- **Digits:** Arabic-Indic vs. Western digits (see #5). This depends on your market (Gulf and Egypt often differ) and should apply to every screen.
- **Font:** No Arabic font or line-height is set. The system fallback may look noticeably different from your Latin font. Worth checking in a render.

### What already passes
- `lang="ar"` is set, so screen readers will use an Arabic voice.
- There is a single `<h1>`, and the list uses `<ul>`.
- The back link is a real `<a href>`.
- All UI text comes from the locale file.
