## Must-fix

**1. Card number and CVC are sent to the logging vendor**
- **Where:** `src/PaymentForm.tsx:7` passes `input: values` (which holds `cardNumber` and `cvc`). `src/errorReporting.ts:12` sends it as-is to `logs.example-observability.io`.
- **Impact:** This happens on every failed payment, including an ordinary decline or timeout. PCI DSS forbids keeping the CVC once a payment is authorised, and card numbers in logs pull the logging vendor, its retention and everyone with log access into PCI scope. It's a reportable data exposure.
- **Fix:** Drop `input` from this call. If you need context, send a few safe fields, e.g. `{ amount, cardLast4 }`.
- **Verify:** Force `/api/pay` to fail (block it in DevTools or return a 500). The request to the logging service should contain no card number or CVC.

**2. The user's access token is sent to a third party**
- **Where:** `src/errorReporting.ts:13` (`token: session?.accessToken`).
- **Impact:** Anyone who can read the logs can act as that user until the token expires. This affects every error the app reports, not just payments.
- **Fix:** Remove the field. If you need to link logs to a session, use an opaque ID the server can look up.

**3. The user's email address is sent**
- **Where:** `src/errorReporting.ts:14`.
- **Impact:** You're sharing more personal data than debugging needs, which creates GDPR processor and retention obligations.
- **Fix:** Send an internal user ID instead of the email.

**4. The full page URL is sent**
- **Where:** `src/errorReporting.ts:15` (`location.href`).
- **Impact:** URLs often carry password-reset tokens, magic-link tokens, OAuth `code`/`state` values or tokens after `#`. Those would all end up in the logs.
- **Fix:** Send `location.origin + location.pathname` and allowlist any query parameters you actually need.

## Should-fix

**5. The logging function accepts any data**
- **Where:** `context.input?: unknown` at `src/errorReporting.ts:3`.
- **Impact:** It invites every caller to pass whole payloads. Findings 1–4 come from that design, not just one bad call site.
- **Fix:** Replace it with a typed, flat set of short text, number and true/false fields. Consider also redacting known sensitive key names (`card`, `cvc`, `password`, `token`, `ssn`…) as a backstop. The backstop doesn't replace fixing the calls.

**6. A failed log call throws its own error**
- **Where:** The `fetch` at `src/errorReporting.ts:5` has no `.catch`.
- **Impact:** If the logging service is down or blocked (ad blockers commonly block these), you get an unhandled promise rejection. If a global `unhandledrejection` handler also calls `reportError`, that can loop.
- **Also:** Browsers cap the total size of pending `keepalive` requests at about 64 KB. A large payload or stack makes the request fail rather than go through.
- **Fix:** Add `.catch(() => {})`, cap the lengths of the message and stack, and consider `navigator.sendBeacon`.

**7. Error messages and stack traces are sent unfiltered**
- **Where:** `src/errorReporting.ts:9–10`.
- **Impact:** The payment message here (`pay failed ${status}`) is safe. Other callers may throw errors that include server response text or user input.
- **Fix:** Truncate them and run them through the same redaction as finding 5.

## Judgment calls and nearby issues
- **Card data passes through your own server:** `submitPayment` sends the raw card number to your own `/api/pay`, which puts your frontend and API fully in PCI scope. A payment provider's hosted card fields or tokenisation (e.g. Stripe Elements) would avoid that, and would make finding 1 impossible. That's a product and compliance decision, so I'm not treating it as a code bug.
- **Missing `Content-Type` on the payment request:** `src/PaymentForm.tsx:4` sends JSON without a `Content-Type: application/json` header. If the server relies on that header to parse the body, payments could fail, and each failure currently leaks card data through finding 1. Worth checking.
- **No sampling or dedup:** There's no sampling, deduplication or rate limiting, so a repeating error could flood the logs.

## What's already fine
- Using `keepalive` is right for errors that happen while the page is closing.
- `release` is included, so errors can be matched to a deployment.
- Errors that aren't `Error` objects are handled safely.
- `submitPayment` re-throws after logging, so the UI can still show the failure.

## Suggested shape of the fix
```ts
type ErrorContext = { action: string; [k: string]: string | number | boolean | undefined };

export function reportError(err: unknown, context: ErrorContext) {
  const session = getSession();
  const body = JSON.stringify({
    message: (err instanceof Error ? err.message : String(err)).slice(0, 500),
    stack: err instanceof Error ? err.stack?.slice(0, 4000) : undefined,
    ...context,
    userId: session?.userId,
    path: location.origin + location.pathname,
    ua: navigator.userAgent,
    release: import.meta.env.VITE_RELEASE,
  });
  fetch("https://logs.example-observability.io/ingest", { method: "POST", keepalive: true, body })
    .catch(() => {});
}
```
The payment call would then be `reportError(e, { action: "submitPayment", amount: values.amount })`. `session.userId` is assumed to exist, since I couldn't see the session module.
