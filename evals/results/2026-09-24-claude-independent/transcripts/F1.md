## Work-orders screen review

I reviewed `src/WorkOrders.tsx` and `src/workorders.css`. The repo has no `package.json`, no app shell and no data layer, so I couldn't render the screen. Everything below comes from reading the code. Where something depends on how the parent component or backend behaves, I've marked it **likely**.

**Result: Fail.** Three must-fix issues, all in the close and due-date paths.

### Must-fix

**1. Closing a work order has no confirmation, no undo and no pending state**
Evidence: `WorkOrders.tsx:27`: `onClick={() => onClose(wo.id)}` fires immediately, and `onClose` returns `void`.
Impact: One mis-tap on a phone closes a work order for real equipment. Nothing shows while the request runs, so a double-click can send the close twice. Nothing in this component shows whether it worked.
Fix: Add either an undo toast ("WO-1042 closed · Undo") or a confirmation that names the asset. Change the handlers to `(id) => Promise<void>`, disable the button and show "Closing…" while the request runs, and show an error on the card if it fails.
Verify: Double-click Close and confirm only one request goes out. Force a server error and confirm the card stays and shows the error.

**2. Keyboard focus is lost after closing a card (likely)**
Evidence: `:27` together with `items.map` at `:15`. When the parent removes the closed item, the button that had focus is deleted.
Impact: Keyboard and screen-reader users land back at the top of the document and have to tab through the whole list again to process the next work order.
Fix: After a successful close, move focus to the next card's heading or button, or to the previous one if it was the last card. Use `tabIndex={-1}` on the `h2` and a ref map. Also announce "Work order closed" through a persistent `role="status"` region.
Verify: Close the middle card with only the keyboard and confirm focus lands on the next card.

**3. The due date can show the wrong day (likely)**
Evidence: `:23`: `new Date(wo.due).toLocaleDateString()`. If `due` is a date-only ISO string like `"2026-09-24"`, JavaScript reads it as midnight UTC. Anywhere in the Americas that displays as **9/23**. An invalid value renders as "Invalid Date". Calling `toLocaleDateString()` with no options also gives ambiguous output like `9/10` versus `10/9`.
Impact: Technicians see deadlines a day early, which is the wrong information on the one field that drives the work.
Fix: Parse date-only values as local dates, or format with `timeZone: "UTC"`. Use explicit options such as `{ month: "short", day: "numeric" }` and guard against invalid dates.
Verify: Run with `TZ=America/Chicago` against a date-only fixture.

### Should-fix

- **Buttons have ambiguous or unstable names.** "Close work order" (`:27`) gets the same name on every card, so a screen reader's button list shows N identical entries. "Assign {asset}" (`:26`) goes the other way: long asset names make the visible labels bloated. Also, if two work orders exist for the same pump, their names collide. Keep the visible text short ("Assign" / "Close") and add context with a visually hidden span containing the work-order ID and asset. "Close" can also be misread as "dismiss"; consider "Mark complete" if that's what it means in your domain.
- **"Assign" still shows on work orders that already have an assignee** (`:22` and `:26`). It should read "Reassign" when `wo.assignee` is set.
- **Priority is only styled for P1.** `.prio`, `.prio-P2` and `.prio-P3` aren't defined in the CSS, so P2 and P3 look like plain grey text. The P1 `▲` comes from CSS `::before`, which most screen readers will read aloud ("up-pointing triangle P1"). Either give it empty alt text (`content: "▲ " / ""`) or render the icon in the markup with `aria-hidden`.
- **Overdue work orders aren't flagged and the list isn't sorted.** The list renders in whatever order it arrives. In a maintenance queue, overdue items and P1 items are the first thing people look for. Add an overdue indicator that uses text as well as color, and a default sort by priority then due date, or confirm the API already sorts.
- **The loading, error and empty states drop the page structure** (`:8–10`). Each returns early without the `<main>` and `<h1>`, so the heading and landmark disappear. The page also jumps, and it blanks completely on every refetch after an assign or close. Keep the header rendered in every state. Only swap out the list area, and keep stale data visible while refreshing.
- **The raw error string is shown to users** (`:9`). "Couldn't load work orders: TypeError: Failed to fetch" means nothing to a technician. Map known errors to plain-language messages and log the raw one. React escapes the string, so this is not an XSS risk.
- **Long asset names and IDs overflow their cards.** `.wo-card`, `h2` and `p` have no `overflow-wrap`, so an unbroken ID like `CHILLER-B2-COMPRESSOR-03` runs past the 300px card. Add `overflow-wrap: anywhere`, plus `min-width: 0` on the grid items.
- **Several CSS rules leak into the rest of the app.** The bare `dl` rule (`css:5`), the global `button:focus-visible` rule (`:10`) and the `:root` tokens all apply app-wide. On top of that, the browser's default `dd { margin-left: 40px }` is never reset, which wastes about 40px of each narrow card. Scope the rules under `.wo-card` and reset `dl` and `dd` margins.

### Needs verification outside this file

- **Duplicate `<main>`:** `<main>` sits inside a component (`:12`). If the app shell also renders one, the page has two main landmarks.
- **Permissions:** Assign and Close render for every user. Hiding a button doesn't enforce anything, so the server has to authorize closes. There's also no read-only state for users who aren't allowed to act.
- **Count accuracy:** The header count is `items.length`. If the API paginates, "(20)" understates the real queue.
- **Dark mode:** Text color is set without a background (`css:3`). If the app has a dark theme, `#1b1f24` text will sit on a dark surface.

### What already works

- Headings and semantics: one `h1`, then one `h2` per card, each `article` labelled by its heading, and a `dl` for the metadata.
- The loading state uses `role="status"`, the error uses `role="alert"`, and there's a retry button.
- The empty state is specific: "New requests from technicians will appear here."
- Touch targets are 44px, focus is clearly visible (3px `#0b57d0`), and action buttons wrap.
- The `auto-fill`/`minmax(min(100%, 300px), 1fr)` grid collapses cleanly to one column on phones without horizontal scroll.
- Contrast is good: `#57606a` on white is about 6:1.
- The card design is restrained and specific to the task. It doesn't look like a generic template.

### Judgment calls

- **Cards versus a table:** a dispatcher triaging 50+ work orders might scan a sortable table faster. Cards suit technicians on phones.
- **P1/P2/P3 labels:** these are fine if your teams already use them. Otherwise "Urgent / High / Normal" is clearer.

I can apply the must-fix and should-fix changes if you'd like. The focus handling and the pending states need a small change to the `onAssign`/`onClose` signatures, so I'd confirm that with you first.
