**Verdict: Fail.** There are six must-fix issues. The worst is that the checkout request sends the price total, admin flag and user ID, all built from values the browser controls. Whether that can actually be exploited depends on the server, which isn't in this repo.

## Must-fix

**1. The order request sends identity and admin status taken from the browser**
- **Evidence:** `src/checkout.ts:12` sends `isAdmin: user.isAdmin, userId: user.id`. Those values come from `sessionStorage` (`src/user.ts:1`), which anyone can edit in DevTools.
- **Impact:** if the server trusts these fields, a user can place orders as someone else or claim admin rights (OWASP A01, broken access control). The request already uses cookies (`credentials: "include"`), so the server should work out who the user is from the session.
- **Fix:** remove `isAdmin` and `userId` from the payload. Confirm the server ignores them if they're sent anyway.
- **Verify:** send a hand-edited request with `isAdmin: true` and another user's ID. The server must reject it or ignore the fields.

**2. The price total, and the unit prices it's built from, come from the browser**
- **Evidence:** `src/checkout.ts:7` works out `total` from `unitPrice` in the cart and sends both (line 12).
- **Impact:** if the server accepts either value, anyone can edit the request and pay less. This needs checking on the server side.
- **Fix:** send only `sku`, `qty` and `coupon`. The server should look up prices, apply the coupon and calculate the total. Show the server's total back to the user before they confirm.
- **Verify:** send `unitPrice: 0.01` or `total: 1`. The order must be priced from the catalog.

**3. Server errors are treated as a successful order**
- **Evidence:** `src/checkout.ts:14` returns `res.json()` without checking `res.ok`.
- **Impact:** errors like 400, 409 or 500 look like success to whatever calls this function. If an error page comes back as HTML (a 502 from a proxy, for example), `res.json()` throws a parsing error with no useful message. Users can get the wrong result after paying, or after failing to pay.
- **Fix:** check `res.ok`. If it's false, parse the error body and throw a typed error that the UI can turn into a clear message.
- **Verify:** fake a 400, a 500, an HTML 502 and a network failure, and confirm each shows a distinct, correct message.

**4. Orders can be placed twice**
- **Evidence:** `placeOrder` has no idempotency key and nothing stops a second call while the first is still in progress.
- **Impact:** a double-click, a retry after a timeout or a flaky network can create duplicate orders and duplicate charges.
- **Fix:** create an idempotency key once per checkout attempt and send it as a header, which the server must honour. Block repeat calls while a request is in progress.
- **Verify:** fire two calls at once with the same key. Only one order should exist.

**5. Refund happens on a single click with no confirmation or feedback**
- **Evidence:** `src/OrderView.tsx:9`, `<button onClick={onRefund}>Refund</button>`. `onRefund` returns `void`, so the view can't track progress, success or failure.
- **Impact:** a refund can't be undone, yet one accidental click triggers it. Nothing shows the amount, and there's no pending state, so double-clicks can send duplicate refunds. The user isn't told whether it worked.
- **Fix:** add a confirmation step that names the order and the formatted amount. Change `onRefund` to return a `Promise`, disable the button while it runs, and report the result in an `aria-live` region. This also needs an idempotency key on the server, as in item 4.
- **Verify:** check with keyboard only and a screen reader. The confirmation should get focus, the pending state should block repeat clicks, and the result should be announced.

**6. Missing or corrupted session data is used anyway**
- **Evidence:** `src/user.ts:1` returns `{}` when nothing is stored, and throws on a malformed value. `placeOrder` then sends `userId: undefined`.
- **Impact:** a signed-out or expired user can send an order with no identity attached instead of being sent to log in, and corrupted storage crashes checkout.
- **Fix:** once item 1 is done, checkout shouldn't need `getUser()` at all. Anywhere else that still uses it should handle a missing user explicitly, for example by redirecting to login, and wrap the `JSON.parse` in `try/catch`.

## Should-fix

- **Permissions only hide buttons** (`src/OrderView.tsx:8-9`). Hiding "Edit" and "Refund" when `canEdit`/`canRefund` is false is fine for the interface, but the server must separately check that the user is allowed to edit or refund. That can't be confirmed from this repo.
- **Totals aren't formatted as money** (`src/checkout.ts:7`, `src/OrderView.tsx:7`). The math uses floating-point numbers, so `0.1 + 0.2` gives `0.30000000000000004`, and the total prints as a bare number like `Total: 1234.5`. Store amounts in cents (integers) and display them with `Intl.NumberFormat` using the order's currency.
- **The order status isn't shown.** `status` is in the `Order` type but never rendered, so users can't tell if an order is already refunded or cancelled. The Refund button also relies entirely on `canRefund` to hide itself for those orders.
- **CSRF protection needs confirming on the server.** The POST uses cookies. The JSON content type forces a browser preflight check, which helps, but the server should still reject other content types or require a CSRF token.
- **Quantities aren't checked.** Nothing blocks `qty <= 0` or fractional quantities. A client-side check would help users, but the server must validate these regardless.

## Minor

- `ownerId` in the `Order` type is never used. Either remove it or confirm it isn't being used somewhere else to decide access.
