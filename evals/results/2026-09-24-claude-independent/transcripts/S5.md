## Must-fix

**1. The screen can upload a different file than the one on screen**
Evidence: `src/UploadReferral.tsx:10`. When a file is rejected, the code shows an error but doesn't clear the file that was already accepted.
Impact: A user picks `referral.pdf`, then picks `scan.jpg`. The input now shows `scan.jpg` and the error message, but Upload is still enabled. Clicking it sends `referral.pdf`. The same happens in browsers that keep the old file when the user cancels the picker (line 9 returns early). A wrong letter could end up on a referral.
Fix: Call `setFile(null)` before every early return, and clear `e.target.value` when a file is rejected.
Verify: Pick a valid file, then an invalid one. Upload must be disabled.

**2. "Uploaded." shows even when the upload fails**
Evidence: `:18–19`. The code never checks `response.ok`, and a network error isn't caught.
Impact: If the server returns 401, 413 or 500, the user still sees "Uploaded." If the network fails, the promise rejects unhandled and the message stays "safe to upload". Either way the user thinks the letter was sent when it wasn't.
Fix: Wrap the request in `try/catch` and check `res.ok`. Show a specific error with a way to retry, and only report success once the server confirms it.
Verify: Make the endpoint return 500, then go offline. Both should show an error.

**3. The success message makes a security claim the code can't back up**
Evidence: `:12`: "✓ Your file has been securely validated and is safe to upload."
Impact: `File.type` is guessed by the browser from the file extension. This check stops honest mistakes, but not a renamed or malicious file, and it tells you nothing about whether the content is safe. For a medical document, telling users it is "securely validated" is simply false.
Fix: Use a neutral message such as "referral.pdf selected (1.2 MB)". Any real validation or malware scan has to happen on the server, and the UI should only report what the server returns.

**4. Upload can be sent more than once**
Evidence: `:15–20` and `:27`. There's no pending state, and the file isn't cleared after success.
Impact: A double-click, or clicking again because nothing seems to happen, sends another POST each time. Each one could create a duplicate referral document.
Fix: Add an `uploading` state that disables the button and shows "Uploading…". Reset the file after a confirmed success.

**5. Screen readers don't announce the status message**
Evidence: `:26`. The status is a plain `<p>` with no live region, and the error isn't linked to the input. This fails WCAG 2.2 success criterion 4.1.3 (status messages).
Impact: This message is the only feedback the screen gives. Screen-reader users won't hear whether the letter was accepted, rejected or sent.
Fix: Make it `role="status"` for progress and success, and `role="alert"` for errors. Link the error to the input with `aria-describedby` and set `aria-invalid`. Mark success and error with text, not only styling; right now the two look identical.

## Should-fix
- **No size limit or guidance.** Users aren't told what's accepted, and a 413 "file too large" response isn't handled. Show a hint near the label (e.g. "PDF, up to 10 MB"), check the size before upload, and map server errors to clear messages.
- **No progress or cancel option.** `fetch` can't report upload progress, so a large scan on a slow connection looks frozen. Consider using XHR for progress plus an `AbortController` so users can cancel.
- **The upload isn't tied to anything visible.** The POST carries no referral or patient ID, and the screen doesn't say what the letter is attached to. The user can't confirm they're uploading to the right case.
- **The file-type check may reject real PDFs.** Line 10 requires both the MIME type and the `.pdf` extension. Some platforms report an empty `type`, which would block valid files. Treat the check as a convenience and let the server have the final say.

## Needs backend or runtime verification
- **CSRF protection:** a cookie-authenticated multipart POST (`credentials: "include"`) is a "simple" request, so another site's form could submit it. Confirm there is a CSRF token or SameSite cookie policy.
- **Server-side checks:** confirm the server does real content-type validation, malware scanning, size limits, filename sanitisation, and authorization so a user can only attach letters to referrals they're allowed to access.
- **Privacy:** confirm who can access the uploaded health document and how long it's kept. Consider telling the user.
