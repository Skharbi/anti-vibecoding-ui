## Security review: Team Notes frontend

**What I looked at:** all 5 project files: `src/App.tsx`, `src/main.tsx`, `index.html`, `vite.config.ts` and `package.json`. The app makes one request, a same-origin `GET /api/notes` that sends cookies, and renders the result as a read-only list. I only read the code. I didn't run the app or look at the backend or deployment.

**Verdict:** Pass with issues. I found no high-impact security flaw in the frontend. The issues below are about hardening, and about checks that have to happen on the backend or deployment.

### Findings

**[Should-fix] No lockfile, and dependency versions are loose**
Evidence: `package.json:3-4` uses `^` ranges, and there is no `package-lock.json`, `pnpm-lock.yaml` or `yarn.lock` in the repo. The repo has no commits yet either.
Impact: every install can pull different versions of the dependencies and their dependencies, and there's no record of what was actually built. The floor `vite ^5.4.0` includes 5.4.x releases with known dev-server vulnerabilities: arbitrary file reads via `server.fs.deny` bypasses (e.g. CVE-2025-30208/31125/31486/32395), and CVE-2025-24010, which let other sites send requests to the dev server. Because nothing is pinned, a fresh install probably gets a fixed version, but nothing guarantees it.
Fix: commit a lockfile, raise the floor to a patched Vite (≥ 5.4.19, or move to a current major), and install with `npm ci` in CI. Don't run `vite --host` on untrusted networks.
Verify: `npm ls vite` shows a patched version, and `npm audit` plus your supply-chain tooling are clean.

**[Should-fix] The response is used without checking its shape**
Evidence: `App.tsx:11` passes the parsed JSON straight to `setNotes`, and `App.tsx:18` calls `.map` on it.
Impact: if the API returns anything other than an array, `notes.map` throws and the whole page goes blank with no error message. That could be an error object, a login page's JSON, or a proxy response. This is a reliability problem rather than an injection problem.
Fix: check the data before storing it, e.g. `Array.isArray(d) && d.every(n => typeof n.id === "string" && …)`, and otherwise show the existing error state. Adding an error boundary would also help.
Verify: mock `/api/notes` to return `{}`, and the page should show "Couldn't load notes."

**[Should-fix] An expired session looks like a generic failure**
Evidence: `App.tsx:10-12` turns every non-OK status into "Couldn't load notes."
Impact: a 401 or 403 doesn't leak any data, so it fails safely. But the user gets no route to log back in, and a "not allowed" response looks the same as an outage.
Fix: handle 401 by sending the user to login, and 403 with a clear "no access" message.

### Needs checking on the backend or deployment
The frontend can't prove any of these:
- **Access control on `/api/notes`:** the server has to limit results to the signed-in user's team. Nothing on the client limits which notes come back.
- **Session cookie:** `HttpOnly`, `Secure`, `SameSite=Lax/Strict`, and the session is actually ended on logout. There are no requests that change data today, so CSRF doesn't apply yet. Add a CSRF defence before adding any create, edit or delete.
- **Security headers:** there's no CSP in `index.html`. Set one at the server or CDN (`default-src 'self'; frame-ancestors 'none'`), plus `X-Content-Type-Options: nosniff`, a `Referrer-Policy` and HSTS.
- **Caching:** notes are private, so `/api/notes` should send `Cache-Control: no-store` (or `private`). That stops shared proxies or the browser from keeping them.
- **CORS:** the API shouldn't reflect arbitrary origins while `Access-Control-Allow-Credentials: true` is set.

### What's already fine
- **No XSS risk found:** `title` and `body` are rendered as React text (`App.tsx:18`), which escapes them. There's no `dangerouslySetInnerHTML`, `innerHTML`, `eval`, Markdown rendering, or links built from user data.
- **No secrets or client storage:** there are no tokens, API keys or `import.meta.env` values in the code, and nothing is written to `localStorage` or `sessionStorage`.
- **No third-party scripts, analytics or embeds.** Only the React runtime is used.
- **Production source maps are off** (Vite's default, and `vite.config.ts` doesn't change it).
- **Errors don't leak details:** the user sees a generic message, not status codes or stack traces.
- `credentials: "include"` on a same-origin request is redundant but harmless.
