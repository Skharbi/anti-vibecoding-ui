## final
**Verdict: Fail.** A patient's health records stay on the device after logout, and the next person to log in on that browser can be shown them. I also found several failure paths where the app acts as if a request worked when it didn't.

I only had three files to review (`src/session.ts`, `src/records.ts`, `src/types.ts`). There's no UI, tests, backend or deployment config here, so I read the code but didn't run anything. Anything that depends on the server is listed separately at the end.

## Must-fix

**1. Logout doesn't clear anything, so the next user can see the previous patient's records**
- **Where:** `logout()` only redirects (`src/session.ts:12-14`). `loadRecords()` returns the cached copy before any network request or auth check (`src/records.ts:4-5`).
- **What happens:** Patient A logs out on a shared or clinic computer. The token, `user` and `records` all stay in `localStorage`. Patient B logs in and gets A's diagnoses, medications and lab results, because the cache is checked first and isn't tied to a user. Even with no one logged in, a direct call returns A's records.
- **Fix:** Logout should (a) call a server endpoint to revoke the session, (b) remove `accessToken`, `user` and `records` (or clear everything the app owns), then (c) use `location.replace("/login")` so the back button doesn't return to the records page.
- **How to check:** Log in as A, load records, log out, log in as B, and confirm the only request is `/api/records` with B's token and B's data.

**2. Health records are stored in `localStorage` with no expiry**
- **Where:** `src/records.ts:8` caches the whole record (MRN, name, date of birth, diagnoses, medications, labs, per `src/types.ts:1`).
- **What happens:** The data survives browser restarts, never expires, and any script running on the page can read it. For healthcare data, this counts as unnecessary exposure on the device.
- **Fix:** Don't persist it. Keep records in memory for the current page (or use a per-session query cache), and have the server send `Cache-Control: no-store`.

**3. Cached records skip auth entirely**
- **Where:** `src/records.ts:4-5`
- **What happens:** Once the cache is filled, an expired or revoked token doesn't matter because `/api/records` is never called again. Records also never refresh, so a patient can be shown outdated medications or lab results.
- **Fix:** Removing the persistent cache (see #2) fixes this. If you keep any cache, tie it to the user and the session, and still let a 401 from the server end the session.

**4. A failed login is treated as a success**
- **Where:** `src/session.ts:2-5` never checks `res.ok`.
- **What happens:** With a wrong password, `accessToken` is `undefined`, and the literal string `"undefined"` is saved. `login()` returns normally, so the caller moves to the logged-in view. After that, `authHeader()` sends `Bearer undefined`, or `Bearer null` if nothing was ever saved (`src/session.ts:9`). The user gets no correct error message.
- **Fix:** When `!res.ok`, throw a typed error (bad credentials, locked, network) and show a generic message that doesn't reveal whether the account exists. Only save a token if one is actually present. `authHeader()` should throw or send the user to login when there's no token, not send a fake one.

**5. Error responses get saved as records**
- **Where:** `src/records.ts:6-8` saves whatever the server returns.
- **What happens:** A 401, 403 or 500 response body is stored as `records` and returned from then on. The app keeps showing broken data until someone clears storage manually, and an expired session never sends the user back to login.
- **Fix:** Check `res.ok`. On a 401, clear the session and redirect to login. On other errors, show an error state with a retry option, and never cache the response.

**6. The access token is stored where any page script can read it**
- **Where:** `src/session.ts:4`
- **What happens:** One XSS bug anywhere in the portal would let an attacker steal a token that works until it expires, and there's no expiry handling in this code.
- **Fix:** The best option is an `HttpOnly; Secure; SameSite` session cookie. That then needs CSRF protection on requests that change data. A second option is a short-lived token kept in memory, renewed through an HttpOnly refresh cookie.
- **Confirmed vs. unknown:** Storing it this way is confirmed from the code. How serious it is depends on the token's lifetime, which the server controls.

## Should-fix

- **No session timeout.** Nothing handles inactivity or expiry: no idle logout, no "your session is about to expire" warning, and no app-wide handling of 401 responses. Patient portals usually need automatic logoff, so check what your compliance requirements say.
- **`user` is also saved in `localStorage`** (`src/session.ts:5`). I can't see what fields it holds. Keep only what the UI actually needs, and in memory.
- **`loadRecords()` has no return type.** It returns `any`, and `PatientRecord` is never used. Declare `Promise<PatientRecord[]>` and validate the response shape, so an error body can't pass for records.
- **A corrupted cache crashes the load.** `JSON.parse(cached)` (`src/records.ts:5`) throws if the stored value is corrupted, and nothing catches it. This goes away if you remove the persistent cache.

## What already works

- Credentials are sent in a POST body, not in the URL.
- Requests use relative same-origin URLs, so there's no hard-coded host or leaked environment setting.
- No secrets or API keys are in the source.
- There's no code that renders raw HTML.

## Needs checking on the server or at runtime

- `/api/records` must decide whose records to return from the token, never from anything the client sends. Otherwise one patient could fetch another's records.
- Token lifetime and revocation, and whether a logout or revocation endpoint exists.
- `Cache-Control: no-store` on record responses, plus the CSP and frame-protection headers.
- Login rate limiting and lockout, whether login errors reveal that an account exists, and MFA.
