## Must-fix

**1. One click issues a refund, with no confirmation**
Evidence: `src/OrdersPage.tsx:28`. The button calls `submitRefund` directly.
Impact: A misclick on a row gives someone's money back, and it can't be undone. Every row looks the same, so hitting the wrong one is easy.
Fix: Ask for confirmation first, and show the order ID, customer and amount. For example: "Refund $84.20 to Jane Doe for order #1042?"
Verify: Clicking Refund and then Cancel sends no POST request.

**2. Double refunds are possible, and refunded orders still show a Refund button**
Evidence: `src/OrdersPage.tsx:14-16, 28`. Nothing marks a refund as in progress, the button is never disabled, and it ignores `o.status`.
Impact: A double-click, or a retry while the network is slow, sends several refund requests. After a refund, the row still offers Refund.
Fix: Track the ID of the refund in progress. Disable that row's button and show "Refunding…" while it runs. Hide or disable the button once the status is `refunded`. Ask the backend to accept an idempotency key as well; the frontend can't fully stop duplicate refunds on its own.
Verify: A fast double-click sends one POST. A refunded row has no working Refund button.

**3. Failures are silent**
Evidence: `src/OrdersPage.tsx:11` (the load has no `.catch`) and `:15` (`await` with no try/catch). Both become unhandled promise rejections.
Impact:
- If loading fails, the page shows an empty table with headers. That looks exactly like "you have no orders".
- If a refund fails, the operator sees nothing and can't tell whether the money went out.
Fix: Show an error message with a Retry button when loading fails. Show a per-row error when a refund fails. Announce the result through a `role="status"` region, or `role="alert"` for errors.
Verify: Make each endpoint return a 500 and check the message and the retry.

**4. A refund can succeed on the server while the page reports failure, which invites a second refund**
Evidence: `src/api.ts:3`. `post` always calls `r.json()`.
Impact: Refund endpoints often reply 204 No Content. In that case `r.json()` throws after the refund has already gone through. The status stays unchanged, and once finding 3 adds error messages the page would report a failure. The operator clicks again and refunds twice.
Fix: Parse JSON only when the response actually has a body, i.e. the status isn't 204 and `content-type` includes `application/json`. Check what the refund endpoint really returns.
Verify: Mock a 204 response. The row should update with no error.

**5. One note field is shared by every refund**
Evidence: `src/OrdersPage.tsx:8, 15, 33-34`.
Impact:
- The note sits below the table and isn't tied to any order. Whatever text is in it gets attached to whichever row's Refund is clicked.
- It's never cleared, so the next refund silently reuses the last note.
- Keyboard users tab through every Refund button before they reach the note.
This puts wrong data on financial records.
Fix: Move the note into the confirmation dialog from finding 1, one per refund, and reset it after each submit. Keep the note's `<label>` in the dialog; the current label is correctly linked.
Verify: Refund order A with note X, then refund order B. B's note starts empty.

**6. Every row's button is just called "Refund"**
Evidence: `src/OrdersPage.tsx:28`, and the empty `<th>` at `:23`.
Impact: A screen reader's list of buttons says "Refund, Refund, Refund…" with no way to tell which order each one refunds.
Fix: Name each button after its order, e.g. `aria-label={`Refund order ${o.id}`}`. Put visually hidden "Actions" text in the empty `<th>`.
Verify: The accessibility tree shows a distinct name for each button.

## Should-fix

- **No loading or empty state** (`:7, 25`). Before data arrives and when there are no orders, the page shows the same bare header row. Keep separate `loading`, `error`, `empty` and `loaded` states.
- **Money shows as a raw number** (`:27`). `{o.total}` renders `84.2` with no currency symbol and the wrong precision. Use `Intl.NumberFormat` with the currency from the API and right-align the column. Also confirm whether `total` is in cents or dollars; the type doesn't say.
- **The page decides the status itself** (`:16`). It hardcodes `"refunded"`, but the server may answer `refund_pending` or partially refund. Use the status in the POST response. Narrow `status: string` to a union so a typo can't produce a status the backend never sends.
- **No accessible way to confirm the status change.** The status cell changes silently. The live region from finding 3 covers this.
- **The whole order list loads at once, with no pagination** (`:11`). At real volumes this is slow and hard to scan. Confirm the API supports paging, then add pagination, filtering by status or customer, and sorting.
- **The URL path isn't encoded** (`:15`). Use `encodeURIComponent(id)`. The risk is low because the IDs come from the server, but it costs nothing.
- **Narrow screens.** A five-column table with no overflow wrapper will spill sideways on phones. There are no styles to check, so this needs a look in a browser.

## Needs backend verification

- **Who is allowed to refund.** The button is shown to everyone, and hiding it wouldn't be real protection anyway. The refund endpoint must check the user's permission itself.
- **CSRF (cross-site request forgery) protection.** `fetch` sends cookies to the same site by default. The JSON content type offers some protection for cross-origin requests, but confirm the backend enforces CSRF or `SameSite` cookie defences.
- **Audit trail.** Check that the refund note and the person who issued the refund are recorded on the server.

## Judgment calls

- **Confirm first or undo after:** a confirmation dialog, or an "undo within N seconds" pattern. For money, I'd go with confirmation.
- **Where refunds live:** inline row actions, or a separate order-detail page. The detail page scales better once partial refunds and reasons are needed.

The biggest structural fix is findings 1 + 2 + 5 together: move refunds into a confirmation dialog for one order at a time, with its own note and an in-progress state. I can implement that along with the `api.ts` fix if you want.
