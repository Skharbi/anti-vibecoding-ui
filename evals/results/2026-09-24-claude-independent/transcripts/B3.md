## Why a clean lint run isn't enough

`jsx-a11y` looks at each JSX element on its own: whether a `role` is valid, whether an input has a label, and so on. It can't tell where keyboard focus goes, whether the page behind the dialog is blocked, or what the Escape key does. Those make up most of what WCAG expects from a dialog, and this one has none of them.

## Must-fix

**1. Focus isn't moved into the dialog or returned when it closes**
- **Evidence:** `ShareDialog.tsx:8-9` shows the dialog but never moves focus into it. Both buttons (`:13`, `:14`) unmount it, and nothing sends focus back to the trigger at `:7`.
- **Impact:** When the dialog opens, keyboard and screen reader users are left on the "Share report" button behind it. After Send or Cancel, the focused button disappears and focus falls back to `<body>`, so they lose their place on the page. This breaks WCAG 2.4.3 (Focus Order).

**2. It isn't actually modal**
- **Evidence:** `:9` has no `aria-modal`, nothing stops Tab from leaving the dialog, and nothing makes the background inert. `dialog.css` has no backdrop and no `z-index`.
- **Impact:** Tab moves straight out into the page behind. Screen reader users can read and use background content without knowing the dialog is open. Sighted users see a floating box over a page that still works.

**3. Escape doesn't close it**
- **Evidence:** There's no key handler anywhere in the component.
- **Impact:** Keyboard users expect Escape to close a dialog (it's part of the standard ARIA dialog pattern). Right now the only way out is to find Cancel.

## Should-fix

- **Send gives no feedback (`:13`).** It closes the dialog without checking the email, without a sending state, and without any success or error message. A screen reader user gets no confirmation that anything happened. Add validation, an inline error tied to the input with `aria-describedby`, and a success message announced through a live region.
- **The input (`:12`)** should have `autoComplete="email"`, and `required` if an address is required.
- **Small screens (`dialog.css:1`).** The CSS sets no `max-width`, `max-height` or `overflow`. With `top: 20%` and an on-screen keyboard open, the buttons can end up off-screen with no way to scroll to them. This needs checking on a narrow phone-sized viewport.

## What already passes

- The dialog has `role="dialog"` and its name comes from a visible heading through `aria-labelledby` (`:9-10`).
- The email field has a properly linked `<label>` (`:11-12`).
- The controls are real `<button type="button">` elements with visible text.

## Recommended fix

Switch to the native `<dialog>` element and open it with `showModal()`. That gives you focus moving into the dialog, Escape to close, an inert background and a `::backdrop` with very little code. Then send focus back to the trigger on `close`: current browsers do this themselves, but it's cheap to guarantee. Before signing off, test it by hand with only the keyboard, then with VoiceOver or NVDA, and on a narrow mobile viewport.
