## Must-fix

**1. The mobile check causes a hydration mismatch and shows the wrong layout without JS**
Evidence: `app/status/page.tsx:8`. `typeof window !== "undefined" && window.innerWidth < 768`
Impact: On the server, `window` doesn't exist, so the server always renders `DesktopBoard`. On a phone, the browser's first render picks `MobileList`, so React reports a hydration mismatch and throws away the server HTML. The two things the README promises both break:
- If JS fails, mobile users get the desktop board.
- If JS works, mobile users see a layout flash and lose the speed benefit of server rendering.

The value is also only read once, so rotating the phone or resizing the window doesn't switch layouts.
Fix: Don't choose layouts in JS. Either render one responsive component styled with CSS media or container queries, or render both and hide one with CSS (`hidden md:block` / `md:hidden`).
Verify: Load the page at 375px with JS disabled and check that the mobile layout appears. With JS on, check the console for hydration warnings.

**2. "Last checked" shows when the page rendered, not when status was checked**
Evidence: `app/status/page.tsx:12`. `new Date().toLocaleTimeString()`
Impact: On a status page this timestamp is the main thing that tells users whether to trust the data. It currently shows the render time, so stale or failed data still looks fresh. It also causes a second hydration mismatch, because the server and browser produce different times, and possibly different time zones and locales. With JS off, users see the server's time zone (usually UTC) with no label.
Fix: Use the check time that comes with the incident data. Render it as `<time dateTime={iso}>` with an explicit time zone, e.g. "14:02 UTC". If you want a relative time like "2 min ago", compute it in a small client component after hydration.
Verify: Make the data source return an old timestamp and check that the page shows that time, not the current time.

**3. Incidents probably don't reach the server HTML (depends on `useIncidents`)**
Evidence: `app/status/page.tsx:1,7`. It's a client hook in a client page. If it fetches inside `useEffect` or with SWR, which is typical, the server HTML contains no incidents.
Impact: With JS off, or while JS is still loading, the page shows no incidents. Worse, an empty list can read as "all systems operational" during an outage.
Fix: Make `page.tsx` a server component that fetches incidents on the server (e.g. `fetch(url, { next: { revalidate: 30 } })`). If you want live updates, put polling in a small client component that starts from the server-fetched data.
Verify: `curl` the page and check that incident text appears in the HTML.

## Should-fix

**4. There are no loading or error states.** `useIncidents()` returns only the incidents (`:7`), so the page can't tell "loading", "fetch failed" and "no incidents" apart. A status page must never show a failed fetch as "all clear". Show an explicit "Couldn't load status, last known data from X" message.

**5. The page can't export `metadata`.** `"use client"` pages can't export `metadata` or `generateMetadata`, and this is a public page people will link to and search for during outages. Moving it to a server component fixes this.

**6. There's no summary line.** The `<h1>` is followed directly by a timestamp. Most people come to a status page to ask "is it down right now?" Add a single summary sentence ("All systems operational" / "Degraded: API") that isn't conveyed by color alone. If the page polls, put that sentence in a `role="status"` region so screen readers announce changes.
