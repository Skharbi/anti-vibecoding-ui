## Review: `src/PatientSearch.tsx`

**Result: Fail.** I only read the code. The repo contains just this one 27-line file, with no package.json, styles, tests or backend, so I couldn't run it. Because it picks a patient in what looks like a clinical app, a wrong or stale result is a patient-safety problem and not just a UI glitch. I've ranked the findings with that in mind.

### Must-fix

**1. Older responses can overwrite newer ones, so the wrong patients can show up**
Evidence: `PatientSearch.tsx:9-14`. Every keystroke sends a request, and whichever response arrives last wins.
Impact: Say you type `smith`. If the slower `smi` response arrives after the `smith` one, the list shows results for `smi` while the box says `smith`. Clearing the box has the same problem: `setHits([])` runs, then a request still in flight brings the old results back under an empty box. Clinicians click from this list.
Fix: Cancel the previous request with an `AbortController`, or tag each request with an ID and ignore any response that isn't the latest. Also cancel on unmount.
Verify: Add a random delay to the API, type quickly, then clear the box. The list must always match the text in the box.

**2. Errors aren't handled, and a failed request can crash the component**
Evidence: `PatientSearch.tsx:12-13`. Nothing checks `r.ok` and there's no `try/catch`.
Impact: If the session expires (401), the server errors (500) or the network drops, `r.json()` either throws an unhandled rejection or returns an error object. `setHits({error: ...})` then makes `hits.map` throw and takes down the React tree. At best, the user sees nothing with no explanation.
Fix: Check `r.ok`, check that the response is an array, and show a short error such as "Couldn't search patients. Retry". Handle 401 separately so it leads to sign-in instead of looking like "no results".
Verify: Mock responses for 401, 500, a non-JSON body and a network failure. Each one should show a message, and the component should keep working.

**3. Screen-reader users aren't told when results arrive, and there are no loading or empty states**
Evidence: `PatientSearch.tsx:20-24`. The list appears silently. Nothing shows while a search runs, and a search with no matches looks the same as one still loading.
Impact: Screen-reader users type and hear nothing. Sighted users can't tell "no match" from "still searching", which matters when the patient may not be registered yet.
Fix: Add a live status line (`<p role="status">`) that says "Searching…", "3 patients found" or "No patients match 'smyth'". A full combobox widget isn't needed: a text input followed by a list of buttons is a valid, simpler pattern as long as the status is announced.
Verify: In VoiceOver or NVDA, type a search and confirm the result count is read out.

### Should-fix

**4. Patient names go into the URL query string**
Evidence: `PatientSearch.tsx:12`, `/api/patients?q=<name>`.
Impact: Query strings often end up in server, proxy, CDN and APM logs. Names and MRNs are PHI (protected health information). I can't see from here whether those logs are redacted, so **this needs checking on the backend**.
Fix: Either send the query as a POST body, or confirm that every hop on that route redacts `q` from its logs.

**5. A request fires on every keystroke, with no debounce or minimum length**
Evidence: `PatientSearch.tsx:9-12`.
Impact: Typing one letter searches the whole patient index. That puts load on a sensitive endpoint and makes the race in #1 more likely.
Fix: Wait about 200–300 ms after typing stops, and require 2–3 characters, unless the input looks like an MRN.

**6. The label doesn't say what can be searched**
Evidence: `PatientSearch.tsx:18`, "Find patient".
Fix: Add hint text linked with `aria-describedby`, such as "Name or MRN", and use it for whichever fields the API actually matches. Using `type="search"` would also give a native clear button.

**7. The result buttons have no `type`**
Evidence: `PatientSearch.tsx:22`.
Impact: If this component sits inside a `<form>`, such as an order or encounter form, clicking a patient also submits that form.
Fix: `type="button"`.

**8. Nothing changes after a patient is picked**
Evidence: `PatientSearch.tsx:22`. `onPick` fires, but the list and query stay as they are.
Impact: Nothing confirms which patient was picked, and it's easy to click a second one by accident. Whether to collapse the list and show the selection may be the parent's job, so check who owns that.

### Judgment call

**9. Name + MRN may not be enough to tell patients apart**
Picking the wrong patient among similar names is a known safety risk. Many clinical tools show date of birth and sex as well. Weigh that against showing only the data the task needs. I'd confirm this with whoever owns clinical safety.
