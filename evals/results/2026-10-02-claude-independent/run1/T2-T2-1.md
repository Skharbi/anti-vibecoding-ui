I rewrote `sql/monthly_revenue.sql` and added `sql/indexes.sql` with two indexes. I haven't run either against a database, so I haven't confirmed the speedup. Run `EXPLAIN (ANALYZE, BUFFERS)` before and after on real data.

**What was slow**
1. **`date_trunc('month', o.created_at) = ...`** applies a function to the column, so no index on `created_at` can be used. I replaced it with a range, `created_at >= start of month AND < start of next month`.
2. **`lower(email) LIKE '%@acme.com'`** has a leading wildcard, so it scans the whole table. I now match `reverse(lower(email)) LIKE 'moc.emca@%'`, which is a prefix match and can use an index on that reversed expression.
3. **The correlated subquery** ran once per customer, and `orders` had no index on `customer_id`. I replaced it with a `LEFT JOIN` and `GROUP BY`. Customers with no orders this month still appear with a NULL total, as before.

**Indexes in `sql/indexes.sql`**
- `customers (reverse(lower(email)) text_pattern_ops)` supports the email filter.
- `orders (customer_id, created_at) INCLUDE (total)` serves the join and the month range, and can be read without touching the table.

Both use `CREATE INDEX CONCURRENTLY`, so they won't block writes, but they can't run inside a transaction block.

The month boundary still follows the session time zone, as the original did. If the `@acme.com` filter only ever targets one domain and is used often, a plain `customers (lower(email))` index won't help it. A stored `email_domain` column would be simpler if you control the schema.
