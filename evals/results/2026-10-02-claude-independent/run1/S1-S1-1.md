# Security review: admin projects UI

I reviewed `src/ProjectRow.tsx`, `src/api.ts` and `src/auth.ts`. This is a frontend-only review. I flag anything that needs backend or runtime verification, and I can't say whether the app is secure overall.

## Findings

### 1. Admin-only delete is enforced only in the UI (High, needs backend verification)
**Evidence:** `ProjectRow.tsx:10-12` renders the button only when `user.role === "admin"`. The request is `DELETE /api/projects/${project.id}` (`ProjectRow.tsx:11`).
- **Trust boundary:** the browser to the API. The role check is a UX control. Anyone with a valid session can send the same DELETE with curl or devtools.
- **Impact:** if the server doesn't check role and ownership, any authenticated user can delete any project by ID (broken access control / IDOR). `ownerId` is passed to the component but never used.
- **Status:** not confirmed. The server code isn't in this repo.
- **Fix:** enforce on the server that the caller is an admin, or is authorised for that specific project. Return 403 or 404 otherwise.
- **Verify:** as a non-admin user, replay the DELETE against a project you don't own. It should fail and the project should remain.

### 2. No CSRF protection for the cookie-authenticated DELETE (Medium, needs backend verification)
**Evidence:** `api.ts:3` uses `credentials: "include"` and sends no CSRF token or custom header.
- **Impact:** if the session cookie is `SameSite=None`, or the API is on a sibling origin with lax CORS, a malicious page could trigger a delete from an admin's browser.
- **Fix:** use `SameSite=Lax` or `Strict` cookies, add a CSRF token or required custom header checked by the server, and allowlist CORS origins. Don't rely on CORS alone.
- **Verify:** inspect the `Set-Cookie` attributes. Send a cross-origin DELETE without the token and confirm it is rejected.

### 3. Destructive action with no confirmation, error handling or result check (Medium)
**Evidence:** `ProjectRow.tsx:11` fires the request on a single click. The `fetch` promise is ignored, and `fetch` doesn't reject on 401, 403 or 500.
- **Impact:** a misclick permanently deletes a project. On failure the UI shows nothing, so a 403 or 500 looks like success. Double-clicks send duplicate requests. A session that expired mid-use also fails silently (fail-open UX). The component never refreshes or removes the row either way.
- **Fix:** add a confirmation dialog that names the project. Disable the button while the request is pending. Check `res.ok` and show an error on failure. Update the list only after the server confirms. Consider re-authentication or soft delete for a high-risk action.

### 4. `useCurrentUser()` is unguarded and may be null (Low–Medium)
**Evidence:** `auth.ts:3` returns the raw context value, and `ProjectRow.tsx:10` reads `user.role` directly.
- **Impact:** if the context is null while loading or after logout, the component throws and can crash the table. Any fix should deny by default, so a missing user never gets admin controls.
- **Fix:** use `user?.role === "admin"`, or have the hook throw a clear error and handle the loading state.

### 5. API client weaknesses (Low)
**Evidence:** `api.ts:1-4`
- `base` comes from `VITE_API_URL` and isn't validated. If it is undefined, requests silently go to `"undefined/api/..."`. Check that it is set, and that production points at an HTTPS origin.
- `get` calls `.json()` without checking `r.ok`, so error responses are parsed as data.
- `path` is concatenated into the URL without encoding. `project.id` is interpolated raw at `ProjectRow.tsx:11`, so use `encodeURIComponent` if IDs aren't guaranteed to be safe. Server-generated UUIDs are fine.
- No timeout or abort support.

## Checked and not found
- No `dangerouslySetInnerHTML`, `innerHTML` or `eval`. `project.name` is rendered as an escaped React text node, so there is no XSS here.
- No secrets, tokens or browser-storage use in these files. `VITE_API_URL` is a public endpoint, not a secret.
