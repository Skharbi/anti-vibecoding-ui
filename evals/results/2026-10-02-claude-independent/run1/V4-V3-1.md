## Findings

**[Should-fix] Non-OK responses are not surfaced as errors**
- **Evidence (Confirmed):** `client.js:1` returns the raw `fetch()` promise. `fetch` resolves on 4xx and 5xx, and rejects only on network failure.
- **Impact:** A caller that does `await send(x)` and assumes success will show a success state after a validation, auth or server failure. The user can lose entered data without any warning.
- **Fix:** Check `res.ok`. On failure, throw or return a typed error with status and parsed body. Keep network failures, auth failures (401/403), validation failures (4xx) and server failures (5xx) distinguishable so the UI can show actionable errors and preserve form values.
- **Verify:** Unit test with a mocked `fetch` returning 400, 401, 500 and a rejection. Each case should reach the caller's error path.

**[Judgment call] `Content-Type: text/plain` on a JSON body**
- **Evidence (Confirmed header and body):** `client.js:1` sends `headers:{'Content-Type':'text/plain'}` with `body:JSON.stringify(data)`.
- **Impact (Needs verification):**
  - The header and body disagree. A server that dispatches on content type may reject the request, or it may parse the body anyway.
  - `text/plain` is a CORS-safelisted type, so a cross-origin page can send this request without a preflight. If the server parses it as JSON and relies only on cookie auth, that could weaken CSRF defences.
  - The URL is relative, so this client is same-origin. That limits the exposure, but only if the API is never called cross-origin.
  - Whether the server rejects, ignores or parses this is unknown. I'm not claiming a vulnerability.
- **Fix:** Unless the contract requires `text/plain`, use `application/json`. Pair that with server-side content-type enforcement and CSRF protection (SameSite cookies, a token, or an Origin check).
- **Verify:** Send the request and check the response. A strict server should answer 415 to `text/plain`. Confirm the server's CSRF mechanism separately.

**[Should-fix] No timeout, cancellation or retry/idempotency**
- **Evidence (Confirmed):** There is no `AbortSignal`, timeout, or idempotency key in `client.js:1`.
- **Impact:** A stalled request leaves the UI in a loading state indefinitely. If callers retry after a timeout, a POST to create items can produce duplicates, depending on server behavior (unverified).
- **Fix:** Accept an optional `signal`, apply a default timeout, and add an idempotency key if the contract supports one. Retry only when it is safe.
- **Verify:** Test against a hung mock server. The call should abort and the UI should leave its loading state.
