## Must-fix

**1. Errors appear for fields the user hasn't touched yet**
- Evidence: `SignupForm.tsx:20-22`. `onChange` runs `validate()` on the whole form on every keystroke.
- Impact: Typing the first letter of their name immediately shows "Invalid email" and the long password error under fields they haven't reached. Email also shows "Invalid email" while the user is still typing it. This is probably the biggest source of the frustration.
- Fix: Track `touched` per field and validate on blur. After a field has shown an error, re-validate it on change. On submit, validate everything.
- Verify: Typing in Name shows no email or password errors. Tabbing out of an invalid email shows its error, and the error clears as soon as the value becomes valid.

**2. A server failure wipes everything the user typed**
- Evidence: `SignupForm.tsx:31-34`. `setForm(initial)` runs on any non-OK response.
- Impact: The user loses their input, including a 12+ character password they just worked out, and sees only "Something went wrong". A duplicate email, a validation rejection and a 500 all look the same.
- Fix: Keep the form values. Map server errors to fields, such as "An account with this email already exists", with a generic retry message only as a fallback.
- Verify: Mock a 409, a 422 and a 500. The values stay and each case shows a specific message.

**3. Submit gives no feedback on success, while pending, or when the network fails**
- Evidence: `SignupForm.tsx:30-35`.
  - Nothing happens when `res.ok` is true: no redirect, no confirmation.
  - There is no pending state and the button isn't disabled, so a double click creates two requests.
  - `fetch` is not in a try/catch, so an offline user gets an unhandled rejection and a silent form.
  - `serverError` is never cleared on resubmit.
- Impact: Users can't tell whether signup worked and will click again.
- Fix: Add a `submitting` state that disables the button and changes its label to "Creating account…". Wrap the call in try/catch. Show a success state or redirect. Clear `serverError` at the start of each submit.
- Verify: Throttle or offline the network, double-click submit, and check the success path.

**4. Fields have no labels, and errors aren't tied to their inputs**
- Evidence: `SignupForm.tsx:39-44`.
  - The only label is `placeholder`, which disappears once the user types.
  - The error `<span>`s have no `id`, so there is no `aria-describedby` or `aria-invalid`.
  - There is no live region and no focus move on a failed submit.
- Impact: Users can't re-check what a field is for after typing. Screen reader users aren't told about errors. The password requirements only show up after the user fails them. This fails WCAG 3.3.1 and 3.3.2 and 1.3.1 and 4.1.3.
- Fix: Add visible `<label htmlFor>` elements. Give each error an `id` and link it with `aria-describedby`, plus `aria-invalid`. Move focus to the first invalid field on submit. Render `serverError` with `role="alert"`.
- Verify: Tab through with a screen reader and confirm names and errors are announced. Check keyboard-only completion.

## Should-fix

- **Missing input semantics** (`:41`, `:39`, `:43`): The email input has no `type="email"`, so mobile users don't get the email keyboard. None of the fields have `autoComplete` (`name`, `email`, `new-password`) or `name` attributes, which breaks autofill and password managers. Add all three.
- **Password rules are hidden and strict** (`:14-15`): The rules (12+ characters, uppercase, number, symbol) appear only as a failure message. Show them as hint text up front, and add a show/hide toggle. From memory, current NIST guidance favors length over composition rules. I haven't checked that against the source, so treat it as a product decision.
- **Weak email and name checks** (`:12-13`): `/^\S+@\S+$/` accepts `a@b`, and a name of `"  "` passes the required check. Trim the name and tighten the email check, or rely on `type="email"` plus server verification.
- **No submit-time summary** when several fields fail. Focus on the first error (see #4).
