## Query
For each customer with an `@acme.com` email, it returns the sum of their orders in the current month, sorted by that sum descending.

## Problems, most severe first

**1. The month filter on `orders` can't use an index (biggest cost).**
`date_trunc('month', o.created_at) = date_trunc('month', now())` wraps the column in a function. The planner can't use a plain index on `created_at`, so it has to evaluate the function on every candidate row.
- The schema has no index on `orders.customer_id` either. Postgres doesn't create indexes for foreign keys automatically.
- The correlated subquery therefore likely does a **sequential scan of `orders` once per matching customer**. That is O(customers × orders).
- Even with a `customer_id` index, it would fetch every order the customer has ever placed and filter them afterwards.

**2. `lower(c.email) LIKE '%@acme.com'` is not sargable.**
- The `lower()` call means a plain index on `email` is ignored.
- The leading wildcard rules out a B-tree prefix search.
- This forces a sequential scan of `customers`. That one is a single pass, so it's cheaper than problem 1, but it still grows with table size.
- The planner also can't estimate how many rows match, so it may choose a poor plan for the subquery.

**3. The correlated subquery runs once per customer.**
Postgres can sometimes flatten these, but not for a scalar aggregate subquery in the SELECT list. It runs as a SubPlan, once per outer row. Combined with problem 1, the cost multiplies.

**4. Minor: the sort.**
The `ORDER BY` is on a computed column, so it needs an in-memory or on-disk sort. That's cheap if the filtered customer set is small. Customers with no orders return NULL and sort last, which is intended.

## Suggested fixes

```sql
-- Indexes
CREATE INDEX orders_customer_created_idx ON orders (customer_id, created_at) INCLUDE (total);
CREATE INDEX customers_email_domain_idx ON customers (lower(email) text_pattern_ops);  -- see note below
```

```sql
-- Rewritten query: range predicate + a single aggregate pass
SELECT c.id, c.name, m.month_total
FROM customers c
LEFT JOIN (
    SELECT customer_id, SUM(total) AS month_total
    FROM orders
    WHERE created_at >= date_trunc('month', now())
      AND created_at <  date_trunc('month', now()) + interval '1 month'
    GROUP BY customer_id
) m ON m.customer_id = c.id
WHERE lower(c.email) LIKE '%@acme.com'
ORDER BY m.month_total DESC NULLS LAST;
```

**What changes:**
- **Range predicate:** `created_at >= … AND < …` is index-friendly. Combined with the composite index, it enables an index-only scan, or at least a narrow range scan.
- **One aggregation:** the join aggregates the month's orders once. It no longer runs a subquery per customer.
- **Same results:** the `LEFT JOIN` keeps customers with no orders this month, which matches the original behavior.

**Email filter:** a suffix match needs a different trick, because `text_pattern_ops` only helps prefix matches. Options:
- Store a `email_domain` column, or add a generated column, and index it. That's the cleanest option.
- Or index the reversed string: `CREATE INDEX ON customers (reverse(lower(email)) text_pattern_ops)`, and query `reverse(lower(email)) LIKE reverse('@acme.com') || '%'`.
- Or use a `pg_trgm` GIN index, which handles `%…` patterns but is heavier.

If the customers table is small, you can skip this and just fix the `orders` side, which is where most of the cost is.
