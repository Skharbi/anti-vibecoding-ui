## Must-fix

**[Must-fix] Patient records are cached in `localStorage` and never cleared**
Evidence (Confirmed): `src/records.ts:4-8` reads and writes the full `/api/records` response under the key `records`. Nothing removes it, and `logout()` doesn't either.
Impact: MRN, DOB, diagnoses, medications and labs stay on disk in plaintext. Any script running on the origin can read them, and so can anyone who later uses the same browser profile. The cache also never expires, so it can serve stale clinical data.
Fix: Don't persist PHI. Keep records in memory (or in a query cache that's dropped on logout). If you need offline or perf caching, use a short TTL and clear it on logout and on a 401.
Verify: Log in, load records, then check DevTools → Application → Local Storage. There should be no `records` entry, and none after logout either.

**[Must-fix] Logout doesn't end the session**
Evidence (Confirmed): `src/session.ts:12-14` only sets `location.href = "/login"`.
Impact: `accessToken`, `user` and `records` all remain in storage. The token stays valid for any later page load or script. No server call revokes it, though I can't tell from the frontend whether the server has a revoke endpoint.
Fix: Make logout call the server's logout/revoke endpoint if one exists. Then clear `accessToken`, `user`, `records` and any other user-scoped state, and then navigate. Clearing should happen even if the network call fails.
Verify: After logout, storage is empty. Replaying the old token against `/api/records` returns 401, which needs a backend check.

**[Must-fix] Records cache is shared across accounts**
Evidence (Confirmed): the cache key is the literal `"records"` (`src/records.ts:4,8`) and `login()` doesn't clear it (`src/session.ts:1-6`).
Impact: User B signing in after user A on the same browser gets A's records served from cache, without any API call. In a patient portal this is a cross-patient disclosure.
Fix: Removing the persistent cache fixes this. Otherwise, clear all user state at the start of `login()` and key any cache by user ID.
Verify: Log in as A, log out, log in as B. B should only ever see B's data.

**[Must-fix] Failed responses aren't checked, so errors get stored as valid state**

On a failed login, `accessToken` is probably `undefined`, and `localStorage.setItem` stores the string `"undefined"`. `authHeader()` then sends `Bearer undefined`.
