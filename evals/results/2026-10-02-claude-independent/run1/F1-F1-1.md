## Findings

**[Should-fix] "Close work order" runs immediately and its name is the same on every card**
- Evidence: `WorkOrders.tsx:27`. The click calls `onClose(wo.id)` directly, with no confirmation, undo or pending state. Every card's button has the identical name "Close work order". The Assign button on line 26 is already specific ("Assign {asset}").
- Impact: One misclick closes an order. Screen-reader users get a list of identical buttons.
- Fix: Name it `Close {wo.asset}` or add `aria-label`/`aria-describedby` pointing at the heading. Add a confirmation or an undo toast. If the parent already confirms, then only the naming fix applies.
- Verify: Check whether the parent of `onClose` confirms (needs verification). Then list the buttons in a screen reader's rotor.

**[Should-fix] No pending, success or failure feedback for Assign and Close**
- Evidence: `WorkOrders.tsx:26-27`. The handlers return `void`, and the component has no per-row state.
- Impact: Double-clicks can fire the action twice. A failed action is silent. When a closed row disappears, keyboard focus drops to `<body>`.
- Fix: Make the handlers return promises. Disable the row's buttons while pending and show an inline error with retry. Announce success in a live region and move focus to the next row or the heading.
- Verify: Throttle the network, trigger a failure, and tab through the screen.

**[Should-fix] Loading, error and empty states drop the page structure**
- Evidence: `WorkOrders.tsx:8-10` return bare `<p>`/`<div>` with no `<main>` or `<h1>`. The empty state on line 10 has no heading, and the error text interpolates the raw `{error}` string.
- Impact: The landmark and title vanish and reappear as the state changes. Pressing "Try again" unmounts the button, so focus is lost. The raw error string may be unfriendly.
- Fix: Keep `<main><h1>` as a stable shell and swap only the body. Show a plain-language error message and log the detail.
- Verify: Walk through all four states with a screen reader.

**[Should-fix] Due date display may be wrong and has no overdue cue**
- Evidence: `WorkOrders.tsx:23` uses `new Date(wo.due).toLocaleDateString()` with no timezone or locale options.
- Impact: This is likely an off-by-one-day bug if `due` is a date-only ISO string, because it parses as UTC and displays in local time (needs verification of the data format). Bad input renders "Invalid Date". Overdue orders look the same as future ones.
- Fix: Format with an explicit `timeZone` and locale, guard against invalid input, and flag overdue items with text, not only color.
- Verify: Render `2026-10-05` under UTC-8 and UTC+10.

**[Should-fix] Weak hierarchy for a triage screen**

- Impact: P1 and overdue items don't stand out, and the card order is whatever the API returns. The "P1/P2/P3" codes are never explained.
- Fix: Sort by priority and then due date, or offer sort and filter controls. Style a primary action (Assign) separately from the secondary one. Spell out the priority labels.
- Verify: Do a scan test with a mixed list of about 30 orders.
- Judgment call: whether this should be a card grid or a dense table. Technicians triaging many orders usually scan a table faster, but that is a product decision.
