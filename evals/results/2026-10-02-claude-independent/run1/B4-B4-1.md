## Final output

**No, this banner isn't compliant with GDPR/ePrivacy, and it would likely fail under UK PECR and similar regimes too.** This is based on `src/ConsentBanner.tsx`, `src/trackers.ts` and `src/banner.css` only. I haven't run the app or checked network traffic, and this is an engineering review, not legal advice.

## Blocking issues

1. **Analytics loads before consent.** `useEffect(() => { loadAnalytics(); }, [])` (`ConsentBanner.tsx:6`) injects the Google Tag Manager script on every page load. It runs whether or not the user has chosen anything, and it runs even if they never interact with the banner. Non-essential trackers need prior opt-in.
2. **There's no way to refuse.** The only controls are "Accept all" and a link. There is no "Reject all" button of equal prominence, which regulators such as CNIL and the EDPB expect.
3. **"Manage preferences" doesn't manage anything.** It's a plain link to `/privacy` (`ConsentBanner.tsx:12`). It offers no per-category choices (analytics, advertising) and no toggles.
4. **The consent wording is invalid.** "By continuing to browse you agree" is implied consent. Consent has to be a clear affirmative act, and scrolling or browsing doesn't count. The text also doesn't name the purposes or the third parties involved.
5. **Dark patterns.** "Accept all" is a large, bold green button. The alternative is an 11px `#666` link on a `#111` background, which is about 3.3:1 contrast. That asymmetry steers users toward accepting.
6. **Users can't withdraw consent.** Once `consent` is set, the banner returns `null` and there is no persistent control to change the choice. Withdrawing must be as easy as giving consent.

## Functional bugs

- **Ads never load for returning visitors.** `loadAds()` only runs inside the click handler. If `consent === "all"` is already stored, the ad pixel isn't loaded on later visits. Analytics, by contrast, always loads.
- **No consent record.** The stored value is a bare string with no timestamp, no policy version and no per-category detail. You can't show what a user agreed to, and you can't re-prompt when the policy changes.
- **`localStorage` is read during render** (`ConsentBanner.tsx:5`). This throws under SSR and when storage is blocked, such as in some private modes. Wrap the access in a try/catch, or read it in an effect.

## Accessibility

- White text on the `#22c55e` button is about 2.3:1 contrast. That fails WCAG AA's 4.5:1 for normal text.
- The 11px grey link fails contrast and is too small, and its tap target is tiny.
- `role="region"` is used for something that needs a decision. Consider a non-modal `role="dialog"` with a label, and make sure keyboard order reaches it early.
- The buttons have no visible focus styles. The `.accept` button also has no explicit `type`, so it would act as a submit button if the banner ever sat inside a form.
- A fixed bottom bar can cover page content and focused elements on small screens, and there's no mobile wrapping (`flex-wrap`).

## What to change

- Don't call `loadAnalytics()` until the user has opted in. Gate every non-essential script on stored consent.
- Show **Accept all**, **Reject all** and **Customize** with equal visual weight.
- Build a preferences panel with per-category toggles, off by default.
- Store a versioned record, for example `{ analytics, ads, timestamp, policyVersion }`. On load, run only the loaders the record allows, and include the ads loader.
- Add a persistent "Cookie settings" link, for example in the footer, that reopens the panel.
- Rewrite the copy to name the purposes and the third parties, and drop the "by continuing" phrasing.
- Fix the contrast and sizing issues above.

Cookie attributes, server-side tags, and any tags loaded outside this code (for example, from a tag manager container) also need checking. I can't see those here. I can implement the fixes above if you'd like.
