## Final output

There's no file named as an account data hook. `src/useInvoices.ts` is the only hook, so I reviewed that and `src/AccountSwitcher.tsx`. The two interact badly: after a switch, you can see the previous account's invoices.

## Blocking

**1. Invoice cache isn't scoped to the account, so data leaks across a switch** (`useInvoices.ts:3-8`)
- The module-level `cache` uses the fixed key `"invoices"`, and nothing clears it on a switch.
- After switching from account A to B, `useInvoices` initialises from the cached A data and skips the fetch (`cache.has` returns early). The billing page then shows A's invoices while the session is B.
- Even if the component stays mounted, the `[]` deps mean it never refetches.
- The cache is also never cleared on logout, so the next user in the same tab can see it.
- Fix: key the cache by account ID, or drop it and use a library with per-key caching (TanStack Query or SWR). Put the account ID in the key and the effect deps. At minimum, clear the cache when the session changes.

**2. A stale in-flight response can overwrite the cache** (`useInvoices.ts:9`)
- There's no abort and no unmount guard.
- If a request for A is still running when the user switches to B, A's response lands afterwards. It calls `cache.set` and `setData`, which poisons the cache and the UI.
- Fix: use `AbortController` in the effect cleanup, or an `ignore` flag. Tie the response to the account it was requested for.

**3. Errors are cached and shown as data** (`useInvoices.ts:9`)
- There's no `r.ok` check. A 401 or 500 JSON body gets stored in the cache as if it were the invoices, and it is never retried.
- A network failure or invalid JSON causes an unhandled rejection. The UI has no signal for it.
- Fix: check `r.ok`, only cache successes, and add a `.catch`.

**4. The switcher navigates even if the switch failed** (`AccountSwitcher.tsx:3-5`)
- It never checks `res.ok`, and there's no `try/catch`. If the switch returns 403 or 500, or the network drops, the user still lands on `/billing`, still in the old account. They'd believe they were on the new one, so this can be a wrong-account billing action.
- Fix: only navigate after a successful response, and show an error otherwise.

## Should fix

- **CSRF risk on the switch request** (`AccountSwitcher.tsx:3`): a cookie-authenticated POST has a string body with no `Content-Type`, so it goes out as `text/plain`. That's a CORS "simple request", so a cross-site form can send it. Send `Content-Type: application/json` and require a CSRF token or a custom header. Confirm the server also checks `Origin` and `SameSite`.
- **No pending or double-click guard** (`AccountSwitcher.tsx:2-8`): rapid clicks fire overlapping switch requests, and the last response to arrive wins, which may not be the last click. Track a pending state, disable the buttons while it's set, and serialise the calls.
- **The `pushState` and fake `popstate` navigation is fragile** (`AccountSwitcher.tsx:4-5`): it only works if the router listens for `popstate`, and it leaves all in-memory state in place. That state includes the cache above, and likely any other per-account data. After a switch, a full reload (`location.assign("/billing")`) is simpler and safer. Otherwise, use the router's `navigate` and invalidate the per-account data.
- **The hook returns bare `unknown`** (`useInvoices.ts:6`): callers can't tell loading from empty from error, and there's no type for the invoice shape. Return `{ data, error, isLoading }` with a real `Invoice[]` type.

## Minor

  - Add `type="button"` to the buttons.

- **Cache has no expiry**: invoices stay stale for the life of the page.
