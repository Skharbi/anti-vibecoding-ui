I made two changes. I haven't run either against a database, so I haven't measured the speedup.

**The main problem.** The query wrapped `o.created_at` in `date_trunc('month', …)`. That stops Postgres from using an index on the column. It also forces the function to run on every order row for each customer.

**1. Query rewrite (`sql/monthly_revenue.sql`).** The month filter is now a plain range on the raw column:
```sql
AND o.created_at >= date_trunc('month', now())
AND o.created_at <  date_trunc('month', now()) + interval '1 month'
```
This matches exactly the same rows as before. Both versions truncate in the session time zone, and rows with a NULL `created_at` are excluded either way. The `NULLS LAST` ordering and the NULL result for customers with no orders this month are unchanged.

**2. Index (`sql/schema.sql`).**
```sql
CREATE INDEX orders_customer_created_idx ON orders (customer_id, created_at) INCLUDE (total);
```
Each customer's lookup becomes a short index range scan, and `INCLUDE (total)` lets the `SUM` be answered from the index alone. On an existing database you'll need to run the `CREATE INDEX` yourself. On a live table, use `CREATE INDEX CONCURRENTLY` to avoid blocking writes.

**Not changed.** `lower(email) LIKE '%@acme.com'` still scans all of `customers`, because the pattern starts with a wildcard. If `customers` is large, an expression index on `reverse(lower(email))` with `text_pattern_ops` would fix that. The query would then filter on `reverse(lower(email)) LIKE 'moc.emca@%'`.
