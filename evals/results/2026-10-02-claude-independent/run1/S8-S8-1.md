## Must-fix

**[Must-fix] Model output is rendered as raw HTML**
- Evidence: `AssistantPanel.tsx:22` passes `reply.html` to `dangerouslySetInnerHTML` with no sanitization.
- Impact: If the model's output carries markup from a ticket or customer record, it can run script in the support agent's session. That session also has `credentials: "include"` access to customer data.
- Fix: Have the API return Markdown or structured text and render it as React nodes. If HTML is unavoidable, sanitize it with DOMPurify and an allowlist before rendering. Also add a CSP as defense in depth.
- Verify: Return `<img src=x onerror=alert(1)>` from a stubbed response and confirm nothing executes.

**[Must-fix] Model-chosen actions run automatically, with no confirmation**
- Evidence: `AssistantPanel.tsx:13` assigns `window.location.href` to a model-supplied URL. `:14` sends a credentialed request to a model-supplied URL, method and body. Nothing is shown to the user first.
- Impact: A manipulated reply can navigate the agent to an arbitrary site. It can also fire a refund or account change at any endpoint, using the agent's cookies. Whether the server rejects this is unverified. The client does nothing to prevent it.
- Fix:
  - Treat the model's `action` as a proposal. Render a card with the plain-language effect, such as "Refund $42.00 to customer #123", and a Confirm button and a Cancel button.
  - Have the server issue the action. The client should send only an opaque action ID, not a URL, method or body.
  - Allowlist action types and paths. Allow `open_url` only for same-origin relative paths.
  - Re-check authorization on the server, independent of the model.
  - Add a CSRF token and an idempotency key for refunds.
- Verify: A reply with `open_url: "https://evil.example"` must not navigate. A `call_api` reply must make no request until the user confirms.

## Should-fix

- **No error handling** (`:10-14`): There is no `res.ok` check and no `try/catch`. A 500, a network failure or non-JSON output leaves the UI silent or throws an unhandled rejection. If the action `fetch` at `:14` fails, the user sees the reply as if it had worked. Show per-step status: reply received, action done or failed.
- **No pending state or double-submit guard** (`:21`): Ask stays clickable during the request. A double-click sends two prompts. Because actions execute automatically, it could also run a refund twice. Disable the button, show "Thinking…", and support abort.
- **Empty input is sendable** (`:21`): Disable Ask when `q.trim()` is empty. Wrap the field in a `<form>` so Enter and Ctrl+Enter submit.
- **Async results aren't announced** (`:22`): The reply container isn't a live region, so screen-reader users get no signal. Add `role="status"` or `aria-live="polite"`, plus a separate `role="alert"` for errors.
- **Missing `Content-Type`** (`:10`): The body is a JSON string with no `Content-Type: application/json` header. It goes out as `text/plain`. Whether the server accepts that needs verification. The `:14` call has the same gap.
- **Generic structure**: `<aside>` has no accessible name. Use `aria-label="Assistant"` and add a heading. There are no visible focus or button styles. The label and field have no spacing or size. The textarea has no `rows` or `maxLength`.
- **Credibility and trust cues**: Nothing marks the reply as AI-generated, or as a suggestion rather than a verified fact. Nothing shows which records the answer used. Add both, and a feedback or report control. Customer records are PII, so also check that the reply isn't logged client-side or in analytics.
- **State handling**: The panel keeps the previous reply and query after a new `ask()`. This can show a stale answer next to a new question, or after an account switch. It has no conversation history.
