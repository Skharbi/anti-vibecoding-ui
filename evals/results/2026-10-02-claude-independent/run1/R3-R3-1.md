# Responsive review: `claims.html`

**Result: Fail.** Two confirmed must-fix issues make the screen unusable on a phone. I read the code and worked out the layout from the CSS. I did not render it in a browser or on a device, so the pixel numbers below are calculated, not measured.

## Must-fix

**[Must-fix] The fixed 260px sidebar leaves almost no room for content on phones**
- Evidence: `claims.html:5-6`. `body` is `display:flex`, and `aside` is `width:260px; flex:none` with no breakpoint.
- Impact: On a 375px phone, the sidebar plus its padding and border take about 281px. That leaves about 94px for `main`, and the table can't shrink to fit. Reviewers have to scroll sideways to reach the table, the note field and the submit button. The three nav links take up the most space on the screen where they matter least.
- Fix: Below about 768px, stack the layout (`body{flex-direction:column}`) and make the sidebar a compact top bar, or put it behind a menu button. Keep `aside` as a `flex:none` column only at wider widths.
- Verify: At 360, 390, 768 and 1280px, the page has no document-level horizontal scroll and the nav is reachable.

**[Must-fix] The table is a fixed 720px wide, with no scroll container or narrow-screen layout**
- Evidence: `claims.html:8-9`. `table{width:720px}` and `td{white-space:nowrap}`. The table sits directly in `main`, not in a scrollable wrapper.
- Impact: The table is wider than any phone, and `nowrap` blocks wrapping. On a phone the whole page scrolls sideways. The Status and Last updated columns, which reviewers need, sit off-screen. A long name such as "Alexandria Montgomery-Whitfield" also widens the first column on desktop.
- Fix: Use one of two approaches.
  1. **Quick fix:** wrap the table in `<div style="overflow-x:auto">`, set `width:100%; min-width:…` on the table, and add a visible scroll cue.
  2. **Better for a triage queue:** under about 640px, turn each row into a card. Show patient and status first, then payer and updated time as secondary lines. Drop `nowrap` from the name and payer cells.
- Verify: At 360px, status and patient are visible without sideways scrolling. The page itself doesn't scroll sideways. A long name wraps cleanly.

## Should-fix

**[Should-fix] The fixed footer bar will crowd the screen on phones**
- Evidence: `claims.html:10, 31`. It is fixed at 64px with `justify-content:flex-end`. The "Approve selected" button has no sizing, so it uses the browser default (about 20–25px tall).
- Impact:
  - The button is well under the 44px touch-target size (24px minimum in WCAG 2.2 AA), and it is the highest-consequence action on the screen.
  - It sits right-aligned and far from the "2 claims selected" label on a narrow screen.
  - The bar takes a fixed 64px of a short landscape viewport.
  - With no `viewport-fit=cover` or `env(safe-area-inset-bottom)` padding, a phone's home-indicator area can crowd the bar.
  - `padding-bottom:80px` on `main` does cover the 64px bar, so this part is fine today.
- Fix: Give the button a `min-height:44px` and padding. Let the bar wrap or space its contents (`justify-content:space-between`). Add `padding-bottom:env(safe-area-inset-bottom)`.
- Verify: Tap the button with a thumb-sized target at 360px and in landscape. The last form control stays visible above the bar.

**[Should-fix] The selection state is not connected to anything**
- Evidence: `claims.html:31` hardcodes "2 claims selected", and the table (`:18-24`) has no checkboxes.
- Impact: This is a workflow problem, not only a responsive one. A reviewer can't tell which claims "Approve selected" will approve. An approval action should name its targets, and on a phone that matters more because the table may be partly off-screen.
- Fix: Add a labelled checkbox column, which must survive the narrow layout (for example as a card checkbox). Drive the count from real selection, and disable the button at zero.
- Verify: Select and deselect rows, and check that the count and the button state update.

**[Should-fix] Nav links are small, stacked with `<br>`, and not marked as current**
- Evidence: `claims.html:15`.
- Impact: Each link is a text-height tap target. There is no current-page indication, and `<br>` is a layout hack.
- Fix: Use a list with links padded to at least 44px, plus `aria-current="page"` on Queue.

**[Should-fix] The textarea overflows its container slightly**
- Evidence: `claims.html:11`. `width:100%` with the default `content-box` sizing, plus its padding and border.
- Fix: Add `box-sizing:border-box`, or use `*{box-sizing:border-box}`.

**[Should-fix] Table semantics are thin**
- Evidence: `claims.html:18-19`. There is no `<caption>`, and the `th` elements have no `scope`. Both matter more once the table is converted to cards or put in a scroll region.
- Fix: Add `<caption>`, `scope="col"`, and `tabindex="0"` plus a label on the scroll wrapper so keyboard users can scroll it.

## Judgment call
Row cards or a scrollable table? Cards read better for triage, but they change how the table scans on desktop. They also lose side-by-side comparison, so I'd use them only below the narrow breakpoint. If reviewers compare many claims, a sticky first column plus horizontal scroll may suit them better.
