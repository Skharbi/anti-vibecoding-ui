## Final output

Yes, client-side logging exposes both tokens and user-entered data. I read the only two source files, `src/errorReporting.ts` and `src/PaymentForm.tsx`. `./session` isn't in the repo, so I couldn't check what `getSession()` returns.

**Findings**

1. **Critical: card data goes to a third-party log service.**
   - `src/PaymentForm.tsx:7` calls `reportError(e, { action: "submitPayment", input: values })`. `values` holds `cardNumber`, `cvc` and `amount`.
   - `src/errorReporting.ts:12` serializes `input` unfiltered into the POST body to `logs.example-observability.io`.
   - Any failed payment, including a plain 4xx or 5xx, sends the full PAN and CVC off-site. That is a PCI DSS violation, because storing the CVC is prohibited even when encrypted.

2. **Critical: the access token is sent in every report.**
   - `src/errorReporting.ts:13` sends `token: session?.accessToken`.
   - Anyone with access to the log vendor or its retention store could use the token to hijack sessions.

3. **High: PII is attached to every report.**
   - `src/errorReporting.ts:14` sends `userEmail`.
   - `src/errorReporting.ts:15` sends `location.href` with its query string and hash. Those can contain reset tokens, OAuth codes or identifiers.

4. **Medium: error messages and stacks may carry sensitive data.**
   - `err.message` and `err.stack` are sent as-is. Today the message is only `pay failed <status>`, but any future error that interpolates input would leak it.

5. **Low: the reporter is unsafe to call.**
   - `fetch` is not awaited and has no `.catch`, so a failed report becomes an unhandled rejection.
   - There is no sampling, rate limit or size cap.
   - Nothing sanitizes the payload centrally, so every caller can leak.

**Suggested fixes**
- Remove `token` entirely. If the backend needs correlation, send an opaque session or request ID instead.
- Remove `userEmail`, or replace it with a non-reversible user ID.
- Drop `input` from `reportError`. In `PaymentForm`, report only non-sensitive metadata, such as `{ action, status }`.
- If a context object is still needed, use an allowlist of fields rather than a denylist, and redact in one place inside `reportError`.
- Strip the query string and hash from the URL by sending `location.origin + location.pathname`, or a route template.
- Add `.catch(() => {})`, a payload size limit and basic rate limiting to the reporter.
- Rotate any tokens that may already have been logged. Check the vendor's retention for stored card data, and treat that as a possible PCI incident.
