**[Should-fix] The `Content-Type` doesn't match the body**
- Evidence: `client.js:1` sends `JSON.stringify(data)` with `Content-Type: text/plain`.
- Impact: A server that parses by content type may reject the request or read the body as a string. Whether it does can't be confirmed without the contract.
- Fix: Send `application/json`, unless the server contract explicitly requires `text/plain`. If it does, document why.
- Verify: Send one request against the real or a mock server and check that the item is created.

**[Should-fix] HTTP failures are not surfaced**
- Evidence: `client.js:1` returns the raw `fetch` promise. `fetch` resolves on 4xx and 5xx, and nothing checks `response.ok`.
- Impact: A caller that only awaits `send()` will treat a rejected or failed save as success. I can't see any callers, so the actual impact depends on them.
- Fix: Check `ok`, then throw a typed error that carries the status and the parsed error body. Return parsed JSON on success.
- Verify: Mock 400, 500 and network-failure responses. Each should reject, and the UI should show an error state.

**[Should-fix] A bad payload throws synchronously**
- Evidence: `send` is not `async`, so a `JSON.stringify` failure (circular data, `BigInt`) throws instead of returning a rejected promise. `undefined` data sends an empty body.
- Impact: Callers that use `.catch()` without `try/catch` miss the error.
- Fix: Make `send` an `async` function and validate or serialize inside it.

**[Should-fix] No timeout, cancellation or duplicate-submit protection**
- Evidence: There is no `AbortSignal`, no timeout, and no idempotency key on a `POST`.
- Impact: A stalled request can hang the UI indefinitely. A user retry or double-click could create duplicate items. Whether the server de-duplicates is unknown.
- Fix: Accept an optional `signal`, add a default timeout, and send an idempotency key if the server supports one. Disable the submit control while the request is pending.
