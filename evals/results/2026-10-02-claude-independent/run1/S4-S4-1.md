## Must-fix

**[Must-fix] Unvalidated `next` parameter is assigned to `window.location.href`**
- Evidence: `src/Login.tsx:12-13`. The value comes straight from `?next=` and is used for navigation with no check.
- Trust boundary: a URL anyone can craft or link to, which then drives the browser after a successful login.
- Impact: an attacker can send a login link with `?next=https://evil.example`. After the user authenticates, they land on a phishing page that looks like a legitimate post-login step. A `javascript:` value is also a script-execution sink, because assigning it to `location.href` runs the code in the app's origin. The scheme risk is browser behavior I'm recalling, not something I ran here.
- Fix: accept only same-origin relative paths.
  ```ts
  function safeNext(raw: string | null) {
    if (!raw || !raw.startsWith("/") || raw.startsWith("//") || raw.startsWith("/\\")) return "/home";
    return raw;
  }
  ```
  A stricter option is to resolve it with `new URL(raw, location.origin)` and require the same `origin`.
- Verify: try `?next=https://x.test`, `//x.test`, `/\x.test` and `javascript:alert(1)`. Each should land on `/home`, and `?next=/reports?id=3` should still work.

**[Must-fix] Failures are handled wrongly or not at all**
- Evidence:
  - `src/Login.tsx:10` has no `try/catch`. A network failure rejects the promise and the user sees nothing.
  - `src/Login.tsx:11` maps every non-OK response to "Email or password is incorrect." A 500, 429 or 503 would blame the user's credentials.
  - There's no pending state. The button stays active, so double-clicks send duplicate requests, and nothing tells the user a request is in flight.
- Impact: the user gets either silence or misleading feedback, and may retry or reset a password for no reason.
- Fix: add `submitting` state and disable the button while it's true, with the label changing to "Signing in…". Wrap the fetch in `try/catch`. Show the credentials message only for 401 (or 400/403 if that's the server contract). Show a "Couldn't reach the server, try again" message for network errors and a "Try again in a moment" message for 5xx/429. Clear the error at the start of each submit.
- Verify: use offline mode, mock 401, 429 and 500 responses, and double-click submit. Each case should give the correct message and send exactly one request.
