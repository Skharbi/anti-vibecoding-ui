## Must-fix

**[Must-fix] The success message claims a security check that doesn't happen**
- Evidence: `UploadReferral.tsx:10-12`. The only checks are `f.type`, which the browser derives from the extension, and `.pdf` in the filename. After they pass, the UI says "securely validated and is safe to upload."
- Impact: A renamed non-PDF, or a malicious or corrupt PDF, gets the same reassurance. A referral letter is probably sensitive health data, so users may trust the message.
- Fix: Use a neutral message such as "referral.pdf selected (1.2 MB)". Don't claim safety anywhere in the client. Treat the type check as a convenience only, and do the real validation on the server.
- Verify: Select a `.txt` file renamed to `.pdf`. The UI must not call it safe, and the server must reject it.

**[Must-fix] "Uploaded." shows even when the upload failed, and network errors go unhandled**
- Evidence: `UploadReferral.tsx:18-19`. The code never checks `res.ok` and has no `try/catch`.
- Impact: A 401, 413 or 500 response still shows "Uploaded." The user may think a referral was filed when it wasn't. A network failure throws an unhandled rejection and shows nothing.
- Fix: Track a status of `idle | uploading | success | error`. Treat `!res.ok` as an error and show a specific message with a retry option. Show success only after `res.ok`.
- Verify: Force 401, 413, 500 and offline responses. Each must show an error, and only a 2xx may show success.

**[Must-fix] A rejected or cancelled pick leaves the previous file queued**
- Evidence: `UploadReferral.tsx:9-10`. Both early returns skip `setFile`, so the old `file` stays in state.
- Impact: Pick `a.pdf`, then pick `b.docx`. The input shows `b.docx` and the message says "Only PDF files are allowed," but the Upload button is still enabled and sends `a.pdf`. Cancelling the picker has the same effect. The user can upload a different document than the one shown.
- Fix: Call `setFile(null)` on every rejection and on an empty selection. Clear the previous message too.
- Verify: Pick a valid file, then an invalid one. Upload must be disabled.

**[Must-fix] Status and error messages aren't announced to screen readers**
- Evidence: `UploadReferral.tsx:26`. The `<p>{msg}</p>` is a plain element with no live region.
- Impact: Screen reader users get no notice of validation errors or upload results. The result of the primary action is silent for them.
- Fix: Render a persistent container with `role="status"` for success and progress, and `role="alert"` for errors. Also link errors to the input with `aria-describedby`.
- Verify: Test with NVDA or VoiceOver. Each state change should be announced once.
