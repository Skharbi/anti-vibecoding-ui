# Frontend security review: Team Notes

I read all five source files: `src/App.tsx`, `src/main.tsx`, `index.html`, `vite.config.ts` and `package.json`. This is a frontend-only review. I didn't run the app, check deployment headers, or look at the backend.

**Verdict:** I found no confirmed high-impact client-side flaw. That is not a security sign-off, because the main risks sit in the backend and deployment, which I couldn't see.

## Findings

### Should-fix

1. **API response is trusted without checking its shape** (Confirmed, `src/App.tsx:10-11,18`)
   - `r.json()` goes straight into `setNotes`. If the API returns a non-array, such as an error object with a 200 status, a proxy HTML page, or `null`, then `notes.map` throws during render.
   - There is no error boundary, so the whole page goes blank instead of showing the "Couldn't load notes" message.
   - This is a reliability issue at a trust boundary (OWASP 2025 A10, mishandling of exceptional conditions). Check `Array.isArray` and the field types, or use a schema validator. Also add an error boundary.
   - To verify, mock `/api/notes` to return `{}` and confirm the blank page.

2. **No session-expiry handling** (Confirmed in the code, impact is likely low)
   - A 401 or 403 is rejected and shown as the generic "Couldn't load notes." (`src/App.tsx:10,12`).
   - It fails closed, which is good, but the user can't tell a logged-out session from an outage. There's also no sign-in redirect and no cleared state.
   - Handle 401 and 403 separately.

3. **No lockfile in the project and caret version ranges** (Confirmed, `package.json:3-4`)
   - The directory listing showed no lockfile, so installs aren't reproducible. That is a supply-chain weakness (OWASP 2025 A03, software supply chain failures).
   - Commit a lockfile and use `npm ci` in CI.
   - I did not check dependency advisories or Vite 5's support status. Run `npm audit` and check Vite's current support policy before relying on either.

4. **`credentials: "include"` is broader than needed** (Confirmed, `src/App.tsx:9`)
   - The URL is relative, so the default `same-origin` already sends cookies. `include` would also send them if the URL later becomes cross-origin.
   - It's a read-only GET, so there is no CSRF exposure today. Any future POST, PUT or DELETE on cookie auth will need CSRF protection from the backend, such as SameSite cookies plus a token or an Origin check.

### Needs verification (backend and deployment)

- **Authorization on `/api/notes`:** The client renders whatever comes back. The server must scope notes to the caller's team or tenant, since the UI can't enforce it. Test with two accounts in different teams.
- **Security headers:** `index.html` has no CSP, and nothing in the repo sets headers. Confirm the production response has:
  - a CSP, ideally with no `unsafe-inline`
  - `frame-ancestors` or `X-Frame-Options`
  - `X-Content-Type-Options: nosniff`
  - a Referrer-Policy
  - HSTS
- **Caching of sensitive responses:** Team notes may be confidential. Check `Cache-Control` on `/api/notes`, and whether back/forward cache or a shared cache could show them after logout.
- **Production source maps:** Vite doesn't emit them by default. Confirm the deployed build has none.
