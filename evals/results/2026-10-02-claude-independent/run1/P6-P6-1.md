## Must-fix

**[Must-fix] Out-of-order responses can show results for the wrong query**
Evidence: `PatientSearch.tsx:9-14`. Every keystroke fires a `fetch`, and each one calls `setHits` when it resolves. There is no abort and no stale-response check.
Impact: A slow response for `smi` can arrive after the response for `smith` and overwrite it. The input says one thing and the list shows another. In a patient-lookup flow, a clinician could pick the wrong patient from a stale list. Clearing the input has the same race: an in-flight response can repopulate the list after `setHits([])`.
Fix: Use an `AbortController` per request and abort the previous one, or ignore responses that aren't the latest. Debounce by about 200–300 ms and add a minimum length if the API suits it.
Verify: Throttle the network, type quickly, and make sure only the latest query's results ever render. Then clear the box mid-request and confirm the list stays empty.

**[Must-fix] Failed requests are unhandled and produce misleading results**
Evidence: `PatientSearch.tsx:12-13`. There is no `r.ok` check and no `try/catch`. A 401, 403 or 500 with a JSON error body, such as `{error: "..."}`, goes straight into `setHits`, and `hits.map` then throws, which unmounts the component. A network failure becomes an unhandled promise rejection and the UI doesn't change.
Impact: An expired session or a server error either crashes the search or silently shows nothing. The user can't tell "no such patient" from "search is broken", which is a serious problem when looking up patients.
Fix: Check `r.ok`, validate that the response is an array, and keep `loading`, `error` and `results` as separate states. Show a distinct error message with a retry. A 401 should go through the app's re-auth path.
Verify: Simulate 401, 500, offline and a malformed body. Each should show a distinct, announced message and the component should stay mounted.

## Should-fix

**[Should-fix] Results are invisible to assistive technology and the pattern is incomplete**
Evidence: `PatientSearch.tsx:19-24`. Results appear in a plain `<ul>` with no live region. There is no loading state and no "No patients found" state. Screen-reader users get no feedback when results arrive or when there are none. The component also has no error state, as noted above.
Fix: Add a visually hidden `role="status"` / `aria-live="polite"` region with messages like "3 patients found", "No patients match 'x'" and "Searching…". Keep the simple list-of-buttons pattern. A full ARIA combobox isn't required here and would be riskier to get right. If you do want arrow-key navigation, follow the APG combobox pattern completely.
Verify: Test with a screen reader and keyboard only (type, Tab to results, Enter).

**[Should-fix] The input and button have weak semantics and no styling hooks**
Evidence: `PatientSearch.tsx:19, 22`.
- The input should have `type="search"`, a `name`, and probably `inputMode`/`enterKeyHint="search"`.
- The button has no `type="button"`. It defaults to `submit`, so inside a surrounding `<form>` it will submit that form.
- Wrap the control in `role="search"` or a `<search>` element.
- The `id="ps"` is hard-coded and will collide if the component renders twice. Use `useId()`.
- There are no classes or styles, so focus, hover and spacing depend on whatever the parent provides. Confirm that focus stays visible.

**[Should-fix] Patient identifiers need care in how they're displayed**
Evidence: `PatientSearch.tsx:22`. Name and MRN are concatenated as `Name · MRN 123`. Two patients with the same name are distinguished only by MRN, with no date of birth.
Impact: Patient-safety guidance usually calls for two identifiers when picking a patient, and DOB is the usual second one. A long name will also wrap oddly inside the button. This depends on what your API returns and on your clinical workflow, so treat it as a product question rather than a confirmed defect.
Fix: If the API provides DOB, show it. Give name and MRN separate elements so MRN can be monospaced and aligned.
