## Must-fix

**[Must-fix] `placeOrder` never checks the HTTP status, so failed orders look like successes**
Evidence: `src/checkout.ts:13-14` returns `res.json()` without checking `res.ok`.
Impact: a 4xx or 5xx response with a JSON error body is returned as if it were an order result. A non-JSON error body (such as a gateway 502 page) makes `res.json()` throw an opaque `SyntaxError`. Either way the caller can't reliably tell the user whether the order was placed.
Fix: check `res.ok` and throw or return a typed result such as `{ ok: false, status, error }`. Wrap parsing so that network errors, timeouts and non-JSON bodies each give the UI a distinct outcome.
Verify: unit-test 200, 422 with a JSON body, 502 with an HTML body, and a rejected `fetch`. Confirm the checkout UI shows an error and keeps the cart in each failure case.

## Should-fix

**[Should-fix] The client sends privileged and derived values in the order payload**
Evidence: `src/checkout.ts:7,12` sends `total`, `isAdmin` and `userId`. `isAdmin` and `id` come from `sessionStorage` (`src/user.ts:1`), which the user can edit.
Impact: whether this matters depends on the server, which I haven't seen. The client can't make these values trustworthy, so they should not be sent as inputs.
Fix: drop `isAdmin`, `userId` and `total` from the request. The server should take identity from the session and compute price from SKUs and the coupon.
Verify (server side): submit a tampered `total`, `isAdmin` or `userId` and confirm the server ignores or rejects it.

**[Should-fix] `getUser()` is unvalidated and can throw**
Evidence: `src/user.ts:1`. `JSON.parse` throws on corrupted storage. An empty or missing entry returns `{}`, so `user.id` is `undefined` and `JSON.stringify` silently omits it. The return type is `any`.
Impact: a corrupted entry crashes checkout. A signed-out user gets an order request with no identity and no client-side message.
Fix: parse in a `try/catch`, validate the shape, and return `null` when there is no user. Have checkout handle that case, for example by prompting for sign-in. If the server derives identity from the session, remove this dependency entirely.

**[Should-fix] No protection against double submission, and no timeout**
Evidence: `src/checkout.ts:5-14` has no idempotency key, in-flight guard or `AbortSignal`.
Impact: a double click or a retry after a slow response can submit the order twice. Whether it creates duplicate orders depends on the server.
Fix: send an `Idempotency-Key` header generated once per checkout attempt. Disable the submit button while the request is pending. Add a timeout.

**[Should-fix] Money is computed with floats and shown without formatting**
Evidence: `src/checkout.ts:7` multiplies and sums `unitPrice` as a JS number. `src/OrderView.tsx:7` renders `{order.total}` raw.
Impact: the display can show values like `19.990000000000002` or a bare `1999` with no currency. Floating-point rounding errors only appear if prices are decimals rather than integer minor units, and I can't tell which they are.
Fix: use integer minor units, or format with `Intl.NumberFormat` and an explicit currency. This is also another reason not to send a client-computed total.

**[Should-fix] The Refund button has no confirmation, pending state or error feedback**
Evidence: `src/OrderView.tsx:9` wires `onClick` straight to the `onRefund` prop.
Impact: a refund is a hard-to-reverse financial action, and one misclick triggers it. There is also no double-click guard or failure message.
Fix: add a confirmation step that states the amount, and disable the button while pending. Show success and error results. Parent code that I haven't seen may already do some of this, so confirm it there first.

**[Should-fix] `OrderView` leaves out status and has no loading or error states**
Evidence: `src/OrderView.tsx:1,6-9`. `status` is in the type but never rendered, and the component assumes `order` and `order.permissions` always exist.
Impact: users can't see whether an order is paid, shipped or refunded, which is the main thing they need when managing an order. A partial API response would crash the component.
Fix: render the status, and handle missing or partial data in the parent or with a guard.

**[Should-fix] The Edit link and Refund button may be hard to tell apart for assistive technology**
Evidence: `src/OrderView.tsx:8-9`. A link and a button sit side by side with no grouping or spacing. Both are correctly native elements. The `<h1>` also lives inside a reusable component.
Impact: this is minor. A component that owns the page `<h1>` can create duplicate or misordered headings if it is rendered more than once.
Fix: take the heading level from the page context, and group the actions with visible, consistent styling. Make Refund visibly a destructive action.
