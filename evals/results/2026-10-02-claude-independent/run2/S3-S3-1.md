# Auth/session review: patient portal frontend

**Result: Fail.** There are confirmed must-fix issues. I only found two relevant files, `src/session.ts` and `src/records.ts`. There are no components, routes or login UI in this tree, and I did static inspection only. I ran nothing.

## Must-fix

**[Must-fix] Logout doesn't clear user data from the browser**
Evidence: `src/session.ts:12-14` only sets `location.href = "/login"`. Nothing removes `accessToken`, `user` (set at `session.ts:4-5`) or `records` (set at `records.ts:8`).
Impact: After "logout", the bearer token stays in `localStorage` and keeps working until the server expires it. The patient's records and profile also remain on disk. On a shared or family computer, the next person can read them from devtools.
Fix: Have `logout()` call a server revoke endpoint, then clear every user-scoped key. Don't clear selectively.
Verify: Log in, log out, then check that `localStorage` is empty and that replaying the old token returns 401.

**[Must-fix] Cached records are shown to whoever signs in next**
Evidence: `src/records.ts:4-5` returns `localStorage["records"]` before any network call. The key has no user ID and no expiry, and the cache isn't tied to the current token. Combined with the logout finding above, a second account on the same browser gets the first patient's records.
Impact: Cross-patient exposure of health data. For healthcare data I'd treat this as high severity.
Fix: Don't persist records in `localStorage`. Hold them in memory, or in a cache keyed by user and cleared on logout and login. If you need offline support, set an explicit retention policy first.
Verify: Sign in as user A and then as user B on the same browser. B should never see A's data.

**[Must-fix] A failed request is cached and later shown as the records**
Evidence: `src/records.ts:6-8` never checks `res.ok`. A 401, 403 or 500 body is parsed and written to `localStorage["records"]`. After that, `records.ts:5` returns it permanently.
Impact: An expired session produces a stuck, wrong "records" state that survives reloads. There is also no 401 handling anywhere, so session expiry isn't detected and the user is never sent back to login.
Fix: Throw on non-2xx. On 401, clear the session and redirect to login. Cache only successful responses.
Verify: Force a 401 and confirm the user lands on login and nothing is written to storage.

## Should-fix

**[Should-fix] Login doesn't check the response and can store `"undefined"` as the token**
Evidence: `src/session.ts:2-5` destructures the JSON without checking `res.ok`. On a failed login, `accessToken` is `undefined` and `localStorage.setItem` stores the string `"undefined"`. Then `authHeader()` (`session.ts:9`) sends `Bearer undefined`, or `Bearer null` if the key is missing.
Impact: A failed login looks identical to a successful one to the caller, so the UI can't show an error. Bad credentials leave the app in a broken half-signed-in state.
Fix: Return a typed success/failure result. Write to storage only on success. Show a generic error message.
Verify: Log in with a wrong password. The UI should show an error and storage should stay empty.

**[Should-fix] Bearer token and profile are in script-readable persistent storage**
Evidence: `src/session.ts:4-5, 9`.
Impact: Any XSS, or any compromised third-party script, can read and exfiltrate the token. I found no XSS sink in these files, so this is a risk and not a demonstrated exploit. I'd still want a stated threat model before accepting it for patient data.
Fix: Prefer an `HttpOnly; Secure; SameSite` session cookie set by the server. If you switch, add CSRF protection for state-changing requests. Alternatively, keep a short-lived access token in memory with a cookie-based refresh.
Verify: After login, `document.cookie` and `localStorage` should expose no credential.
