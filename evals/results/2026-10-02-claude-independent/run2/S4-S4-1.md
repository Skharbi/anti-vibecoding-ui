## Must-fix

**[Must-fix] Unvalidated `next` parameter is assigned to `window.location.href`**
- Evidence: `src/Login.tsx:12-13`. `next` comes straight from the query string and is assigned with no check. This is confirmed from the code.
- Impact:
  - A crafted link such as `/login?next=https://evil.example` sends the user to an attacker's site right after they sign in. The phishing page can look like a "session expired, sign in again" prompt.
  - A `next=javascript:...` value is also assigned to `location.href`, which runs script in your origin. That is DOM XSS after a successful login.
  - The attacker needs the victim to log in through the crafted link.
- Fix: accept only same-origin relative paths.
  ```ts
  function safeNext(raw: string | null): string {
    if (!raw || !raw.startsWith("/") || raw.startsWith("//") || raw.startsWith("/\\")) return "/home";
    try {
      const u = new URL(raw, window.location.origin);
      return u.origin === window.location.origin ? u.pathname + u.search + u.hash : "/home";
    } catch { return "/home"; }
  }
  ```
- Verify: try `next=https://x.com`, `//x.com`, `/\x.com` and `javascript:alert(1)`. Each should land on `/home`. `next=/reports?id=3` should still work.

## Should-fix

**[Should-fix] A network failure or timeout leaves the user with no feedback**
- Evidence: `src/Login.tsx:10`. `fetch` is not in a `try/catch`, so a network error rejects the handler and nothing is shown.
- Impact: the button appears to do nothing when the user is offline or the server is unreachable.
- Fix: catch the error and show "Couldn't reach the server. Check your connection and try again."

**[Should-fix] Every non-OK response is reported as wrong credentials**
- Evidence: `src/Login.tsx:11`. A 429, 500 or 503 also shows "Email or password is incorrect."
- Impact: a locked-out or rate-limited user, or one hitting a server outage, keeps retyping a correct password.
- Fix: show the credentials message only for 401/403, with separate copy for 429 and 5xx. Keep the credentials message generic so it doesn't reveal whether the account exists.

**[Should-fix] No pending state, so double submits are possible**
- Evidence: `src/Login.tsx:8-23`. There is no in-flight flag.
- Impact: Enter or a click repeated on a slow connection sends duplicate session requests. There is also no "Signing in…" feedback.
- Fix: add a `pending` state, set `aria-disabled` and ignore submits while it is true. Don't use native `disabled` on the button, because that drops keyboard focus mid-submit. Also clear the old error when a new attempt starts.

**[Should-fix] The error is not tied to the fields, and focus isn't managed**
- Evidence: `src/Login.tsx:22`. `role="alert"` does announce the message, which is good. But the inputs have no `aria-invalid` or `aria-describedby`, and focus stays on the button.
- Fix: give the error an `id`, point `aria-describedby` at it from the password input, and move focus to the password field or the error after a failed attempt.

**[Should-fix] Missing basics for a login form**
- Evidence: `src/Login.tsx:19-21`. There is no `required`, and no "Forgot password?" or account-recovery link. Users with a password manager are unaffected.
- Fix: add `required` and a recovery link. Check against the product's flow whether either is intentionally elsewhere.
