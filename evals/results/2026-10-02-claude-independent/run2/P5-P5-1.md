## Findings

**[Should-fix, needs server verification] The client sends identity, privilege and price fields from user-editable state**
Evidence: `src/checkout.ts:12` sends `isAdmin`, `userId` and a client-computed `total`. `src/user.ts:1` reads them from `sessionStorage`, which the user can edit.
Impact: if the server trusts any of these fields, a user could claim admin rights, act as another user, or set their own price. The code confirms the client sends them. Whether the server honours them is unverified, so I'm not claiming exploitability.
Fix: remove `isAdmin`, `userId` and `total` from the request body. The server should derive identity from the session cookie and price from SKUs and its own catalog. Send only `items` (`sku` and `qty`) and `coupon`. If the server still requires those fields, treat that as a server bug.
Verify: with an edited `sessionStorage` user and a tampered `total`, the server should ignore them or reject the request.

**[Should-fix] A failed order can look like a successful one**
Evidence: `src/checkout.ts:13-14` returns `res.json()` without checking `res.ok`. There is no `try/catch`.
Impact: a 4xx or 5xx response body is returned as if it were an order. A non-JSON error page (502, for example) throws an opaque `SyntaxError`. The UI can show success when the order failed, or a generic crash when it should show a retry message.
Fix: check `res.ok` and throw a typed error carrying the status and the server's message. Handle network failure separately so callers can show specific error and retry states.
Verify: mock 400, 409, 500, a non-JSON 502, and a network failure. Each should reach the caller as a distinct error.

**[Should-fix] No protection against duplicate order submission**
Evidence: `placeOrder` (`src/checkout.ts:5`) has no idempotency key, no in-flight guard and no abort or timeout.
Impact: a double click or a retry after a timeout can create duplicate orders. Callers aren't visible, so a guard there may exist.
Fix: send an `Idempotency-Key` header generated once per checkout attempt, if the server supports it. Also disable the submit control while the request is pending.
Verify: double-click the submit button and confirm only one order is created.

**[Should-fix] `getUser()` is brittle and untyped**
Evidence: `src/user.ts:1`.
Impact: corrupt stored JSON makes `JSON.parse` throw, and blocked storage makes `sessionStorage` throw. A missing user returns `{}`, which is typed `any`. Checkout then silently sends `userId: undefined` and `isAdmin: undefined`.
Fix: wrap the read in `try/catch`, validate the shape, and return `null` when there is no user. Make `placeOrder` fail clearly when the user is missing. If the identity fields are removed from the request (see the first finding), this mostly goes away.
Verify: unit tests for missing, corrupt and valid stored values.

**[Needs verification] Stale user data across account switches**
Evidence: `src/user.ts:1` reads a user cached in `sessionStorage`.
Impact: the user cache survives only for the tab session. I can't see the logout or login code that clears it, so I can't tell whether a second account in the same tab could inherit the previous user.
Verify: log out and log in as a different user in the same tab, then check what `getUser()` returns.

**[Should-fix] Refund is a destructive action with no safeguards in this component**
Evidence: `src/OrderView.tsx:9` calls `onRefund` directly. The prop is typed `() => void`.
Impact: there is no confirmation step, no pending or disabled state, and no way to show an error. That invites double refunds on a double click. The parent may add a confirmation, but I can't see it.
Fix: make the handler return a promise. Add a confirmation step that states the amount and order, a pending state that disables the button, and an error and success message in a live region.
Verify: use the keyboard to open and cancel the confirmation, double-click, and simulate a rejected refund.

**[Should-fix] Total is shown as a raw number**
Evidence: `src/OrderView.tsx:7`. The cart total in `src/checkout.ts:7` is also a float sum.
Impact: the user sees `19.9` instead of a formatted amount, with no currency. Float totals can show rounding drift.
Fix: use integer minor units, or have the server return the total. Format it with `Intl.NumberFormat` and an explicit currency and locale.

**[Should-fix, minor] `status` is in the `Order` type but never shown**
Evidence: `src/OrderView.tsx:1`.
Impact: users can't see whether the order is pending, shipped or refunded. After a refund there is also no visible state change. The edit and refund controls aren't hidden by status either, and that rule may belong on the server.
