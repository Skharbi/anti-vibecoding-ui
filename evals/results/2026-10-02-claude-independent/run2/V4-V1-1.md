## Findings

**[Should-fix] No declared character encoding**
- Evidence: Confirmed in `index.html:1`. There is no `<meta charset>`, and I can't see the server's `Content-Type` header.
- Impact: If the server doesn't send `charset=utf-8`, the browser may guess the encoding. The current content is ASCII, so nothing breaks today. The risk appears once real item names with non-ASCII characters are added.
- Fix: Add `<meta charset="utf-8">` as the first element in the head, or confirm the server sends the charset header.
- Verify: Check the response headers, then load a non-ASCII string and confirm it renders correctly.

**[Judgment call] Empty state is a dead end**
- Evidence: Confirmed at `index.html:1`. The only content is "No items." with no reason, next step or action.
- Impact: A user can't tell whether the list is truly empty, still loading, or failed to load. Nothing tells them how to add an item.
- Fix: Tie the copy to the real product. For example, say what an item is and add the create action. Add distinct loading and error states once data exists. Whether this is a defect depends on product context I don't have. The state may be a placeholder.
- Verify: Render each state (loading, empty, error, populated) and check that each is visually and textually distinct.

**[Judgment call] Generic title and heading**
- Evidence: Confirmed. `<title>` and `<h1>` are both "Items".
- Impact: Browser tabs, history and screen-reader page announcements can't be told apart from other pages.
- Fix: Use the product name and the specific view once they are known.

**[Judgment call] Viewport meta lacks `initial-scale=1`**
- Evidence: Confirmed. The content is `width=device-width` only.
- Impact: Modern browsers mostly handle this, and I did not render it. It is a low-risk difference.
- Fix: Use `width=device-width, initial-scale=1`. Do not disable zoom.
