## Privacy risks (confirmed in code)

1. **Card data is sent to a third-party log service.**
   - `PaymentForm.tsx:7` passes `input: values` to `reportError`.
   - `values` holds `cardNumber`, `cvc` and `amount`.
   - `errorReporting.ts:12` serializes it into the POST to `logs.example-observability.io`.
   - Any failed payment, including a plain 500, sends the full card number and CVC off-site.
   - This is the most serious problem. It is likely also a PCI DSS concern, because CVC must not be stored after authorization. That conclusion needs scope-specific confirmation from your compliance owner.

2. **The bearer token is sent in the log.** `errorReporting.ts:13` sends `session?.accessToken`. Anyone with access to the logs or the vendor could replay it. The token should never be in telemetry, and any tokens already sent should be treated as exposed and rotated.

3. **The user's email is sent on every report.** `errorReporting.ts:14` adds it with no stated need. An opaque user ID, or a hash if you need correlation, would cover the same use.

4. **`location.href` can leak secrets.** `errorReporting.ts:15` sends the full URL, including query string and hash. These often carry reset tokens, OAuth codes or search terms. Send `origin + pathname`, or a route template.

5. **Error text and stacks may contain user data.** `err.message` is sent unredacted. Messages built from server responses or user input can carry PII.

6. **Everything is sent without consent or retention controls.** I can't see a consent gate, sampling, or a documented retention period for this endpoint. Whether consent is legally required depends on jurisdiction and the vendor agreement, so treat that as something to verify.

## Useful diagnostics already collected

- Message, stack, `action`, `release`, user agent and URL are all useful for triage. The `release` field lets you match stacks to source maps.

## Diagnostic gaps

- **Missing context:** there is no timestamp, request or trace ID, HTTP status field, or `err.cause`. `pay failed 500` is the only server signal. Capture the status and a server correlation ID from a response header.
- **Reporter failures:** the reporter's `fetch` has no `.catch`, so an ingest outage becomes an unhandled rejection. It also checks no response status, and it sets no `Content-Type`.
- **No volume control:** there is no dedupe, sampling or rate limit. A retry loop or a broken release could flood the endpoint.
- **No global capture:** only the explicit `submitPayment` path reports errors. Nothing hooks `window.onerror`, `unhandledrejection` or a React error boundary, so most failures go unseen.
- **Retry risk:** `submitPayment` rethrows after reporting. The caller needs to avoid auto-retrying a non-idempotent payment, which should use an idempotency key. I couldn't verify this from the files given.

## Suggested direction

```ts
export function reportError(err: unknown, context: { action: string; status?: number; requestId?: string }) {
  const session = getSession();
  const body = JSON.stringify({
    message: scrub(err instanceof Error ? err.message : String(err)),
    stack: err instanceof Error ? err.stack : undefined,
    action: context.action,
    status: context.status,
    requestId: context.requestId,
    userId: session?.userId,               // opaque ID, no token or email
    page: location.origin + location.pathname,
    ua: navigator.userAgent,
    release: import.meta.env.VITE_RELEASE,
    ts: Date.now(),
  });
  fetch(INGEST_URL, { method: "POST", keepalive: true, headers: { "Content-Type": "application/json" }, body })
    .catch(() => {});
}
```

- Remove `input` from the payload and from the `PaymentForm.tsx:7` call. If you need form context, log field names or validity flags only.
- `scrub` should be an allowlist or regex redaction for card-like digit runs, emails and token patterns.
- Add global handlers and sampling or dedupe.
- Verify on the backend side what the ingest endpoint has already stored, who can read it, and how long it keeps data. Purge the card and token data if it was stored.
