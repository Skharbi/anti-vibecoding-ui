# Security review: admin projects UI

I read all three source files (`ProjectRow.tsx`, `api.ts`, `auth.ts`). I didn't run the app. `UserContext` isn't in the repo, so I couldn't check the provider or the server.

**Result: Fail.** There is one confirmed must-fix: an irreversible delete with no confirmation and no feedback. The most serious security risks depend on the server, so they are listed as verification work. A frontend review can't clear them.

## Must-fix

**[Must-fix] Irreversible delete with no confirmation, error handling or pending state**
- Evidence: `src/ProjectRow.tsx:11` calls `api.del(...)` straight from `onClick`. `src/api.ts:3` returns the raw `fetch` promise.
- Impact:
  - One misclick deletes a project.
  - `fetch` doesn't reject on 403, 404 or 500, so a failed delete looks the same as a successful one.
  - Nothing removes the row or refetches the list, so the UI never reflects the result.
  - Double-clicking sends duplicate requests.
  - A rejected promise (network error) goes unhandled.
- Fix:
  - Add a confirmation dialog that names the project.
  - Check `r.ok` and surface errors.
  - Disable the button while the request is pending.
  - Update or refetch the list on success.
  - Consider soft-delete or undo.
- Verify: Check `ProjectRow.tsx` for the new states, then delete as an admin and as a non-admin, once with the network offline and once with the server returning 403.

## Needs verification (server side)

These can't be confirmed from the frontend. They are the highest-impact risks if the backend is weak.

1. **Authorization on `DELETE /api/projects/:id`.**
   - Evidence: the only role check is client-side, at `ProjectRow.tsx:10`.
   - Hiding the button is not authorization. The server must independently enforce admin role (and ownership, if it applies) on every delete.
   - `ownerId` is in the props but never used. If non-admin owners should be able to delete, that rule isn't implemented anywhere visible.
   - Verify: as a non-admin, call the endpoint directly with another user's project id and expect 403 or 404.
2. **CSRF.**
   - Evidence: `src/api.ts:3` sends a state-changing `DELETE` with `credentials: "include"` and no CSRF token or custom header.
   - `base` comes from `VITE_API_URL`, which suggests a cross-origin API.
   - Whether this is exploitable depends on cookie `SameSite` attributes, the CORS policy and any server-side token check, none of which are visible here.
   - Verify: inspect the `Set-Cookie` attributes and CORS headers, and test a cross-site request.
3. **Session expiry.** Nothing handles 401 or 403 responses. Verify that the app doesn't keep showing admin controls after the session expires or the role changes.

## Should-fix

- **`user` may be null or undefined.**
  - Evidence: `ProjectRow.tsx:10` reads `user.role` unguarded, and `useCurrentUser` (`src/auth.ts:3`) returns the raw context value, so a missing provider or logged-out state would throw.
  - A crash is better than failing open, but this should use `user?.role` or an explicit loading/unauthenticated state.
- **`api.get` doesn't check `r.ok`.** `src/api.ts:4` parses error responses as data, so a 401 or 500 body can flow into the UI as if it were valid.
- **The path isn't encoded.** `ProjectRow.tsx:11` interpolates `project.id` directly. Use `encodeURIComponent(project.id)` as hardening against ids containing `/` or `..`. The id comes from the server, so I'd treat this as low risk.
- **`VITE_API_URL` has no fallback.** If it is unset, `base` is `undefined` and requests go to the literal path `"undefined/api/..."`. Fail fast at startup instead.
- **Accessible name.** Every row's button is just "Delete project", so screen-reader users can't tell which project it deletes. Use `aria-label={`Delete project ${project.name}`}`.
- **Empty `<td>` for non-admins.** This is minor. Confirm the table has a matching header.

## What I found fine

- No `dangerouslySetInnerHTML`, `innerHTML` or `eval`. `project.name` is rendered as escaped text.
- No secrets in the client code. `VITE_API_URL` is a public base URL, not a credential.
- No tokens in browser storage. Auth relies on cookies.
