**Short answer:** the code doesn't trap focus. It does the opposite, and the dialog is unreachable and unoperable from the keyboard. Both problems come from the same missing focus management. I only read the code. I haven't run it in a browser or with a screen reader.

## Confirmed defects (must-fix)

1. **Dialog controls aren't focusable** (`src/ConfirmModal.tsx:15,16,18`).
   - Cancel, Archive and ✕ are `<div>` and `<span>` elements with `onClick`.
   - They have no `tabindex`, no role and no key handlers, so Tab skips them and Enter/Space do nothing.
   - A keyboard user who opens the dialog can't confirm, cancel or close it.
   - Use real `<button type="button">` elements.

2. **Focus never moves into the dialog** (`:9-10`).
   - After Enter on "Archive project", focus stays on the trigger behind the overlay.
   - Nothing calls `focus()`, and the markup has no `autoFocus`.
   - The dialog opens, but keyboard focus is still outside it.

3. **The background stays interactive** (`:10`).
   - The overlay is only visual (`position: fixed`).
   - Tab moves through the page behind it, and focus disappears behind the scrim.
   - That is the "trapped" feeling you're seeing. Focus is lost behind the overlay, not held inside the dialog.
   - Use `<dialog>` with `showModal()`, or add `inert` or `aria-hidden` on the background plus a focus trap.

4. **No Escape handling** (`:10-19`). No `keydown` handler exists, and the only dismiss paths are mouse clicks.

5. **Focus indicators are removed** (`src/modal.css:5`).
   - `.btn:focus, .close:focus { outline: none; }` removes the focus ring with no replacement.
   - Once these become buttons, focus would be invisible. This fails WCAG 2.4.7.
   - Delete the rule, or use `:focus-visible` with a visible style.

6. **No dialog semantics** (`:10-12`).
   - There is no `role="dialog"` or `aria-modal`.
   - The title is a `<div>`, so the dialog has no accessible name. Add `aria-labelledby`, or use `<dialog>` and an `<h2>`.

7. **Focus isn't restored on close** (`:8-9`). The trigger has no ref and nothing refocuses it after close.

## Smaller issues (should-fix)

- The ✕ button has no accessible name. Add `aria-label="Close"`.
- The `.close` span comes last in the DOM, so once it's focusable the tab order will be wrong. Place it before the content.
- `.modal { width: 420px }` will overflow at 320px viewports. Use `width: min(420px, calc(100vw - 32px))` and a `max-height` with scroll.
- This is a destructive action, so initial focus should go to Cancel, not Archive.

## Suggested fix

The smallest correct change is a native `<dialog>`. It provides the focus trap, Escape handling, inert background and top-layer rendering:

```tsx
const ref = useRef<HTMLDialogElement>(null);
useEffect(() => {
  const d = ref.current;
  if (open) d?.showModal(); else d?.close();
}, [open]);

<dialog ref={ref} onClose={() => setOpen(false)} aria-labelledby="archive-title">
  <h2 id="archive-title">Archive this project?</h2>
  <p>…</p>
  <button type="button" autoFocus onClick={() => setOpen(false)}>Cancel</button>
  <button type="button" onClick={() => { onArchive(); setOpen(false); }}>Archive</button>
</dialog>
```

Native `<dialog>` restores focus to the trigger on close in current browsers. I'm stating that from memory and haven't verified it against a current source. If you need to support older browsers, add a ref-based refocus.
