## Findings

### Should-fix

1. **Unvalidated API response can blank the whole page** (`src/App.tsx:10-11,18`). This is confirmed from the code.
   - `r.json()` goes straight into `setNotes`, and `notes.map(...)` runs during render.
   - If the API ever returns a non-array, such as `{ "error": "..." }` with a 200 status, `.map` throws during render.
   - There is no error boundary, so React unmounts the whole tree. The user sees a blank page and `role="alert"` never fires.
   - Fix: check `Array.isArray` and the field types before calling `setNotes`. Treat anything else as the error state. Add an error boundary in `main.tsx`.

2. **Session expiry and permission failures aren't told apart** (`src/App.tsx:10,12`). This is confirmed from the code.
   - `401`, `403`, `500` and network failures all show "Couldn't load notes."
   - It fails closed, which is good: no data is shown. But users get no path to re-authenticate, and a permission denial looks like an outage.
   - Fix: branch on status. Send `401` to sign-in and show a distinct message for `403`.

3. **No cleanup on unmount or re-run** (`src/App.tsx:8-13`). This is confirmed from the code.
   - The fetch has no `AbortController`. Today it only affects React 18 StrictMode double-invocation.
   - It becomes a stale-state risk, or a cross-account data flash, once account switching or routing exists. See the note on user-specific state below.

4. **Dependencies are not pinned in the repo** (`package.json`). Supply-chain hygiene needs verification.
   - All versions are caret ranges and no lockfile is present, so builds aren't reproducible.
   - I did not check advisories or Vite 5.x and React 18 support status. Run `npm audit` and check provenance against current sources before treating either as a finding.
   - Fix: commit the lockfile and use `npm ci` in CI.

### Needs backend or runtime verification (can't be judged from this repo)

- **Authorization on `GET /api/notes`** (`src/App.tsx:9`).
  - The request sends cookies, and the client has no notion of team or tenant.
  - The server must scope results to the caller's team. Test with two accounts in different teams.
  - Confirm that the endpoint doesn't over-return fields.
- **CSRF.** The app currently only reads, so there's no exposure. Once notes can be created, edited or deleted with cookie auth, you'll need `SameSite` cookies plus a CSRF token or an equivalent check. UI confirmation is not a control.
- **Security headers.** `index.html` has no CSP meta tag, and headers can't be judged from source. Check these on the deployed origin:
  - a CSP such as `default-src 'self'`
  - `frame-ancestors` or `X-Frame-Options`
  - `X-Content-Type-Options: nosniff`
  - a referrer policy
  - HSTS
- **Cookie attributes and response caching.** Check `HttpOnly`, `Secure` and `SameSite` on the session cookie. Check `Cache-Control: private, no-store` on `/api/notes`, since notes are sensitive team data.
- **`/api` routing.** `vite.config.ts` has no proxy, so `/api` only works with a same-origin reverse proxy in production. In dev it will 404. Confirm there's no hardcoded cross-origin target, which would change the CORS and cookie picture.

### Passes (evidence in code)

- **XSS:** `title` and `body` render as React text children, which are auto-escaped. There is no `dangerouslySetInnerHTML`, `innerHTML`, `eval`, or URL-valued attribute. If you later render Markdown or links, sanitize them and allowlist URL schemes.
- **Secrets:** no tokens, keys or `VITE_*` variables in the client code.
- **Storage and telemetry:** no `localStorage`, `sessionStorage`, analytics, logging or third-party scripts.
- **Credentials:** `credentials: "include"` on a relative URL stays same-origin.
- **Source maps:** Vite's default build doesn't emit them, and none are enabled in the config.
