## Findings

**[Should-fix] Content-Type contradicts the body**
- **Evidence (Confirmed):** `client.js:1` sends `JSON.stringify(data)` with `Content-Type: text/plain`.
- **Evidence (Needs verification):** how the server reacts. It may return 415, parse the body as a string, or leniently parse it as JSON.
- **Impact:** if the server follows the header, every request fails or arrives as an unparsed string. If it parses leniently, the header gives CSRF protection nothing to work with. The URL is same-origin, so CORS preflight isn't relevant here, but `text/plain` is a "simple" content type. A server that relies on a JSON-only content-type check as its CSRF defence would be bypassed.
- **Fix:** send `application/json`, unless the contract explicitly requires `text/plain`. If it does, document why.
- **Verify:** an executed request against a test server returns the expected response. Another request with a wrong content type is rejected with 415 or 400.

**[Must-fix, pending callers] The function returns a raw `Response` with no error handling**
- **Evidence (Confirmed):** there is no `response.ok` check, no status mapping, no body parsing, and no `catch` or typed error.
- **Evidence (Needs verification):** whether callers check `ok`. None are present.
- **Impact:** `fetch` resolves on 4xx and 5xx. A caller that only uses `await send()` will show success when the save failed, and the user's data is lost without any signal. Network failure, validation error, 401/403, and 5xx all look the same to callers, so the UI can't show the right state or preserve entered values.
- **Fix:** have `send` throw a typed error (status, parsed error body, network vs. HTTP) and return parsed data on success. Separate 401/403 from validation (422) and server errors so the UI can handle each.
- **Verify:** unit tests with a mocked `fetch` for 200, 4xx, 5xx, and network rejection. Check that each caller renders an error state.

**[Should-fix] A non-idempotent POST with no timeout, abort, or duplicate guard**
- **Evidence (Confirmed):** no `AbortSignal`, timeout, or idempotency key in `client.js:1`.
- **Evidence (Likely):** double submits or retries can create duplicate items. This depends on the callers and the server.
- **Impact:** a hung request leaves the UI stuck in loading with no recovery. A double click or manual retry may create duplicates.
- **Fix:** accept an optional `signal` and apply a default timeout. Send an `Idempotency-Key` header if the server supports one. Disable the submit control while the request is pending.
- **Verify:** throttle or offline the network and confirm the request ends in a visible, retryable error. Double-click submit and confirm only one item is created.

**[Should-fix] `JSON.stringify` is unguarded**

- **Impact:** a synchronous throw bypasses any `.catch()` chain that callers attach to the returned promise.
- **Fix:** make the function `async` so everything surfaces as a rejection. Validate that `data` is defined.
- **Verify:** unit tests calling it with a circular object and with `undefined`.
