# Responsive review: `claims.html`

**Result: Fail on narrow screens.** I read the HTML and CSS but did not render the page, so the overflow findings come from the CSS arithmetic, not a screenshot or device test.

## Must-fix

**1. The sidebar takes most of a phone screen and stays on screen**
- Evidence: `claims.html:5-6`. `body` is `display:flex`, and `aside` is `width:260px; flex:none` with no breakpoint or media query anywhere in the file.
- Impact: at 375px, the nav uses about 70% of the width for three links. At 320px, 260px of fixed sidebar leaves roughly 60px for content, minus main's 20px of padding on each side.
- Fix: below about 768px, stack the layout (`flex-direction:column`) and turn the sidebar into a top bar or a menu button. Use `min-height:100vh` only on desktop.
- Verify: at 320, 375 and 768px, the nav takes at most one compact row and content gets the full width.

**2. The claims table forces page-level horizontal scroll**
- Evidence: `claims.html:8-9`. The table is `width:720px`, cells are `white-space:nowrap`, and nothing wraps it in a scroll container. `main` has no `min-width:0`, so the table's width pushes the whole page wider.
- Impact: reviewers have to pan the whole page sideways. The Status and Last updated columns sit off-screen, and the fixed footer and the note form get dragged around with the page.
- Fix: choose a pattern for narrow screens.
  - Quick option: wrap the table in `<div role="region" aria-label="Claims" tabindex="0" style="overflow-x:auto">`, add `min-width:0` to `main`, and use `width:100%; min-width:720px` on the table.
  - Better option for phones: below about 640px, render each claim as a stacked row with Patient and Status first, since those carry the triage decision.
- Verify: at 320px, `document.scrollingElement.scrollWidth` equals the viewport width, and any table scrolling happens inside the wrapper.

## Should-fix

**3. The fixed footer can cover content and focus**
- Evidence: `claims.html:7,10`. The footer is 64px, and `main` has 80px of bottom padding. On a phone the footer plus the browser chrome and on-screen keyboard take a large share of the viewport.
- Impact: the focused textarea or Submit button can end up behind the footer. Needs verification on a real device or emulator.
- Fix: add `scroll-padding-bottom: 80px` on `html` so focused elements scroll clear of the footer. Use `env(safe-area-inset-bottom)` for iOS, and check how it behaves when the keyboard is open.

**4. Touch targets are probably too small**
- Evidence: `claims.html:15,31`.
  - The footer button has no styling, so it uses the browser default of about 13px text and roughly 21px height.
  - The nav links are plain text stacked with `<br>`.
- Impact: hard to hit on a phone, and likely below the 24px WCAG 2.2 minimum (2.5.8). I haven't measured them, so this is likely, not confirmed.
- Fix: give buttons and links `min-height:44px` and add padding. Replace the `<br>` with a list or flex column with gaps.

**5. The form controls need two small fixes**
- Evidence: `claims.html:11`. The textarea has `width:100%` but no `box-sizing:border-box`, so it overflows its container by its padding and border, a few pixels.
- Its default font is about 13px, which can make iOS Safari zoom the page on focus (likely, needs device check).
- Fix: `textarea, button { font:inherit; box-sizing:border-box }`.

## Judgment calls and adjacent issues

- **Two competing primary actions:** "Submit review" sits in the form and "Approve selected" sits in the footer, and both look like default buttons. On a small screen it's unclear which acts on what. Differentiate them and consider moving the form's submit into the same bar.
- **Selection is non-functional:** the footer says "2 claims selected" but the table has no checkboxes. "Approve selected" has no confirmation or undo. That is a workflow bug, not a responsive one. It matters more on touch, where mis-taps are easier.
- **Smaller items:** `<nav>` has no `aria-label`, and the table has no `<caption>`.
