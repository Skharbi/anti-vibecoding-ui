# Performance analysis of `sql/monthly_revenue.sql`

This is a static read of the query and `schema.sql`. I don't have a database, row counts or an `EXPLAIN` plan, so the cost claims below are expectations, not measurements.

## What the query does
It lists customers whose email ends in `@acme.com`, with each one's order total for the current month. The list is sorted by that total, highest first.

## Problems, in order of impact

**1. The `orders` filter can't use an index (the main issue).**
`date_trunc('month', o.created_at) = date_trunc('month', now())` wraps the column in a function. Even a plain index on `created_at` can't be used for it. The correlated subquery therefore runs once per matching customer, and each run scans that customer's orders. The schema has no index on `orders.customer_id` either. Postgres doesn't create one for a foreign key, so each run is probably a **sequential scan of the whole `orders` table**. That makes the cost roughly *matching customers × total orders*.

**2. The `customers` filter always scans the whole table.**
`lower(c.email) LIKE '%@acme.com'` has two blockers:
- `lower()` on the column rules out any plain index on `email`.
- The leading `%` rules out a B-tree prefix match.

Every row in `customers` is read and lowercased. This is a single pass, so it costs less than problem 1, but it grows with table size.

**3. Smaller issues**
- The correlated subquery in the `SELECT` list runs once per customer. Postgres can't turn it into a join. A single aggregate would let it pick a hash join.
- Customers with no orders this month return `NULL` and sort last. That is probably what you want. Just be aware that it isn't a total of 0.
- `now()` is stable within a statement, so it is evaluated once. That part is fine.

## Suggested fixes

**Rewrite with a sargable range and one aggregate:**
```sql
SELECT c.id, c.name, o.month_total
FROM customers c
LEFT JOIN (
    SELECT customer_id, SUM(total) AS month_total
    FROM orders
    WHERE created_at >= date_trunc('month', now())
      AND created_at <  date_trunc('month', now()) + interval '1 month'
    GROUP BY customer_id
) o ON o.customer_id = c.id
WHERE c.email_domain = 'acme.com'   -- or the expression index below
ORDER BY o.month_total DESC NULLS LAST;
```

**Indexes:**
```sql
-- Range scan on the month, with customer_id and total in the index
CREATE INDEX orders_created_at_cust_idx
  ON orders (created_at) INCLUDE (customer_id, total);

-- Customer email suffix match; reverse the string so the match becomes a prefix
CREATE INDEX customers_email_rev_idx
  ON customers (reverse(lower(email)) text_pattern_ops);
-- then: WHERE reverse(lower(c.email)) LIKE reverse('@acme.com') || '%'
```
- If you only ever filter on one domain, a partial index is simpler:
  ```sql
  CREATE INDEX ON customers (id) WHERE lower(email) LIKE '%@acme.com';
  ```
  This only helps if the query keeps the exact same predicate.
- A `pg_trgm` GIN index on `lower(email)` also supports `LIKE '%...'`. It is a heavier index than the others.
- Also consider a plain `orders (customer_id, created_at)` index if you often look up a single customer's orders.
