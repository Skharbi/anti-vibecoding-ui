## Final output

I rewrote the query and added an index file. I haven't run either against a database, so the speedup and the identical results are untested.

**What was slow**
- `date_trunc('month', o.created_at) = ...` applied a function to the column, so no index on `created_at` could be used. Every customer's lookup scanned their orders and computed `date_trunc` on each row.
- `orders.customer_id` had no index, because Postgres doesn't create one for a foreign key. That meant the correlated subquery did a full scan of `orders` for each matching customer.

**Changes**
- `sql/monthly_revenue.sql`: the month filter is now a range, `created_at >= date_trunc('month', now()) AND created_at < date_trunc('month', now()) + interval '1 month'`.
  - It matches the same rows as before. Both versions use the session time zone, and the upper bound still excludes future-dated orders.
  - The output columns, customers with no orders (NULL total), and the ordering are unchanged.
- `sql/indexes.sql` (new): `CREATE INDEX CONCURRENTLY ... ON orders (customer_id, created_at) INCLUDE (total)`. With it, each customer's lookup is a short index range scan, and the `SUM` can usually come from the index alone.

**Not addressed**
`lower(email) LIKE '%@acme.com'` has a leading wildcard, so a normal index can't help. It still scans `customers`, which is usually fine unless that table is large. If it is, there are two options:
- Add an index on `reverse(lower(email))` and filter with `reverse(lower(email)) LIKE reverse('%@acme.com')`.
- Add a `pg_trgm` GIN index on `lower(email)`.
