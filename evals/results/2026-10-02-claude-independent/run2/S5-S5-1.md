# Review: `src/UploadReferral.tsx`

**Result: Fail.** There are four confirmed must-fix issues from reading the code. I did not run the component, so responsive layout, focus appearance and real server responses are not verified.

## Must-fix

**1. The success message makes a false security claim**
- Evidence: `UploadReferral.tsx:12` sets "Your file has been securely validated and is safe to upload." The only checks are the MIME type and extension at line 10.
- Impact: Both checks are trivially spoofed, and nothing inspects the file content. Telling users a referral document is "safe" misleads them, and it appears before anything has been uploaded.
- Fix: Show neutral text such as `referral.pdf · 1.2 MB · ready to upload`. Treat the client checks as convenience only, and do the real validation on the server.
- Verify: Select a renamed non-PDF file with a spoofed type. The UI must not say "safe" or "validated".

**2. "Uploaded." shows even when the upload fails**
- Evidence: `:18-19` never checks `res.ok` and has no `try/catch`. A 4xx or 5xx response still sets "Uploaded."
- Impact: A user can believe a referral was submitted when it wasn't. A network failure throws an unhandled rejection and shows no message.
- Fix: Check `res.ok`, catch errors, and show a specific error with a retry option.
- Verify: Mock a 413, a 500 and an offline request. Each should show an error and keep the file selected.

**3. Upload can send a stale file after an invalid pick**
- Evidence: At `:10` an invalid file returns early without `setFile(null)`. A previously chosen valid file stays in state.
- Impact: The input shows the new invalid file and the error message appears, but the Upload button stays enabled. Clicking it sends the old file. This is the wrong document going out in a referral flow.
- Fix: Clear `file` on every change event, including when the picker is cancelled and `f` is undefined (`:9`), then set it again only if the new file is valid.
- Verify: Pick a valid PDF, then a `.txt` file. Upload must be disabled.

**4. Double submit and missing pending state**
- Evidence: `upload()` at `:15-20` has no in-flight flag, and the button is only disabled when `!file` (`:27`).
- Impact: Repeated clicks send duplicate requests. There is no feedback while a large file uploads.
- Fix: Add a `status` of `idle | uploading | success | error`. Disable the button and show "Uploading…" while in flight.
- Verify: Throttle the network, click twice, and confirm a single request.

## Should-fix

- **Status is not announced to screen readers.** `<p>{msg}</p>` (`:26`) is not a live region, so errors and success are silent for AT users. Use `role="status"` for progress and success and `role="alert"` for errors, and keep the element always mounted. Also connect the error to the input with `aria-describedby`.
- **There is no state design beyond the happy path.** Missing pieces:
  - a size limit and a message for oversized files;
  - progress and cancel for large files;
  - a way to clear or replace the file after success (the form stays as-is, so a second click re-uploads);
  - a statement of the accepted file and size limit in the help text.
- **Sensitive-data context is missing.** A referral letter likely contains personal or health information. The screen doesn't say who can see the file or what happens next. This is a product-copy question for you, and the right wording depends on your data policy.
- **The `type` check can wrongly reject valid PDFs.** `f.type !== "application/pdf"` (`:10`) can fail when the OS or browser reports an empty type. This is Likely, not Confirmed. The extension check plus server validation may be enough, so verify across browsers before keeping the MIME check.
- **The button has no explicit `type="button"`.** It is harmless today, but it will submit the form if this is later wrapped in one.
- **There is no styling or visual design.** The markup is bare and has no hierarchy, spacing or file-name display. I can't judge brand fit without the surrounding app, so match your design system.
