# Signup form review (`src/SignupForm.tsx`)

I read the code only. I didn't run it, and there's no CSS in the repo, so I couldn't check responsive layout, focus styles or contrast. **Result: Fail.** There are confirmed must-fix issues, and several domains are unverified.

## Must-fix

**1. Errors for every field appear as soon as you type in one**
Evidence: `SignupForm.tsx:20-22`. `onChange` runs `validate(next)` on the whole form after each keystroke.
Impact: typing the first letter of the name immediately shows "Invalid email" and the long password error for fields the user hasn't reached. The email and password errors also stay on while the user is still typing a valid value. This is the most likely source of the frustration.
Fix: track which fields have been touched. Validate a field on blur, then re-validate it on change once it has shown an error. Validate everything on submit.
Verify: type in the name field and confirm no email or password errors appear.

**2. A failed submit wipes everything the user typed**
Evidence: `:33`, `setForm(initial)`.
Impact: after any server error the user has to retype all fields, including a password that took 12+ characters with rules.
Fix: keep the form values. Clear the password at most.
Verify: force a 500 response and confirm the name and email are still filled in.

**3. Missing feedback: success, pending and network failure**
Evidence: `:30-35`.
- When `res.ok` is true, nothing happens, so the user gets no confirmation and no redirect.
- There is no pending state, and the button stays enabled, so double-clicking can create duplicate requests.
- A rejected `fetch` (offline or timeout) is unhandled. The user sees nothing.
- The only server message is "Something went wrong", which gives no hint about a taken email or a rejected field.

Fix: add a `submitting` state that disables the button and shows "Creating account…". Wrap the call in try/catch. Show a specific error message, and map field errors from the response (for example 409 or 422) onto the matching inputs. Handle success explicitly.
Verify: test the success, 4xx, 5xx and offline paths.

**4. Fields have no labels, only placeholders**
Evidence: `:39, 41, 43`.
Impact: the hint disappears once the user types, so they can't check what a field was for. Placeholders are also not a dependable accessible name for screen readers.
Fix: add visible `<label htmlFor>` elements. Keep placeholders for examples only.
Verify: check that each input's accessible name is its label, and that clicking the label focuses the input.

**5. Errors aren't announced or linked to their fields**
Evidence: `:40, 42, 44, 45`. The errors are bare `<span>`s with no `aria-invalid`, no `aria-describedby` and no live region.
Impact: screen-reader users don't hear errors on submit. Nothing moves focus to the first invalid field, and the server error isn't announced either.
Fix: set `aria-invalid` and `aria-describedby` on each input. Render the server error in `role="alert"`. On a failed submit, focus the first invalid field.
Verify: do a keyboard-only and screen-reader pass.

## Should-fix

- **Missing input attributes** (`:39-43`): the email input has no `type="email"`, so mobile users get the wrong keyboard. There are no `autoComplete` values (`name`, `email`, `new-password`), no `name` attributes, and no `autoCapitalize` or `spellCheck` handling on email. Browsers and password managers can't help the user fill the form.
- **Password rules are hidden until broken** (`:14-15`): state the requirement up front as help text. Consider a show/hide toggle. A single regex with one combined message doesn't tell the user which rule failed. Check the composition rules against your password policy. Current guidance (NIST SP 800-63B) favours length over forced character classes. I'm recalling that from memory and haven't checked the current text.
- **Vague messages** (`:12-13`): "Required" and "Invalid email" don't say what to do. Use something like "Enter your full name" or "Enter an email like name@example.com".
- **Validation edge cases** (`:12`): a name of just spaces passes, so trim before checking.
- **Request construction** (`:30`): the body is a JSON string with no `Content-Type` header, so the browser sends `text/plain`. Whether your server accepts that depends on its contract, which I haven't seen. Setting `Content-Type: application/json` is cheap. I also can't tell from here how CSRF or credentials are handled.
