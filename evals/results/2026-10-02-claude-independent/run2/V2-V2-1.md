## Findings

**[Should-fix] Third-party analytics SDK loads unconditionally on page load**
- Evidence (Confirmed): `index.html:1`. The `<script>` is static, with no consent check, no conditional loader and no `async`/`defer`. Nothing in the file gates it.
- Impact: Fetching the script discloses the visitor's IP address, user agent and referrer to `analytics.example`, before any user action. What the SDK does after it runs (cookies, device IDs, event collection) is not visible here.
- Whether this is a compliance problem depends on jurisdiction, purpose and any consent mechanism elsewhere (consent tool, tag manager, server-side gating). All of those are unknown, so I'm not asserting a violation.
- Fix: Load the SDK only after the applicable lawful-basis check passes, using a small loader that injects the script. If no consent is required for this purpose and jurisdiction, document that decision instead.
- Verify: Load the page with a clean profile and look at the network panel and storage. The SDK request should not fire before the gate passes, and no cookies or storage entries should appear before then.

**[Should-fix] No visible transparency or control surface**
- Evidence (Confirmed): The markup has no privacy notice link, no explanation of what is collected, and no opt-out or preferences control.
- Impact: Users get no notice of the tracking. Whether a notice is required depends on the unknowns above.
- Fix: Add a privacy notice link and an accessible preferences control, sized to the actual obligations.
- Verify: Check the notice against the SDK's real data flows.

**[Needs verification] SDK behavior, identifiers and data flow**
- The following are not checkable from this file:
  - Which identifiers the SDK sets, such as cookies, localStorage or fingerprinting.
  - Which events and fields it collects, including whether it records DOM text, URLs or query strings.
  - Whether it uses session replay or autocapture.
  - Where the vendor processes the data, its retention period, and whether its role is processor or independent controller.
- `analytics.example` is a reserved placeholder domain, so this may be scaffolding rather than the real vendor.
- Verify: Read the vendor documentation and DPA, then run the page in a browser and inspect cookies, storage and outgoing payloads.

**[Needs verification] Supply-chain trust of a mutable remote script**
- Evidence (Confirmed): No `integrity` or `crossorigin` attribute is set. For a vendor-hosted SDK that updates, SRI is usually impractical.
- The script runs with full page privileges, so it can read anything rendered on the page. The page is currently non-sensitive, but a real dashboard would show account or business data.
- Fix: Consider self-hosting, or a CSP that limits script sources and `connect-src`. Check the response headers, since a CSP and a `Referrer-Policy` may already be set at deploy time.
